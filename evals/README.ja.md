# エージェントのハーネスを評価する

このリポジトリのハーネスとは、コーディングエージェントがコードのほかに読むものと、作業中に出会う仕組みのことである。`AGENTS.md` のファイルと、`.claude/` のフック、スキル、サブエージェントがそれにあたる。
TPL-0020 は、ハーネスをあえて小さく保つ。新しい指示を足せるのは、チェックでは捕まえられない失敗を評価が示したあとだけである。
このディレクトリが、その評価である。エージェントは、このリポジトリの作業を、ハーネスありで1回、なしで1回行う。採点が、それぞれの結果の価値を決める。

## 1回の実行が比べるもの

| 条件 | エージェントが受け取るもの |
|---|---|
| `harness` | いまのリポジトリ |
| `bare` | `AGENTS.md`、`CLAUDE.md`、`.claude/` を除いたリポジトリ |

ほかは、どちらの条件でも同じである。コード、ガイド、チェック、Git のフック、モデル、上限、エージェントが確認なしに使える道具（`allowed-tools.txt`）は変わらない。
`make check` はどちらの条件にもある。それを実行するようエージェントに伝えるのはハーネスだけであり、チェックが失敗したままターンを終えるのを止めるのもハーネスだけである。

1回の実行は、1つのコミットのファイルをチェックアウトの外のディレクトリにコピーし、そこに独立した Git リポジトリを作る。そのため、エージェントはこのリポジトリを変えられず、親ディレクトリの指示ファイルもエージェントに届かない。コピーには `evals/` がない。そこに解答を見つけたエージェントは、作業をしなくて済んでしまうからである。
利用者の設定とメモリは読み込まない。そのため、実行の結果は、誰のマシンで動かしたかに左右されない。
`bare` の実行のあとは、採点の前にハーネスのファイルを戻す。そのため、どちらの条件も、同じリポジトリとして採点される。

## 作業

作業は、ディレクトリ `tasks/<task>/` である。

| ファイル | 内容 |
|---|---|
| `task.txt` | エージェントへの依頼。人が頼むときのように、手順ではなく目的を書く |
| `grade.sh` | 作業の基準。それぞれの基準は、コピーの中でコマンドが成功すれば合格である |
| `solution.patch` | すべての基準に合格する変更。作業が実行できることと、採点が見分けられることを示す |

| 作業 | 依頼の内容 | 測るもの |
|---|---|---|
| `read-the-logs` | ガイドに新しい節を足す | 英語の文章と一緒に、対訳も変わるか（TPL-0021） |
| `booking-horizon` | 中核の文脈に業務の決まりを足し、新しい種類の problem を返す | 決まりがドメインにあり、ページ、文脈の README、画面の文言がそれに続くか（TPL-0004、TPL-0008） |

どの作業にも、このリポジトリのすべての変更に当てはまる基準が2つ加わる。`make check` が通ること、そして変更がチェックを弱めないことである。つまり、許可や無視のファイル、フック、チェックに触れず、無視のコメントも足さない。

## 実行する

```sh
make eval TASK=read-the-logs ARM=harness
make eval TASK=read-the-logs ARM=bare
make eval-report
```

`make eval` は、端末なしで Claude Code を起動する（`claude -p`）。実行した人のアカウントの利用枠を使い、1回に数分から30分かかる。どのチェックも、これを起動しない。
実行は `results/` に記録を書く。作業、条件、コミット、モデル、ターン数と時間、拒否されたコマンドの数、それぞれの基準とその結果である。エージェントの変更そのものは、リポジトリの外に残る。その場所は、実行の最後の行が示す。

| 変数 | 意味 | 既定値 |
|---|---|---|
| `EVAL_CLAUDE` | Claude Code のコマンド | `claude` |
| `EVAL_MODEL` | モデル | `sonnet` |
| `EVAL_MAX_TURNS` | ターン数の上限 | `150` |
| `EVAL_TIMEOUT` | 時間の上限（秒） | `2700` |
| `EVAL_REF` | 開始するコミット | `HEAD` |
| `EVAL_KEEP` | `1` にすると、実行のあともコピーを残す | 未設定 |

1回の実行から分かることは少ない。エージェントは、同じことを繰り返さないからである。結論を出す前に、それぞれの条件を何回か実行する。記録はコミットし、次の人が、判断の根拠を見られるようにする。

## 結果を読む

どちらの条件でも不合格になる基準は、ハーネスが助けていない作業である。まず、エージェントの変更を見る。基準が、依頼に書かれていないことを求めているのかもしれない。
ハーネスなしのときだけ不合格になる基準は、ハーネスが役に立っているところである。
ハーネスありで不合格になり、`make check` も捕まえなかった基準は、チェックの候補である。どのチェックでもその決まりを守れないときにだけ、`AGENTS.md` の1文にする。そのプルリクエストには、失敗を示した記録を書く（TPL-0020）。

## 作業を足す

1. チームの人が頼みそうな変更で、結果をコマンドで判定できるものを選ぶ。
2. `task.txt` を、その人が頼むように書く。何がほしいかと、その理由を書き、触るファイルの一覧は書かない。その一覧こそ、評価が測るものである。
3. `grade.sh` に、関数 `grade_task` を書く。この関数が、基準ごとに `criterion <name> <command>...` を呼ぶ。動作は外から判定する。`booking-horizon` の受け入れテストが API を通して判定するのと同じである。ある1つの解答だけが選ぶ名前を探す基準は、よい仕事を不合格にする。
4. 自分でその作業をし、変更を `solution.patch` として保存する（`git diff > evals/tasks/<task>/solution.patch`）。
5. `make test-evals` を実行する。いまのリポジトリがすでに作業の基準に合格するとき、解答がもう適用できないとき、解答が基準に不合格のときに、失敗する。

`make test-evals` は `make check-all` の一部である。`evals/` のファイル、または解答の変えるファイルが対象に入ると動く。そのため、解答の下にあるコードを変えたときは、解答をそれに合わせるまで失敗する。
