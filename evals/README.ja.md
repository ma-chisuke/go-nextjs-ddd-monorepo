# エージェントのハーネスを評価する

このリポジトリのハーネスとは、コーディングエージェントがコードのほかに読むものと、作業中に出会う仕組みのことである。`AGENTS.md` のファイルと、`.claude/` のフック、スキル、サブエージェントがそれにあたる。
TPL-0020 は、ハーネスをあえて小さく保つ。新しい指示を足せるのは、チェックでは捕まえられない失敗を評価が示したあとだけである。
このディレクトリが、その評価である。エージェントは、このリポジトリの作業を、ハーネスありで1回、なしで1回行う。採点が、それぞれの結果の価値を決める。

## 1回の実行が比べるもの

| 条件 | エージェントが受け取るもの |
|---|---|
| `harness` | いまのリポジトリ |
| `bare` | `AGENTS.md`、`CLAUDE.md`、`.claude/` を除いたリポジトリ。それらがあって初めて意味を持つものも除く。フックのテストと、指示のファイルを挙げる README の行である |

ほかは、どちらの条件でも同じである。コード、ガイド、チェック、Git のフック、モデル、上限、エージェントが確認なしに使える道具（`allowed-tools.txt`）は変わらない。
`make check` はどちらの条件にもある。それを実行するようエージェントに伝えるのはハーネスだけであり、チェックが失敗したままターンを終えるのを止めるのもハーネスだけである。

1回の実行は、1つのコミットのファイルをチェックアウトの外のディレクトリにコピーし、そこに独立した Git リポジトリを作る。そのため、エージェントはこのリポジトリを変えられず、親ディレクトリの指示ファイルもエージェントに届かない。コピーには `evals/` がない。そこに解答を見つけたエージェントは、作業をしなくて済んでしまうからである。
実行する人の設定とメモリは読み込まない。そのため、実行の結果は、誰のマシンで動かしたかに左右されない。
エージェントが作業する前は、どちらの条件でも `make check` が通る。そのため、実行のあとで失敗するチェックは、エージェントの仕事の結果である。
`bare` の実行のあとは、採点の前にハーネスのファイルを戻す。そのため、どちらの条件も、同じチェックで採点される。

## 作業

作業は、ディレクトリ `tasks/<task>/` である。

| ファイル | 内容 |
|---|---|
| `task.txt` | エージェントへの依頼。人が頼むときのように、手順ではなく目的を書く |
| `grade.sh` | 作業の基準。それぞれの基準は、コピーの中でコマンドが成功すれば合格である |
| `solution.patch` | すべての基準に合格する変更。作業が実行できることと、採点が見分けられることを示す |

| 作業 | 依頼の内容 | 測るもの |
|---|---|---|
| `read-the-logs` | ガイドに新しい節を足す | 英語の文章と一緒に、対訳も変わるか（TPL-0021） |
| `booking-horizon` | 中核の文脈に業務の決まりを足し、新しい種類の problem を返す | 決まりがドメインにあり、ページ、文脈の README、画面の文言がそれに続くか（TPL-0004、TPL-0008） |
| `rename-room` | 補完の文脈の API に操作を足し、会議室の名前を変えられるようにする | 操作が API の文書から始まり、生成コード、クエリ、2つのストア（本物と、API テストが使う偽物）、API テスト、文脈の README がそれに続くか（TPL-0006、TPL-0007） |
| `room-floor` | 会議室に、データベースに保存する省略可能なプロパティを足す | スキーマ、クエリ、生成コード、API の文書がそろって変わり、データを持つデータベースにそのまま当てられるスキーマの変更になっているか（TPL-0010、TPL-0011） |
| `time-zone-in-mail` | 統合イベントにプロパティを足し、受け取る側がそれを読む | 2つの文脈の間の契約が、両側とも互換を保って変わるか。新しいバージョンを作らず、どちらの文脈も相手を import しないか（TPL-0005、TPL-0013） |
| `reservation-length` | 画面に情報を1つ足す。予約ごとの長さである | 長さを出す処理が純粋なロジックで単体テストを持ち、サーバーが描くページがそれを表示し、ブラウザーのシナリオがそれを確かめるか |

どの作業にも、このリポジトリのすべての変更に当てはまる基準が2つ加わる。`make check` が通ること、そして変更がチェックを弱めないことである。つまり、許可や無視のファイル、フック、チェックに触れず、無視のコメントも足さない。

## 実行する

```sh
make eval EVAL_TASK=read-the-logs EVAL_ARM=harness
make eval EVAL_TASK=read-the-logs EVAL_ARM=bare
make eval-report
```

`make eval` は、端末なしで Claude Code を起動する（`claude -p`）。実行した人のアカウントの利用枠を使い、1回に1分から45分かかる。どのチェックも、これを起動しない。
実行は `results/` に記録を書く。作業、条件、コミット、モデル、時間、出力トークン数、拒否されたコマンド、それぞれの基準とその結果である。記録のターン数は、実行の最後の区間のものである。バックグラウンドのコマンドがエージェントを起こすたびに、Claude Code がターン数を0から数え直すからである。実行のあいだで、ターン数を比べてはならない。アカウントの利用枠の上限か API のエラーで終わった実行は、記録を書かず、`make eval` は失敗する。エージェントの変更そのものは、リポジトリの外に残る。その場所は、実行の最後の行が示す。

| 変数 | 意味 | 既定値 |
|---|---|---|
| `EVAL_CLAUDE` | Claude Code のコマンド | `claude` |
| `EVAL_MODEL` | モデル | `sonnet` |
| `EVAL_MAX_TURNS` | ターン数の上限 | `150` |
| `EVAL_TIMEOUT` | 時間の上限（秒） | `2700` |
| `EVAL_REF` | 開始するコミット | `HEAD` |
| `EVAL_KEEP` | `1` にすると、実行のあともコピーを残す | 未設定 |

1回の実行から分かることは少ない。エージェントは、同じことを繰り返さないからである。結論を出す前に、それぞれの条件を何回か実行する。記録はコミットし、次の人が、判断の根拠を見られるようにする。

## 結果を読む

どちらの条件でも不合格になる基準は、ハーネスが助けていない作業である。まず、エージェントの変更を見る。基準が、依頼に書かれていないことを求めているのかもしれない。
ハーネスなしのときだけ不合格になる基準は、ハーネスが役に立っているところである。
ハーネスありで不合格になり、`make check` も捕まえなかった基準は、チェックの候補である。どのチェックでもその決まりを守れないときにだけ、`AGENTS.md` の1文にする。そのプルリクエストには、失敗を示した記録を書く（TPL-0020）。

## 作業を足す

1. チームの人が頼みそうな変更で、結果をコマンドで判定できるものを選ぶ。
2. `task.txt` を、その人が頼むように書く。何がほしいかと、その理由を書き、触るファイルの一覧は書かない。その一覧こそ、評価が測るものである。
3. `grade.sh` に、関数 `grade_task` を書く。この関数が、基準ごとに `criterion <name> <command>...` を呼ぶ。動作は外から判定する。`booking-horizon` の受け入れテストが API を通して判定するのと同じである。ある1つの解答だけが選ぶ名前を探す基準は、よい仕事を不合格にする。
   採点は、自分用の Docker もネットワークも使わない。コピーにないものは、`run.sh` が「What a grader may use」の下に挙げる関数から得る。`with_database` は、コピーのスキーマを当てた自分用のデータベースを、手元の PostgreSQL に作る。`free_port` は、空いているポートを返す。`integration_tests` は、文脈の統合テストを実行する。`own_dependencies` は、Node のパッケージをコピーの中にインストールする。サーバーを起動した採点は、失敗したときも含めて、そのサーバーを止める。
4. 自分でその作業をし、変更を `solution.patch` として保存する。

   ```sh
   git add --all && git diff --cached -- . ':!*.gen.go' ':!*.gen.ts' | sed -e '/^index /d' -e 's/^\(@@ [^@]* @@\).*/\1/' > evals/tasks/<task>/solution.patch
   ```

   このコマンドは、生成されたコードを除く。`make test-evals` が、解答を当てたあとに `make gen` で生成し直すからである。こうすると、API 文書を変更しても、API に触れる作業の解答が一斉に壊れることがない。Git のオブジェクトの名前を書いた行と、各ハンクの行番号に続く文字列も除く。後者は、Git が単語の途中で切ってしまう。どちらも、つづりのチェックが単語として読んでしまう。
5. `make test-evals` を実行する。手元の PostgreSQL が動いていなければ、このターゲットが起動する。このターゲットは、最初に `bare` の条件を確かめる。ハーネスのないコピーで `make check` が通り、ハーネスを戻したあとも通ることである。作業ごとには、いまのリポジトリがすでに作業の基準に合格するとき、解答がもう適用できないとき、解答が基準に不合格のときに、失敗する。それぞれの基準が捕まえるはずの壊し方で解答を壊し、その基準が不合格になることも確かめる。

`evals/` の外の文書は、このディレクトリの中にリンクを張らず、パスで名指しする。実行は、コピーからこのディレクトリを取り除く。リンクがあると、コピーの中でそれが切れ、作業と関係のない理由で `make check` が失敗する。解答も同じ種類のコピーで採点するので、`make test-evals` はそのようなリンクで失敗する。

`make test-evals` は `make check-all` の一部である。`evals/` のファイル、または解答の変えるファイルが対象に入ると動く。そのため、解答の下にあるコードを変えたときは、解答をそれに合わせるまで失敗する。
