# network

1 つの環境のネットワークを作るモジュールである。VPC を作り、アベイラビリティーゾーンごとに、公開・非公開・データベースの 3 種類のサブネットを置く（TPL-0015）。

| サブネット | 置くもの | VPC の外への経路 |
|---|---|---|
| 公開 | Web フロントエンドのロードバランサー | インターネットゲートウェイ |
| 非公開 | 各文脈と Web フロントエンドのタスク | 既定ではなし。AWS のサービスには VPC エンドポイントで届く |
| データベース | Aurora のクラスター | なし |

インターネットから届くのは、公開サブネットに置いたものだけである。そのため、文脈の API は、置き場所によって非公開になる（TPL-0014）。

## タスクから AWS への経路

既定では、非公開サブネットの中からインターネットには出られない。
タスクは、呼び出す AWS のサービスに VPC エンドポイント（AWS PrivateLink）で届く。Amazon S3 にはゲートウェイエンドポイントを、`interface_endpoints` の各サービスにはインターフェイスエンドポイントを置く。
通信は VPC の中にとどまり、タスクのセキュリティグループは VPC の外のアドレスを許可しない。許可するのは、エンドポイントのセキュリティグループ（`endpoints_security_group_id`）と Amazon S3 のプレフィックスリスト（`s3_prefix_list_id`）への HTTPS である。

AWS は、NAT ゲートウェイを、AWS のサービスに届く最も簡単な方法だと説明している。同時に、NAT ゲートウェイではタスクの通信先を絞れない、という代償も挙げている。
AWS Well-Architected Framework のセキュリティの柱は、マネージドサービスに届く既定の方法として VPC エンドポイントを勧めている。
このテンプレートは、その勧めに従う。

- インターフェイスエンドポイントは、ゾーンごとに時間単位で課金される。`interface_endpoints_in_every_zone = false` にすると、エンドポイントごとのネットワークインターフェイスが 1 つになる。費用は下がるが、そのゾーンの障害で使えなくなる。stg のような環境に向く。
- AWS の外のサービスを呼ぶ文脈には、インターネットへの経路が要る。`nat_gateways` を `single` か `per-zone` にし、その文脈のセキュリティグループで通信を許可する。
- `interface_endpoints` にないサービスには、タスクから届かない。タスクが呼ぶサービスは、一覧に足す。
- VPC の既定のセキュリティグループにはルールがない。VPC のフローログは CloudWatch Logs に送る。

AWS にはまだ適用していない。Amazon SES の API のエンドポイントのサービス名 `email` は、Amazon SES の文書に従ったが、文書は名前をそのままの形では書いていない。初めて適用するときに、`aws ec2 describe-vpc-endpoint-services` で確かめる。

`tests/` のテストは、AWS provider のモックに対してモジュールを plan する。そのため、`make check-all` は AWS のアカウントなしでテストを実行する（`validate-terraform`）。

入力、出力、リソースの一覧は、terraform-docs がコードから[英語版](README.md)に書き出す。コードの中の説明は英語なので、一覧は英語版だけにある。
