# github-oidc

GitHub Actions が、保存した鍵なしで 1 つの AWS アカウントに入るためのロールを作るモジュールである（TPL-0018）。
ジョブは GitHub に短命のトークンを求める。AWS は、ロールの信頼ポリシーがトークンのサブジェクトを名指ししているときに、トークンをそのロールの認証情報に交換する。

| ロール | 引き受けられるもの | できること |
|---|---|---|
| `github-plan` | このリポジトリのプルリクエストのジョブ | インフラの読み取り（`ReadOnlyAccess`）と、state のロック |
| `github-deploy` | この環境に対応する GitHub の環境を名指しするジョブ | 変更の適用（`deploy_policy_arns`） |

stg と prd のアカウントは、それぞれ自分の 2 つのロールを持つ。そのため、一方の環境の認証情報は、もう一方では役に立たない（TPL-0015）。

- どちらの信頼ポリシーも、サブジェクトの全体を `StringEquals` で比べる。`repository` には、ワイルドカードなしで 1 つのリポジトリを書く。所有者のすべてのリポジトリのように広く一致する条件は、誰もレビューしていないコードにロールを渡してしまう。
- どのブランチがデプロイできるか、ジョブの前に人が承認するかは、GitHub の環境の設定が決める。prd には、レビュアーを必須にする（[GitHub の設定](../../../docs/guides/github-settings.ja.md)）。
- GitHub は、フォークからのプルリクエストにトークンを渡さない。そのため、そのプルリクエストでは plan が走らない。
- デプロイするロールは、既定で `AdministratorAccess` を持つ。このロールは IAM ロールを作るので、ポリシーを狭めても届く範囲は限られない。範囲を限るのは、誰がこのロールを引き受けられるかである。

このモジュールは、管理者の権限を持つ人が、アカウントごとに 1 度適用する。まだ存在しないロールを、ワークフローは引き受けられないからである。そのあとの変更は、ほかの変更と同じくプルリクエストを通る。

AWS にはまだ適用していない。サブジェクトは GitHub の文書に従った。リポジトリを不変の形で書く場合について、文書はブランチのサブジェクトだけを示している。ここでは、プルリクエストと GitHub の環境のサブジェクトも同じ形で組み立てた。AWS がトークンを拒んだら、出力の `plan_subject` と `deploy_subject` を、トークンの `sub` クレームと比べる。

入力、出力、リソースの一覧は、terraform-docs がコードから[英語版](README.md)に書き出す。コードの中の説明は英語なので、一覧は英語版だけにある。
