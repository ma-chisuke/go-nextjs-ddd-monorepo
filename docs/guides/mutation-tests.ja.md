# ミューテーションテスト

カバレッジからわかるのは、テストがどの行を実行するかである。ある行が間違っていたときにテストが失敗するかどうかは、カバレッジからはわからない。
この問いに答えるのがミューテーションテストである。道具がコードを1か所だけ小さく変え、変えたコードに対してテストを実行する。変え方には `<` を `<=` にする、`true` を `false` にする、文を1つ削除するといったものがある。
個々の変更をミュータントと呼ぶ。失敗するテストがあれば、そのテストはミュータントを殺したことになる。どのテストも通るミュータントは生き残り、テストが守っていない規則があることを示す。

## test-mutation が調べるもの

`make test-mutation` は、`tools/go.mod` が固定する gomutants を、`make/go.mk` の `MUTATION_PACKAGES` が並べるパッケージに対して実行する。並べるのは中核の文脈ごとのドメインとユースケースであり、業務の規則はここにある（TPL-0003）。
Reservation では、時間帯の重なり、会議室の定員、15分の区切り、時間帯の長さの上限、過去、取り消しの期限がその規則である。
補完の文脈はミューテーションの対象にしない。そのユースケースはトランザクションスクリプトであり、テストはデータベースに対して実行する。そのため、実行は遅いうえに、わかることが少ない。

- gomutants は `go test` のオーバーレイでコードを変えるので、ソースのファイルに書き込まない。
- ミュータントごとに実行するのは、そのミュータントのパッケージのテストのうち、変えた行を実行するものだけである。したがって、ドメインの規則はドメインのテスト自身が守らなければならない。API のテストは数に入らない。
- 生き残ったミュータントは1つでもチェックを失敗させる。どのテストも実行しない行のミュータントも同じである。到達すべき割合はない。80パーセントのような閾値を置くと、規則が誰にも気付かれずにすり抜けてしまう。
- テストを終わらなくしたミュータントは、殺したものとして数える。テストが気付いたからである。コンパイルできないミュータントは数えない。
- コードと同じ機械語にコンパイルされるミュータントは等価であり、gomutants が自分で除く（`--detect-equivalent`）。

このチェックは `make check-all` に含まれる。並べたパッケージの Go のファイル、`backend/go.mod`、`equivalent-mutants.allow`、チェックの定義のいずれかが範囲に入ると実行する。
2026年11月に Reservation のドメインとユースケースで実行したところ、ミュータントは338個で、ほかの作業で忙しいノートパソコン上で、一度に4個ずつ実行して約100秒かかった。
一度に実行するミュータントの数は `MUTATION_WORKERS` で決める。既定はプロセッサの数の半分である。

## 一つのパッケージだけを実行する

```sh
make test-mutation MUTATION_PACKAGES=backend/internal/reservation/internal/domain
```

gomutants の報告は、すべてのミュータントとその状態を含めて `.cache/mutation/backend.json` に残る。

中核の文脈を加えるときは、その `internal/domain` と `internal/app` を `MUTATION_PACKAGES` に加える。

## 指摘の読み方

生き残ったミュータントは、次のような指摘になる。

```text
backend/internal/reservation/internal/domain/reservation.go:168: [mutation/survived] every test passes with `<` changed to `<=` (CONDITIONALS_BOUNDARY, mutant backend/internal/reservation/internal/domain/reservation.go:checkTerms:CONDITIONALS_BOUNDARY#2). ...
```

この行は `attendees < 1` であり、予約の参加人数は少なくとも1人という規則にあたる。参加人数がちょうど1人の予約を試すテストがなかったので、規則が「少なくとも2人」になってもすべてのテストが通る。

ミュータントの名前は `<file>:<function>:<type>#<n>` であり、その関数の中でその種類の n 番目の箇所を指す。ファイルのほかの箇所を変えても名前は変わらない。同じ関数を変えると、番号は振り直されることがある。
`[mutation/not-covered]` は、どのテストもまったく実行しない行を指す。

1つのミュータントだけを、その判定とともに実行するには次のようにする。

```sh
make mutant ID='backend/internal/reservation/internal/domain/reservation.go:checkTerms:CONDITIONALS_BOUNDARY#2'
```

結果は `KILLED` か `LIVED` で表示され、ミュータントが生き残ると失敗する。
ミュータントでテストが失敗するか通るかを手で確かめるには、指摘の行で指摘のとおりにコードを変え、そのパッケージに `go test` を実行し、変更を戻す。

## 生き残ったミュータントへの対処

生き残ったミュータントは、次の2つのどちらかを問うている。

- このコードがすることを確かめるテストはあるか。たいていはなく、対処はその変更で失敗するテストである。そのパッケージのテストの書き方に合わせ（多くはテーブル駆動テストの行を1つ足す）、テストが守る規則を名前にする。先の指摘なら、主催者1人だけの予約が対処になる。
- そのコードは必要か。後の検査が繰り返す条件や、起こりえない分岐からは、どのテストも殺せないミュータントが生まれる。コードを単純にし、それだけで1つのコミットにする。たとえば、あるユースケースは、すべてのエラーが `found` を真にして返ってくるのに `found || err != nil` を調べていた。今は1つのフラグだけを調べる。

行を実行するだけのテストは、何も殺さない。変更で変わるはずの結果を検証する。
テストの欠落ではなくコードの誤りを生き残ったミュータントが示しているなら、コードを直してそのことをコミットに書く。

## 許可がふさわしい場合

ミュータントには等価なものがある。変更がコードの動作を変えようがないため、どのテストもコードと区別できない。
まず、ミュータントが消えるまでコードを変えることを選ぶ。たとえば、会議室が開く時刻と閉まる時刻は、それぞれ別々に秒を指定して組み立てていた。時間帯は15分の区切りに乗るので、片方だけを1秒ずらしても何も変わらなかった。今は両方を1つの関数から得るので、変更は両方をずらし、境界のテストがそれに気付く。

コードを変えられないときは、ルートの `equivalent-mutants.allow` でミュータントを生き残らせる。書き方はミュータント1つにつき1行である。

```text
# <mutant> | <original> -> <replacement> | <reason>
```

- ミュータントと変更は、指摘が示すとおりに書く。
- 理由には、変更が等価であることの証明を書く。「テストしにくい」は証明ではない。テストで殺せるミュータントには、書くべきテストがある。
- 行を足すかどうかは、レビューで決めることである。エージェントは行を書かず、指摘と証明を添えて作業を止め、判断を求める。
- 生き残ったミュータントのどれにも一致しない行は、チェックを失敗させる（`mutation/unused-allowance`）。理由のない行も同じである（`mutation/allowance-format`）。テストがミュータントを殺したときや、コードが変わったときには、その行を消すことになるので、このファイルに古い行は溜まらない。
