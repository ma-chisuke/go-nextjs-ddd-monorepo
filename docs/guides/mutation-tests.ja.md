# ミューテーションテスト

カバレッジからわかるのは、テストがどの行を実行するかである。ある行が間違っていたときにテストが失敗するかどうかは、カバレッジからはわからない。
この問いに答えるのがミューテーションテストである。道具がコードを1か所だけ小さく変え、変えたコードに対してテストを実行する。変え方には `<` を `<=` にする、`true` を `false` にする、文を1つ削除するといったものがある。
個々の変更をミュータントと呼ぶ。失敗するテストがあれば、そのテストはミュータントを殺したことになる。どのテストも通るミュータントは生き残り、テストが守っていない規則があることを示す。

## ミューテーションテストが調べるもの

`make check-all` には、コードの言語ごとに1つずつ、ミューテーションテストのチェックがある。`test-mutation` は業務の規則を持つ Go のパッケージに gomutants を実行し、`test-mutation-frontend` はフロントエンドの純粋なロジックに StrykerJS を実行する。
どちらも同じ規則に従う。

- 生き残ったミュータントは1つでもチェックを失敗させる。どのテストも実行しない行のミュータントも同じである。到達すべき割合はない。80パーセントのような閾値を置くと、規則が誰にも気付かれずにすり抜けてしまう。
- ミュータントごとに実行するのは、変えた行を実行する単体テストだけである。API のテストやブラウザーでのテストは数に入らない。
- テストを終わらなくしたミュータントは、殺したものとして数える。テストが気付いたからである。コンパイルできないミュータントは数えない。
- どちらの道具もソースのファイルに書き込まない。gomutants は `go test` のオーバーレイでコードを変え、StrykerJS は `.cache/mutation/stryker/` に置いたソースの写しを変える。
- 一度に実行するミュータントの数は `MUTATION_WORKERS` で決める。既定はプロセッサの数の半分である。

### Go：test-mutation

`make test-mutation` は、`tools/go.mod` が固定する gomutants を、`make/go.mk` の `MUTATION_PACKAGES` が並べるパッケージに対して実行する。並べるのは中核の文脈ごとのドメインとユースケースであり、業務の規則はここにある（TPL-0003）。
Reservation では、時間帯の重なり、会議室の定員、15分の区切り、時間帯の長さの上限、過去、取り消しの期限がその規則である。
補完の文脈はミューテーションの対象にしない。そのユースケースはトランザクションスクリプトであり、テストはデータベースに対して実行する。そのため、実行は遅いうえに、わかることが少ない。
ミュータントごとに実行するのは、そのミュータントのパッケージのテストだけである。したがって、ドメインの規則はドメインのテスト自身が守らなければならない。
コードと同じ機械語にコンパイルされるミュータントは等価であり、gomutants が自分で除く（`--detect-equivalent`）。

このチェックは、並べたパッケージの Go のファイル、`backend/go.mod`、`equivalent-mutants.allow`、チェックの定義のいずれかが範囲に入ると実行する。
2026年11月に Reservation のドメインとユースケースで実行したところ、ミュータントは338個で、ほかの作業で忙しいノートパソコン上で、一度に4個ずつ実行して約100秒かかった。
中核の文脈を加えるときは、その `internal/domain` と `internal/app` を `MUTATION_PACKAGES` に加える。

### フロントエンド：test-mutation-frontend

`make test-mutation-frontend` は、`frontend/package.json` が固定する StrykerJS とその tap ランナーを実行する。対象は、`frontend/src/` のモジュールのうち、隣に単体テスト（`*.test.ts`）を持つものである。これらは純粋なロジックであり、フォームを読み取り、problem の種類ごとの文言を選び、タイムゾーンの中の時刻を変換する。
`frontend/stryker.config.mjs` は単体テストから対象のモジュールを求める。そのため、テストを持つモジュールを新しく加えると、設定を書き換えなくても、そのモジュールは対象となる。コンポーネントとサーバーのモジュールには単体テストがない。ブラウザーでテストするからであり（`make e2e`）、ミューテーションの対象にもしない。

- 単体テストは、`make test-frontend` と同じく Node のテストランナーで、テストのファイルごとに別々のプロセスで実行する。StrykerJS はテストのファイル1つを1つのテストとして数え、ミュータントの行に届くテストのファイルをすべて実行する。そこには、変えたモジュールを import するモジュールのテストも入りうる。
- 終わらないループは、ミュータントが実行された回数を数えて止める。この回数はマシンによらない。それ以外は時間で止め、その時間の下限を30秒にしている。忙しいマシンが遅いテストを停止と取り違えると、生き残ったミュータントが隠れてしまうからである。実際、下限が5秒のときには、負荷が100のマシンで52個のミュータントが時間切れになった。
- StrykerJS は等価なミュータントを見分けない。

このチェックは、対象のモジュールかその単体テストが範囲に入ると実行する。`frontend/stryker.config.mjs`、`frontend/package.json`、`equivalent-mutants.allow`、`tools/stryker/`、チェックの定義のいずれかが範囲に入ったときも同じである。
2026年11月に単体テストのある8つのモジュールで実行したところ、ミュータントは737個で、ノートパソコン上で一度に4個ずつ実行して約75秒かかった。3回の実行で、どのミュータントの状態も同じだった。

## 一部だけを実行する

```sh
make test-mutation MUTATION_PACKAGES=backend/internal/reservation/internal/domain
make test-mutation-frontend MUTATION_MODULES=frontend/src/lib/input.ts
```

報告は、すべてのミュータントとその状態を含めて `.cache/mutation/backend.json` と `.cache/mutation/frontend.json` に残る。
フロントエンドの一部のモジュールだけを実行すると、ほかのモジュールの許可は調べない。

## 指摘の読み方

生き残ったミュータントは、次のような指摘になる。

```text
backend/internal/reservation/internal/domain/reservation.go:168: [mutation/survived] every test passes with `<` changed to `<=` (CONDITIONALS_BOUNDARY, mutant backend/internal/reservation/internal/domain/reservation.go:checkTerms:CONDITIONALS_BOUNDARY#2). ...
frontend/src/lib/input.ts:32: [mutation/survived] every test passes with `number >= min` changed to `number > min` (EqualityOperator, mutant frontend/src/lib/input.ts:wholeNumber:EqualityOperator#1). ...
```

1行目は `attendees < 1` であり、予約の参加人数は少なくとも1人という規則にあたる。参加人数がちょうど1人の予約を試すテストがなかったので、規則が「少なくとも2人」になってもすべてのテストが通る。
2行目は、フォームに入力する整数の下限である。フォームが受け付ける最小の数である1を入力するテストがなかったので、フォームが1を拒んでもすべてのテストが通る。

Go のミュータントの名前は `<file>:<function>:<type>#<n>` であり、その関数の中でその種類の n 番目の箇所を指す。
フロントエンドのミュータントの名前は `<file>:<declaration>:<Mutator>#<n>` であり、その最上位の宣言（関数や、文言の表のような定数）の中で、そのミューテーションの種類の n 番目のミュータントを指す。StrykerJS は実行全体でミュータントに通し番号を振るので、この名前は `tools/stryker/mutants.jq` が付ける。
どちらの名前も、ファイルのほかの箇所を変えても変わらない。同じ関数や宣言を変えると、番号は振り直されることがある。
`[mutation/not-covered]` は、どのテストもまったく実行しない行を指す。

1つのミュータントだけを、その判定とともに実行するには次のようにする。

```sh
make mutant ID='backend/internal/reservation/internal/domain/reservation.go:checkTerms:CONDITIONALS_BOUNDARY#2'
make mutant-frontend ID='frontend/src/lib/input.ts:wholeNumber:EqualityOperator#1'
```

どちらも、テストがミュータントを殺せば `KILLED` を、生き残れば `LIVED`（gomutants）か `SURVIVED`（StrykerJS）を表示し、生き残ったときは失敗する。
StrykerJS は名前でミュータントを1つだけ実行できない。そのため `mutant-frontend` は、その宣言のミュータントをすべて実行し、目的の1つの結果を読む。かかる時間は数秒である。
ミュータントでテストが失敗するか通るかを手で確かめるには、指摘の行で指摘のとおりにコードを変え、テスト（パッケージへの `go test` か `make test-frontend`）を実行し、変更を戻す。

## 生き残ったミュータントへの対処

生き残ったミュータントは、次の2つのどちらかを問うている。

- このコードがすることを確かめるテストはあるか。たいていはなく、対処はその変更で失敗するテストである。そのパッケージやモジュールのテストの書き方に合わせ（多くはテーブル駆動テストの行を1つ足す）、テストが守る規則を名前にする。先の指摘なら、主催者1人だけの予約と、数に1を入力したフォームが対処になる。
- そのコードは必要か。後の検査が繰り返す条件や、起こりえない分岐からは、どのテストも殺せないミュータントが生まれる。コードを単純にし、それだけで1つのコミットにする。たとえば、あるユースケースは、すべてのエラーが `found` を真にして返ってくるのに `found || err != nil` を調べていた。今は1つのフラグだけを調べる。フロントエンドでは、フォームを読み取る関数が、項目の文言を書いた後で、型検査のためだけに時間帯と参加人数をもう一度調べていた。今は失敗する側の分岐で文言を書くので、どの条件も何かを決めている。

行を実行するだけのテストは、何も殺さない。変更で変わるはずの結果を検証する。
テストの欠落ではなくコードの誤りを生き残ったミュータントが示しているなら、コードを直してそのことをコミットに書く。

## 画面が表示する文言

フロントエンドでは、多くのミュータントが文字列を空にする。その文字列は、項目の文言や problem の種類ごとの文言のように、画面が表示する文である。すべての文を固定するテストでは、言い回しを変えるたびにテストも変えることになる。どの文も固定しないテストでは、文言が空になっても誰も気付かない。このリポジトリのテストは、そのどちらも採らない。

- 事実を含む文は、一字一句固定する。ここでいう事実は、数、規則、その文が指す項目の3種類である。数を含む文の例は「Enter a whole number from 1 to 1000.」である。規則を含む文の例は「A reservation can be cancelled until 30 minutes before it starts.」である。項目を指す文の例は「Enter the name of the room.」である。この文言を変えると画面の伝える内容も変わるので、テストも変えることになる。
- それ以外の文は、文言は文であるという規則で守る。文は大文字で始まり、ピリオドで終わる。この規則は、文言が何であっても、空になれば失敗する。

ミューテーションの対象から外す文字列はない。

## 許可がふさわしい場合

ミュータントには等価なものがある。変更がコードの動作を変えようがないため、どのテストもコードと区別できない。
まず、ミュータントが消えるまでコードを変えることを選ぶ。たとえば、会議室が開く時刻と閉まる時刻は、それぞれ別々に秒を指定して組み立てていた。時間帯は15分の区切りに乗るので、片方だけを1秒ずらしても何も変わらなかった。今は両方を1つの関数から得るので、変更は両方をずらし、境界のテストがそれに気付く。
フロントエンドでは、タイムゾーンごとのフォーマッターを保持するキャッシュが、時間でしか区別できない2つのミュータントを生んでいた。いつも見つからないキャッシュと、何も保持しないキャッシュである。フォーマッターを1つ作るのにかかる時間は約40マイクロ秒であり、1つのページが時計を読む回数は多くても数10回なので、キャッシュはなくした。

コードを変えられないときは、ルートの `equivalent-mutants.allow` でミュータントを生き残らせる。書き方はミュータント1つにつき1行である。

```text
# <mutant> | <original> -> <replacement> | <reason>
```

- ミュータントと変更は、指摘が示すとおりに書く。
- 行は、ミュータントが指すファイルの言語のチェックに属する。JavaScript か TypeScript のファイルなら `test-mutation-frontend` に、それ以外のファイルなら `test-mutation` に属する。Go のファイルも JavaScript や TypeScript のファイルも指さない行では、`test-mutation` が失敗する。
- 理由には、変更が等価であることの証明を書く。「テストしにくい」は証明ではない。テストで殺せるミュータントには、書くべきテストがある。
- 行を足すかどうかは、レビューで決めることである。エージェントは行を書かず、指摘と証明を添えて作業を止め、判断を求める。
- 生き残ったミュータントのどれにも一致しない行は、チェックを失敗させる（`mutation/unused-allowance`）。理由のない行も同じである（`mutation/allowance-format`）。テストがミュータントを殺したときや、コードが変わったときには、その行を消すことになるので、このファイルに古い行は溜まらない。
