# API を変更する

`contracts/http/` にある文脈の OpenAPI 文書は、その API を呼ぶクライアントとの契約である（TPL-0006）。
チェック `lint-contracts-breaking` は、各文書をベースブランチ上のバージョンと比べ、クライアントとの互換性を壊す変更で失敗する（TPL-0007 の層6）。
チェック `test-api-fuzz` は、各文書から生成したリクエストを API に送り、文書が許さない答えで失敗する（層5）。

## 意図して互換性を壊す

応答のプロパティの削除や、必須のリクエストのプロパティの追加など、oasdiff がエラーと判定する変更は、このチェックで失敗する。指摘には、oasdiff のルールと文書の行が付く。
変更が意図したものであれば、同じプルリクエストで文書の `info.version` を上げる。1.0 未満ではマイナーバージョンを上げ（`0.1.0` から `0.2.0`）、1.0 以降はメジャーバージョンを上げる（`1.4.0` から `2.0.0`）。
こうして上げると、oasdiff はその文書の互換性を壊す変更を受け入れる。上がったバージョンは、そのプルリクエストが意図して契約を壊すことをレビュアーに示す。
すべてのクライアントが追従できるかはレビュアーが判断する。このリポジトリの中にあるクライアント（フロントエンドや、ほかの文脈にある生成されたクライアント）は、同じプルリクエストで変更する。
比べる相手は、CI と同じく、`origin/main`（`CHECK_BASE` を設定したときはその値）とのマージベースである。新しい文書には比べる相手がないので、チェックは通る。

## クライアントを変更に追従させる

API の文書を変えたあと、`make gen` が契約の両側のコードを生成し直す。一方は、文脈の Go のサーバーとほかの文脈のクライアントである（oapi-codegen）。もう一方は、フロントエンドの TypeScript の型 `frontend/src/lib/api/<context>.gen.ts` である（openapi-typescript）。
するとフロントエンドの型チェックが、型に合わなくなった画面のコードを挙げる。`lint-frontend-types` は、パス・パラメーター・本文を文書がもう許さない呼び出しと、なくなった答えの部分を使う箇所のそれぞれで失敗する。
互換性を壊す変更は、それらの画面を同じプルリクエストで直す。画面が変わった API と合わせて動くかは、`make e2e` でわかる。

## 文書から生成したリクエストで API を確かめる

`make check-all` は `test-api-fuzz` を実行する（TPL-0007 の層5）。このチェックは、どのテストも送らないリクエストに API がどう答えるかを調べる。
Schemathesis が `contracts/http/` の各文書を読み、そこからリクエストを生成して、その文脈の API に送る。
チェックは API をチェックアウトからビルドし、手元の PostgreSQL にある専用のデータベースの上で動かす。そのため Docker は要るが `make up` は要らず、手元のシステムのデータにも手を付けない。

Schemathesis は、操作ごとに次のリクエストを送る。

- 文書にある例
- 文書の制約をそれぞれ両側から試すリクエスト。限度ちょうどの値と限度を越えた値、必須のプロパティやヘッダーを欠いたもの、別の型の値、そのパスにないメソッド、操作が受け取らないメディアタイプの本文である
- スキーマから生成した 100 個のリクエスト。正しいものも正しくないものも含む
- 操作のあいだのリンクをたどる、最大 10 個のリクエストの連なり。リンクには、文書が宣言するもの（予約の `ETag` を `If-Match` に入れて、その予約を変更する操作へ進むなど）と、Schemathesis が推定するもの（新しい会議室を読み出す操作へ進むなど）がある

Schemathesis が作り出すリクエストは、API が何を保持しているかを知りようがない。作り出した会議室を指定した予約は、予約の決まりのどれかが調べる前に、知られていない会議室として拒まれる。
そこでチェックは、Schemathesis を始める前に Facility の API を通して会議室を登録し、その id と UTC での明日と昨日の時刻を `.cache/api-fuzz/data/` のファイルに書き出す。
生成した予約と変更は、`tools/schemathesis/schemathesis.toml` の設定に従い、ほとんどの場合、会議室と時間帯をこれらのファイルから取る。
会議室と時刻は、予約が受け付けられるか、決まりを1つだけ破って拒まれるかのどちらかになるよう選んである。拒む決まりは、時間帯の5つ（15分刻みでない・長すぎる・終わりが始まりより前である・過去である・会議室の利用時間の外である）と、参加人数が定員を超えること、ほかの予約が会議室を押さえていることである。
一連のリクエストは、受け付けられた予約を読み出し、変更し、取り消す。
会議室と時刻の一覧と、それぞれを置いた理由は `tools/scripts/api-fuzz.sh` にある。

答えは、操作が宣言するステータス（そのパスにないメソッドには、ヘッダー `Allow` を付けた 405）を持ち、そのステータスについて文書が示すコンテントタイプ・ヘッダー・本文を持たなければならない。
さらに、文書が許さないリクエストには 4xx を返し、文書が許すリクエストを読めないものや正しくないものとして拒まず、どのリクエストにも 5xx を返さないことを求める。
チェックの設定は `tools/schemathesis/schemathesis.toml` にある。

次の答えはこのチェックでは引き出せず、その原因になるリクエストを送るのは API のテスト（層4）だけである。

- 開始の30分前を過ぎた取り消し。実行から30分以内に始まる予約が要る。そのためには時刻を実行した時刻から決めることになり、2つの実行で送るリクエストが異なってしまう
- Reservation の 503。応答しない Facility が要る

チェックだけを実行するには、次のようにする。

```sh
make test-api-fuzz
```

かかる時間は、空いているマシンで30秒ほど、マシンがほかの作業で忙しいときは2分以上になる。
コードと文書が同じなら、同じ日（UTC）のどの実行も同じリクエストを送る。そのため指摘は、原因を直すまで毎回現れる。
別の日に実行すると、リクエストの時間帯は日数の差だけずれる。API が作る id は実行ごとに異なる。

### 指摘の読み方

指摘は、文書の中の操作の行と、失敗した Schemathesis のチェックを挙げる。

```text
contracts/http/facility.openapi.yaml:82: [schemathesis/status_code_conformance] GET /rooms/{roomId}: Undocumented status code (ST103): Received: 410; Documented: 200, 400, 404, 422, 500. Answer: 410 room-not-found: no room has the id 4a6ffa02-1a33-56f0-a26b-39316053eee8. Request: GET /rooms/4a6ffa02-1a33-56f0-a26b-39316053eee8
```

`Answer` の後ろには、ステータスと、problem であればその種類と詳細が続く。`Request` の後ろには、ベース URL を除いた送信内容が続く。
`.cache/api-fuzz/<context>/output.txt` には、指摘ごとの curl コマンドを含む Schemathesis の報告がある。`.cache/api-fuzz/<context>/api.log` には API のログがあり、500 の原因になったエラーはここでわかる。

リクエストをもう一度送るには、`make up` で手元のシステムを起動し、指摘の curl コマンドを実行する。そのとき、ベース URL を API のもの（Facility は `http://127.0.0.1:18081`、Reservation は `http://127.0.0.1:18082`）に替える。
新しい会議室の id のように API が作る id は、実行ごとに異なる。
予約が指定する会議室はチェックが登録したもので、手元のシステムはそれを知らない。`tools/scripts/api-fuzz.sh` と同じ設定の会議室を手元のシステムに登録し、その id をリクエストに入れる。

### 指摘の直し方

どちらの側が誤っているかを決め、その側を直す。

- API が意図して返す答え（ステータスやヘッダー）を文書が挙げていなければ、文書が誤っている。その答えを文書に足す。その変更がクライアントとの互換性を壊すときは、[意図して互換性を壊す](#意図して互換性を壊す)に従う。
- API がどうしても受け取れない値を文書が許すときも、文書が誤っている。PostgreSQL に保存するテキストの中の文字 U+0000 がその例で、500 で失敗する。スキーマを API が受け取る範囲に狭める。リクエストのスキーマを狭めると契約が壊れるので、[意図して互換性を壊す](#意図して互換性を壊す)に従う。
- 文書が許すリクエストを API が拒むとき、文書にない答えを返すとき、500 で失敗するときは、コードが誤っている。コードを直し、そのリクエストを送る API のテスト（層4）を足して、`make check` でも捕まるようにする。
- JSON Schema では書けない決まり（時間帯は始まりより後に終わる、など）は、文書の許すリクエストを、操作の宣言する 4xx で拒むことがある。このときはどちらの側も誤っていない。`tools/schemathesis/schemathesis.toml` で、その操作の `positive_data_acceptance` にそのステータスを足し、決まりを理由として書き添える。

チェックをすべての操作について止めることはしない。道具が誤って出す指摘は、その操作についてだけ設定を変え、理由を隣に書く。
