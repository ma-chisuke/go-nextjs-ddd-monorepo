# TPL-0017: 手元の環境では AWS Emulator で AWS を代用する

## 背景と課題

テンプレートは、AWS のアカウントなしに、1台のマシンの上で Docker Compose だけで動く必要がある。
コピーしたばかりの人も、サンドボックスの中のコーディングエージェントも、CI も、システム全体を同じ方法で動かす。

システムの大半は、手元で動かすのが簡単である。PostgreSQL 18、各文脈、Next.js、それに通知（Notification）が送るメールを受け止める Mailpit がそうである。
難しいのは AWS である。
イベントは EventBridge と SQS を通り（TPL-0013）、秘密情報は Secrets Manager から取り出す。
コードが AWS を使うのはアダプターを通してだけである（TPL-0004）。それでも、そのアダプターと、EventBridge のルールからキューへの振り分けを試すには、相手になる何かが要る。

これまでの定番は LocalStack だった。
しかし LocalStack は2026年3月から認証トークンを必須にしており、トークンにはアカウントが要る。アカウントなしで動く必要のあるテンプレートは、LocalStack に頼れない。
2026年11月11日、AWS は AWS のサービスの公式のエミュレーターとして、AWS Emulator を公開した。

テンプレートが使う AWS のサービスを、手元の環境でどう用意すればよいか。

## 判断の基準

- 手元の環境は、アカウントもトークンもなしに、Docker Compose だけで動く。
- テンプレートが頼る動きを再現できる。EventBridge のルールから SQS への配信、デッドレターキュー、Secrets Manager である。
- できれば、手元と AWS のキューとルールを同じ Terraform の定義から作り、両者がずれないようにする。
- テンプレートをコピーするチームに、ライセンスの負担をかけない。

## 検討した選択肢

- AWS Emulator
- LocalStack
- 開発者ごとに本物の AWS のアカウントを使う
- サービスごとに別々の偽物を使う
- 手元では AWS を使わず、テストでポートを偽物に差し替える

## 決定

採用：「AWS Emulator」。テンプレートが使う AWS のサービスを、アカウントなしで手元に用意できる選択肢は、これだけだからである。

決まりは次のとおりである。

- Docker Compose で、システム全体を動かす。中身は PostgreSQL 18、AWS Emulator、各文脈、Next.js、メール用の Mailpit である。
- AWS は AWS Emulator を RPM と deb のパッケージとして公開しており、コンテナイメージは公開していない。テンプレートは、自分の Dockerfile `infra/local/aws-emulator/Dockerfile` でイメージをビルドする。ダイジェストで固定した Amazon Linux 2023 minimal の上に、固定したバージョンの RPM パッケージを入れる。入れる前に、アーキテクチャごとにパッケージの SHA-256 を確かめ、さらに `rpm` が、リポジトリに置いた AWS の公開鍵 `signing-key.asc` でパッケージの署名を確かめる（TPL-0024）。
- AWS Emulator は、既定でテレメトリーを送る。イメージは `EMULATOR_TELEMETRY=off` を設定する。
- AWS Emulator はデータをメモリにしか持たない。そのため、手元の環境は、エミュレーターが起動するたびにイベントバス・キュー・ルールを作る。
- 手元の環境は、AWS の環境が使う Terraform のモジュール `infra/modules/event-bus` と `infra/modules/event-subscription` を、エミュレーターに適用する。そのため、手元のバス・キュー・ルールは AWS と同じコードから作られる（TPL-0015）。これらを適用するルート `infra/local/` は、このマシンの上のエンドポイントしか受け付けない。適用するのは `tools/scripts/aws.sh apply`（`make aws-apply`）で、`make up`・`make smoke`・`make e2e` がこれを実行する。このスクリプトは Terraform の state をリポジトリの外に置き、エミュレーターが再起動していれば捨てる。
- エミュレーターは、ポート 9297 で HTTPS を提供する。証明書は起動のたびに作り、名前は `localhost` と `127.0.0.1` だけである。その証明書には、エミュレーターが状態のディレクトリに書く CA が署名する。ホストは、`tools/scripts/aws.sh server` でその CA を受け取る（`.cache/aws-emulator/ca.pem`）。サービスのコンテナは、CA の入ったボリュームをマウントする。そして `AWS_ENDPOINT_SERVER_NAME=localhost` で、証明書に書かれた名前を知る。サービスはその名前を確かめ、確認を省かない（`platform/awsconfig`。`AWS_ENDPOINT_URL` なしにこの変数を設定すると拒む）。エミュレーターは、CA のファイルを所有者だけが読める形で書く。そのため、エミュレーターはサービスと同じユーザー 65532 で動く。
- エミュレーターはリクエストの署名を確かめない（`--auth off`）。起動のたびに新しい認証情報を作るからである。ポートは、ループバックアドレスにだけ公開する。
- Docker Compose のどのサービスも、ポートをループバックアドレスにだけ、32768 より小さい番号で公開する。PostgreSQL は 15432、AWS Emulator は 19297、Mailpit は 18025、Facility は 18081、Reservation は 18082、フロントエンドは 13000 である。32768 以上のポートは、Linux と macOS が自分で割り当てる。外へ向かう接続にも割り当てる。手元の PostgreSQL への接続を保っているテストが、サービスがこれから公開するポートを先に使い、サービスが起動に失敗したことがある。ポートが 55432 から 59297 の間にあった頃、これで CI が1日に2回、別々のポートで失敗した。
- `make up` がエミュレーターを新しく起動したときは、その CA のボリュームをマウントするサービスを再起動し、新しい CA を読ませる。ほかの方法でエミュレーターが再起動したときは、人が再起動する（[サービスを手元で動かす](../../guides/run-locally.ja.md)）。
- テンプレートが頼る動きには、それぞれ CI で動くテストがある。エミュレーターのあるバージョンがその動きをしなくなれば、テストが失敗する（確認の方法を参照）。
- 手元のシステムには、Secrets Manager や SES を呼ぶものがない。サービスは秘密情報を環境変数から読み、AWS では ECS がその環境変数を埋める（TPL-0014）。Notification はメールを Mailpit に送る。そのため、手元の環境は秘密情報を作らない。AWS でメールを送るアダプター `notification/internal/adapter/ses` には、エミュレーターの SES に対する結合テストがある。このテストは、送信元にする ID を自分で作る。
- エミュレーターは、環境のリハーサル（`make rehearse-infra`、TPL-0015）でも AWS アカウントの代わりになる。リハーサルは、stg のユニットをデプロイと同じ順序でエミュレーターに適用し、prd のユニットをそれに対して plan する。手元のシステムはエミュレーターのリージョン `us-east-1` に置き、リハーサルは環境のリージョンである `ap-northeast-1` に置く。エミュレーターの SQS と EventBridge はリージョンごとに分かれているので、リハーサルは手元のシステムのキューとバスに手を付けない。
- リハーサルで出会うエミュレーターの制限は、`infra/live/_units/` と `tools/scripts/infra.sh` で、それぞれにコメントを付けて扱う。モジュールの中では扱わない。制限の一覧は「補足」にある。

この決定のうち3つの点は、最初の計画と違う。

- 最初の計画では、AWS が公開する Dockerfile からイメージをビルドするつもりだった。テンプレートは自分の Dockerfile を書く。ベースイメージをダイジェストで固定し、パッケージを入れる前に確かめるためである（TPL-0024）。
- 最初の計画には、エミュレーターが EventBridge から SQS へ配信できない場合の代わりの案があった。エミュレーターは配信できたので、この案は作っていない（TPL-0013）。
- 最初の計画では、試す動きに Secrets Manager を挙げていた。Secrets Manager はエミュレーターで動くが、手元のシステムには使うものがないので、手元のシステムのためのテストは置かない。リハーサルは、モジュール `database` のシークレットを、書き込み専用の引数でエミュレーターに作る。

### 結果

- 良い点：誰でも、アカウントもトークンもなしに、イベントの流れを含めてシステム全体を動かせる。CI でも同じように動かせる。
- 良い点：AWS Emulator は AWS 自身が出しており、ライセンスは CC0 である。テンプレートをコピーするチームに、ライセンスの条件が課されない。
- 良い点：手元のバス・キュー・ルールは、AWS の環境が使うモジュールから作られる。
- 良い点：エミュレーターはモジュールのリソースをすべて受け付けるので、アカウントなしで環境全体を適用できる。stg の9つのユニットで約3分かかる。
- 悪い点：公開は2026年11月11日であり、短い間に大きく変わる可能性がある。テストが確かめるのはテンプレートが頼る動きだけであり、AWS との違いもすでに1つ見つかっている。存在しないバスへのイベントを、エミュレーターは受け付けて捨てる。そのため中継は、起動のときに自分のバスがあることを確かめる（`Publisher.Ready`、TPL-0013）。
- 悪い点：再起動すると状態が消えるので、手元の環境は毎回 AWS のリソースを作り直す必要がある。起動後の最初の適用には1分ほどかかる。AWS の provider は SQS のキューを1つ作るたびに25秒ほど待ち、購読1つにつきキューは2つあるからである。モジュール `event-subscription` は、キューのポリシーをキューの引数として設定する。ポリシーを別のリソースにすると、もう1回待つからである。
- 悪い点：CA はエミュレーターが起動するたびに変わる。エミュレーターが再起動したら、それを呼ぶサービスも再起動し、ホストも CA をもう一度コピーする必要がある。エミュレーターを新しく起動した `make up` は、この2つを行う。`make up` によらない再起動のあとは、人が行う。
- 悪い点：イメージを Dockerfile から手元でビルドするので、どのマシンでも最初の起動に手順とビルドの時間が加わる。
- 悪い点：エミュレーターのバージョンを更新する Renovate のルールは、まだない。更新するには、Dockerfile のバージョンと2つのチェックサムを手で変える（TPL-0025）。
- 悪い点：エミュレーターは AWS そのものではない。権限・クォータ・遅延が違いうるので、本物のサービスで初めて動かす場所は、引き続き stg である。
- 悪い点：エミュレーターは、Terraform が作ったものを覚えるだけで、何も起動しない。タスクもデータベースも動かない。そのためリハーサルが示すのは環境の形だけである。イメージが起動すること、データベースを準備するタスクが成功すること、サービスが名前で互いを見つけることは示さない。

### 確認の方法

Docker Compose は、PostgreSQL 18、AWS Emulator、Mailpit、各文脈のプロセス、Next.js を動かす。プロセスは、Facility と Reservation の API、Reservation の中継、Notification のワーカーである。Next.js は `frontend/Dockerfile` からビルドするサービス `web` で、<http://127.0.0.1:13000> にある。`make up` がこれらを起動する。
システムのプロセスは、すべて Compose の中で動く。ホストから適用するのは、スキーマと AWS のリソースだけである。適用するのは `tools/scripts/db.sh` と `tools/scripts/aws.sh` で、使う pgschema と Terraform は `mise.toml` が固定したものである。こうして、それぞれの固定を1か所に保つ（TPL-0010、TPL-0022）。

次のテストが、エミュレーターの動きを確かめ続ける。どれも `make check-all` で動くので、CI でも動く。

- `platform/awsevents` の結合テスト（`awsevents_integration_test.go`。`make test-integration` で動く）は、発行側と受け取る側をエミュレーターに対して動かす。カスタムのバスのルールは、`events.amazonaws.com` を許すポリシーを持つ SQS のキューへ、イベントの `detail` を届ける。ハンドラーが失敗し続けるイベントと、イベントではないメッセージは、`maxReceiveCount` 回受け取られたあとでデッドレターキューに移る。AWS が予約した `source` のエントリーには、`PutEvents` がステータス 200 と失敗したエントリーで答え、発行側はそれをエラーとして報告する。`Publisher.Ready` は、バスがあるかどうかを答える。
- `make smoke` は、Terraform で `infra/local/` を適用してシステムを起動する。そして予約を作って変更し、取り消したうえで、3通のメールを Mailpit で待つ。
- `make e2e` も同じやり方でシステムを起動する。そしてブラウザーの中の人が会議室を登録し、予約し、変更して取り消す。テストは、3通のメールを Mailpit で待つ。
- `notification/internal/adapter/ses` の結合テスト（`make test-integration`）は、エミュレーターに SES の ID を作って検証させる。そして、その ID から SES v2 の `SendEmail` でメールを送る。また、検証済みの ID のどれにも当たらない差出人を、エミュレーターが `MessageRejected` で拒むことも確かめる。
- `make rehearse-infra` は、stg のユニットをエミュレーターに適用し、prd のユニットをそれに対して plan する。エミュレーターのあるバージョンがモジュールのリソースを受け付けなくなれば、ここで失敗する。

## 選択肢の長所と短所

### AWS Emulator

- 良い点：AWS 自身が出しており、ライセンスは CC0 で、アカウントが要らない。
- 悪い点：新しく、対応範囲がわからない。データはメモリにしか持たず、イメージは手元でビルドし、テレメトリーは既定で有効である。

### LocalStack

- 良い点：成熟しており、広く使われ、多くのサービスに対応している。Terraform 向けの道具もある。
- 悪い点：2026年3月から認証トークンが必須であり、トークンにはアカウントが要る。テンプレートは、アカウントなしで動く必要がある。

### 開発者ごとに本物の AWS のアカウントを使う

- 良い点：本物のサービスなので、動きの違いがない。
- 悪い点：人・エージェント・CI の実行のどれにも、アカウント・認証情報・予算が要り、使ったあとの片付けも要る。テンプレートはアカウントなしで動くという決まりにも反する。
- 悪い点：ネットワークへの接続が要り、実行のたびにリソースを作るので遅い。

### サービスごとに別々の偽物を使う

- 良い点：小さく成熟した偽物もある。たとえば ElasticMQ は、SQS の API を実装している。
- 悪い点：サービスごとに偽物が要る。しかも、テンプレートがいちばん試したいのは、サービスをまたぐ EventBridge のルールから SQS のキューへの振り分けである。

### 手元では AWS を使わず、テストでポートを偽物に差し替える

- 良い点：動かすものがない。テストでは、ポートを Go で書いた偽物に差し替える（TPL-0004）。
- 悪い点：アダプターと、EventBridge と SQS の間の振り分けが、stg まで一度も動かない。そのため、そこにある不具合の発見が遅れる。

## 補足

2026年11月時点で、AWS Emulator について[発表](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-emulator-now-available/)からわかることは次のとおりである。

- AWS が2026年11月11日に公開した。
- ライセンスは CC0 で、アカウントが要らず、データはメモリにしか持たない。
- AWS は Linux 向けのパッケージと Dockerfile を公開しているが、コンテナイメージは公開していない。
- 既定でテレメトリーを送る。`EMULATOR_TELEMETRY=off` で止められる。
- 対応するサービスの一覧は公開されていなかった。

バージョン 1.0.498 で、2026年11月18日に確かめたことは次のとおりである。

- パッケージは `downloads.aws.com` にある RPM と deb のファイルで、AWS の鍵で署名されている。バージョンの一覧の場所は、Dockerfile の先頭のコメントにある。コンテナイメージはない。
- エンドポイントは、ポート 9297 の HTTPS である。証明書は `localhost` と `127.0.0.1` に向けてエミュレーターが起動のたびに作り、エミュレーターが状態のディレクトリに書く CA が署名する。
- エミュレーターは、起動のたびに新しい認証情報を作る。`--auth off` で署名の確認を止められる。
- カスタムのバスのルールが SQS のキューへ配信するのは、キューのポリシーが `events.amazonaws.com` を許すときだけである。これは AWS と同じである。入力パス `$.detail` は働き、SQS は `maxReceiveCount` 回受け取られたメッセージをデッドレターキューに移す。
- AWS が予約した `source`（`aws.` で始まるもの）のエントリーには、`PutEvents` がステータス 200 と失敗したエントリーで答える。
- 存在しないバスへのイベントは、受け付けられて捨てられる。AWS はこれを拒む。
- Terraform は、AWS の provider 6.73.0 で `infra/local/` をエミュレーターに適用できる。provider は、SQS のキューを1つ作るたびに25秒ほど待つ。
- Secrets Manager（シークレットの作成と読み出し）と SES v2 の `SendEmail` は、手での確認で動いた。

インフラのマイルストーンの間に、2026年11月、バージョン 1.0.498 で確かめたことは次のとおりである。

- モジュールのリソースをすべて受け付ける。
  - ネットワーク：VPC とそのサブネット・経路・フローログ、ゲートウェイエンドポイントとインターフェイスエンドポイント、セキュリティグループのルール。
  - IAM、Amazon ECR、書き込み専用の引数を使う Secrets Manager、CloudWatch Logs、Terraform のバックエンドとしての S3。
  - ECS のクラスター・タスク定義・Service Connect 付きのサービス、Service Connect の HTTP 名前空間。
  - ロードバランサーとそのリスナー、Route 53、ACM への証明書のリクエスト、RDS のクラスター。
- Aurora PostgreSQL はバージョン 17.9 までしか知らず、18 は知らない。リハーサルは、データベースを 17.9 で適用する。
- エンドポイントのサービス `email`（Amazon SES の API）を知らない。リハーサルは、このエンドポイントを除く。
- ACM は証明書を発行しない。エミュレーターのロードバランサーは、発行されていない証明書も受け付ける。リハーサルは、証明書のリクエストとドメインのホストゾーンの作成を自分で行う。
- ECR のリポジトリに `localhost:<port>/<name>` という名前を付ける。モジュール `database` は、この形のイメージのアドレスを拒む。リハーサルは、AWS と同じ形でアドレスを書く。
- RDS のクラスターに独自のポートを返すので、2回目の plan にはポートの変更が出る。
- リハーサルが設定する `skip_requesting_account_id` のもとでは、provider は参照先のセキュリティグループを `<account>/<group>` の形で読み戻す。そのため、2回目の plan に変更が出る。
- タスクを起動せず、データベースも動かさない。
- ECS の `CreateGateway` に "scaffolded but not implemented" と答える（TPL-0014）。
- SES v2 の `SendEmail` は、検証済みの ID が対象とするアドレスからは送り、それ以外の差出人は `MessageRejected` で拒む。
