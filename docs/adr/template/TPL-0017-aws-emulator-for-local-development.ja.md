# TPL-0017: 手元の環境では AWS Emulator で AWS を代用する

## 背景と課題

テンプレートは、AWS のアカウントなしに、1台のマシンの上で Docker Compose だけで動く必要がある。
コピーしたばかりの人も、サンドボックスの中のコーディングエージェントも、CI も、システム全体を同じ方法で動かす。

システムの大半は、手元で動かすのが簡単である。PostgreSQL 18、各文脈、Next.js、それに通知（Notification）が送るメールを受け止める Mailpit がそうである。
難しいのは AWS である。
イベントは EventBridge と SQS を通り（TPL-0013）、秘密情報は Secrets Manager から取り出す。
コードが AWS を使うのはアダプターを通してだけである（TPL-0004）。それでも、そのアダプターと、EventBridge のルールからキューへの振り分けを試すには、相手になる何かが要る。

これまでの定番は LocalStack だった。
しかし LocalStack は2026年3月から認証トークンを必須にしており、トークンにはアカウントが要る。アカウントなしで動く必要のあるテンプレートは、LocalStack に頼れない。
2026年11月11日、AWS は AWS のサービスの公式のエミュレーターとして、AWS Emulator を公開した。

テンプレートが使う AWS のサービスを、手元の環境でどう用意すればよいか。

## 判断の基準

- 手元の環境は、アカウントもトークンもなしに、Docker Compose だけで動く。
- テンプレートが頼る動きを再現できる。EventBridge のルールから SQS への配信、デッドレターキュー、Secrets Manager である。
- できれば、手元と AWS のキューとルールを同じ Terraform の定義から作り、両者がずれないようにする。
- テンプレートをコピーするチームに、ライセンスの負担をかけない。

## 検討した選択肢

- AWS Emulator
- LocalStack
- 開発者ごとに本物の AWS のアカウントを使う
- サービスごとに別々の偽物を使う
- 手元では AWS を使わず、テストでポートを偽物に差し替える

## 決定

採用：「AWS Emulator」。テンプレートが使う AWS のサービスを、アカウントなしで手元に用意できる選択肢は、これだけだからである。

決まりは次のとおりである。

- Docker Compose で、システム全体を動かす。中身は PostgreSQL 18、AWS Emulator、各文脈、Next.js、メール用の Mailpit である。
- AWS は AWS Emulator を Linux 向けのパッケージと Dockerfile として公開しており、コンテナイメージは公開していない。そのため、テンプレートは公開されている Dockerfile から、固定したバージョンでイメージをビルドする。
- AWS Emulator は、既定でテレメトリーを送る。テンプレートは `EMULATOR_TELEMETRY=off` を設定する。
- AWS Emulator はデータをメモリにしか持たない。そのため、手元の環境は起動するたびにキュー・ルール・秘密情報を作る。
- この決定の時点では、対応するサービスの一覧が公開されていなかった。テンプレートが頼る動き（EventBridge から SQS への配信、デッドレターキュー、Secrets Manager）には、それぞれ小さなテストを用意し、CI で実行する。
- それらのテストが失敗した場合は、送信箱の中継が購読の表を読み、EventBridge を使わずに自分で SQS のキューへイベントを送る形に切り替える（TPL-0013）。
- AWS Emulator に Terraform を適用できるなら、手元の環境でも同じ Terraform の定義を適用する。そうすれば、キューとルールは AWS と同じコードから作られる（TPL-0015）。

### 結果

- 良い点：誰でも、アカウントもトークンもなしに、イベントの流れを含めてシステム全体を動かせる。CI でも同じように動かせる。
- 良い点：AWS Emulator は AWS 自身が出しており、ライセンスは CC0 である。テンプレートをコピーするチームに、ライセンスの条件が課されない。
- 良い点：Terraform を適用できれば、手元のキューとルールは AWS で使う定義から作られる。
- 悪い点：公開は2026年11月11日であり、実績がない。テンプレートに必要なサービスと動きにどこまで対応しているかは、テストを動かすまでわからない。短い間に大きく変わる可能性もある。
- 悪い点：再起動すると状態が消えるので、手元の環境は毎回 AWS のリソースを作り直す必要がある。
- 悪い点：イメージを Dockerfile から手元でビルドするので、どのマシンでも最初の起動に手順とビルドの時間が加わる。
- 悪い点：エミュレーターは AWS そのものではない。権限・クォータ・遅延が違いうるので、本物のサービスで初めて動かす場所は、引き続き stg である。

### 確認の方法

M0 にはまだ手元の環境がないので、この決定を守らせるものはまだない。
イベントを扱うマイルストーンで、AWS Emulator のテスト（EventBridge から SQS への配信、デッドレターキュー、Secrets Manager）が CI で動き始める。テンプレートが頼る動きにエミュレーターのあるバージョンが対応していなければ、このテストが失敗する。
それまでは、レビューでこの決定を守る。

## 選択肢の長所と短所

### AWS Emulator

- 良い点：AWS 自身が出しており、ライセンスは CC0 で、アカウントが要らない。
- 悪い点：新しく、対応範囲がわからない。データはメモリにしか持たず、イメージは手元でビルドし、テレメトリーは既定で有効である。

### LocalStack

- 良い点：成熟しており、広く使われ、多くのサービスに対応している。Terraform 向けの道具もある。
- 悪い点：2026年3月から認証トークンが必須であり、トークンにはアカウントが要る。テンプレートは、アカウントなしで動く必要がある。

### 開発者ごとに本物の AWS のアカウントを使う

- 良い点：本物のサービスなので、動きの違いがない。
- 悪い点：人・エージェント・CI の実行のどれにも、アカウント・認証情報・予算が要り、使ったあとの片付けも要る。テンプレートはアカウントなしで動くという決まりにも反する。
- 悪い点：ネットワークへの接続が要り、実行のたびにリソースを作るので遅い。

### サービスごとに別々の偽物を使う

- 良い点：小さく成熟した偽物もある。たとえば ElasticMQ は、SQS の API を実装している。
- 悪い点：サービスごとに偽物が要る。しかも、テンプレートがいちばん試したいのは、サービスをまたぐ EventBridge のルールから SQS のキューへの振り分けである。

### 手元では AWS を使わず、テストでポートを偽物に差し替える

- 良い点：動かすものがない。テストでは、ポートを Go で書いた偽物に差し替える（TPL-0004）。
- 悪い点：アダプターと、EventBridge と SQS の間の振り分けが、stg まで一度も動かない。そのため、そこにある不具合の発見が遅れる。

## 補足

2026年11月時点で、AWS Emulator について[発表](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-emulator-now-available/)からわかることは次のとおりである。

- AWS が2026年11月11日に公開した。
- ライセンスは CC0 で、アカウントが要らず、データはメモリにしか持たない。
- AWS は Linux 向けのパッケージと Dockerfile を公開しているが、コンテナイメージは公開していない。
- 既定でテレメトリーを送る。`EMULATOR_TELEMETRY=off` で止められる。
- 対応するサービスの一覧は公開されていなかった。

まだ確かめていないこと：EventBridge から SQS への配信、デッドレターキュー、Secrets Manager、AWS Emulator への Terraform の適用。これらは、イベントを扱うマイルストーンで確かめる。
