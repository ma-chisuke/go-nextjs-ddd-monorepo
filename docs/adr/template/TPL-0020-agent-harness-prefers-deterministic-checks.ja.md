# TPL-0020: コーディングエージェントのハーネスでは決定的なチェックを優先し、指示は最小限から始める

## 背景と課題

このテンプレートでも、チームがテンプレートから作る製品でも、コードと文書の多くはコーディングエージェントが書く。
文章でしか書かれていない決まりは、エージェントが破りうる。決まりを読まないこともあれば、長い作業の途中で見失うことも、読み違えることもある。
そのとき、決まりが破られたことは、エージェントにも、ほかの誰にも伝わらない。

よくある対策は、リポジトリを説明する指示のファイルである。そこには、アーキテクチャ・慣習・すべての決まりを書く。
エージェントはこのファイルを作業のたびに読むので、毎回トークンを消費する。コードが変わるにつれてファイルの中身は古くなり、エージェントがそこに書かれた決まりを破っても何の知らせもない。
ETH Zurich による2026年の「Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?」という研究がある。この研究は、リポジトリの概要を書いたファイルがエージェントの作業の成功率を上げず、費用を2割以上増やしたと報告している。

エージェントにこのテンプレートの決まりを守らせるにはどうすればよいか。また、すべてのエージェントが読む指示には何を書くべきか。

## 判断の基準

- 大事な決まりは、エージェントがそれを読まなかったときも、理解しなかったときも守られる。
- エージェントは、チェックの出力から自分の誤りを人の手を借りずに直せる。
- どのエージェントも作業のたびに指示を読むので、指示の1行1行が費用に見合う。
- どのエージェント製品にも、人と同じ決まりが効く。
- 指示を変えるときは、推測ではなく、失敗の証拠に基づく。

## 検討した選択肢

- 決定的なチェックを優先し、指示は最小限にして、評価で確かめた失敗からだけ増やす
- アーキテクチャとすべての決まりを説明する長い指示のファイル
- ハーネスを作らず、エージェントはコードと README だけを頼りに作業する
- エージェント製品ごとに別々の決まりのファイルを置く

## 決定

採用：「決定的なチェックを優先し、指示は最小限にして、評価で確かめた失敗からだけ増やす」。チェックはエージェントが何を読んだかに関係なく決まりを守らせ、短い指示のファイルは費用が小さく、古くなりにくいからである。

決まりは次のとおりである。

- 大事な決まりは、チェックで守らせる。チェックの指摘は1件1行で、ファイルと行・ルール・直し方・理由を書いた記録を示す。エージェントは、その1行から自分で誤りを直せる。
- `AGENTS.md` に書くのは、コマンド・ファイルの置き場所・「終える前に `make check` を実行する」という指示・よくある既定から外れる決まりだけである。理由は記録に、手順はスキルとガイドに書く。
- `CLAUDE.md` は `AGENTS.md` を読み込むだけにする。こうして、どのエージェントも同じファイルを読む。`backend/` と `frontend/` には、それぞれの部分への指示を書いた専用の `AGENTS.md` があり、それを読み込む `CLAUDE.md` が隣にある。
- どの道具にも `AGENTS.md` を書かせない。Next.js 16 は、`next dev` がコーディングエージェントを見つけると、アプリの `AGENTS.md` に自分のブロックを足す。そのブロックはこのリポジトリの文章のチェックに通らず、消してもまた書き戻される。`frontend/next.config.ts` はこれを止め（`agentRules: false`）、`frontend/AGENTS.md` がそのブロックと同じことを書く。Next.js 16 はエージェントの知る Next.js と違うので、エージェントはコードを書く前に、インストールされたバージョンに付属する `frontend/node_modules/next/dist/docs/` の下の文書を読む。
- `AGENTS.md` に指示を足すのは、どのチェックでも捕まえられない失敗を `evals/` の評価が示したときだけである。指示を足すプルリクエストには、その失敗を示した実行の記録を書く。

ハーネスは次の部品からなる。

- Claude Code のフック。エージェントがファイルを編集すると、そのファイルを整形する。生成コードの編集・`.env` の読み取り・prd への変更の適用・force push を止める。ターンの終わりには、変更の及ぶ範囲のチェックを実行し、失敗をエージェントに差し戻す。差し戻す回数には上限がある。
- 繰り返す手順のためのスキル（`.claude/skills/`）。`write-adr` は記録を書き、`sync-translation` は対訳を最新にする。`add-endpoint` や `add-screen` のようなコードのスキルは、それぞれ `docs/guides/` のガイドに従い、それが変えるコードと一緒に加わる。
- 書いた本人とは別の目で見るサブエージェント（`.claude/agents/`）。`design-reviewer` は変更を記録に照らしてレビューし、`translation-reviewer` は対訳を原文と比べる。
- 権限の設定。安全なコマンドは確認なしで実行させ、危険なコマンドは拒む。
- lefthook。人にも、コミットの前とプッシュの前に同じチェックをかける（`lefthook.yml`）。

`evals/` の評価は、ハーネスを測るものであり、次のように動く。

- 1回の実行では、コーディングエージェントにこのリポジトリの作業を1つ、2つの条件のどちらかで与える。`harness` はいまのリポジトリであり、`bare` は `AGENTS.md`・`CLAUDE.md`・`.claude/` を除いたリポジトリである。ほかは、チェックも含めて、どちらの条件でも同じである。
- 実行はどれも、チェックアウトの外にあるコピーで行う。コピーは独立した Git リポジトリで、`evals/` を含まない。そのため、エージェントはこのリポジトリを何も変えられず、作業の解答も見つけられない。
- 採点は、作業の基準と、どの変更も満たすべき2つの基準で、各実行の結果を決める。2つの基準とは、`make check` が通ることと、変更がどのチェックも弱めないことである。
- `make check-all` に含まれる `make test-evals` は、採点が結果を見分けられることを、エージェントなしで確かめる。`make eval` はエージェントを起動する。1回の実行に利用枠と時間がかかるので、これは人だけが実行する。

最初の実行は、2026年11月20日に行った。2つの作業をそれぞれの条件で1回ずつ、モデル `sonnet` で実行し、4回のうち3回がすべての基準に合格した。
ハーネスがない条件では、エージェントは作業 `booking-horizon` の変更を一通り書いたが、`make check` を一度も実行しなかった。あとで実行した `make check` は、5件の指摘を出した。2つのファイルで古くなっていた生成コード、整形されていない Go のファイル1つ、対訳の2つの文である。ハーネスがある条件では、エージェントは止まる前に `make gen` と `make check` を実行した。
作業 `read-the-logs` では、どちらの条件でも対訳が更新された。ハーネスがない条件では、エージェントは対訳のマーカーを手で計算した。
ハーネスがある条件で不合格になった基準はないので、指示は足していない。4回の実行は何も証明しない。これは最初の観察にすぎず、これらの実行で示せないことは[評価の記録](../../../evals/results/README.ja.md)に書いてある。

### 結果

- 良い点：エージェントが決まりを読んだかどうかに関係なく、決まりは守られる。エージェントは、決まりを破ったその時点で決まりを知る。
- 良い点：人・エージェント・CI が1つの `make check` を共有するので、エージェント製品ごとの決まりは要らない。
- 良い点：`AGENTS.md` が短いままなので、作業ごとの費用が小さく、古くなる部分も少ない。
- 良い点：新しい指示は、推測ではなく実行の結果に基づく。評価は、同じ作業を、同じチェックのもとで、ハーネスのあるエージェントとないエージェントに与える。
- 悪い点：名前の付け方、ドメインモデルの形、テストが確かめるべきことを確かめているかなど、チェックできない決まりもある。それらはレビューと、レビューを担うサブエージェントに頼る。
- 悪い点：記録を示す指摘は少ない。示すのは、このリポジトリが自分で書いたチェックの指摘と、Trivy のライセンスの指摘だけである。ほかの指摘は、このリポジトリが1行の形に整えるもの（gitleaks・Trivy・ESLint・tflint など）も含め、ルールと、直し方かリンクを示すだけである。エージェントは、ルールの名前から理由を探す必要がある。
- 悪い点：評価はまだ小さい。2つの作業が扱う変更は2種類だけであり、4回の実行は最初の観察にすぎない。そのため、短い `AGENTS.md` で足りるかどうかは、まだ測れていない。選択は、いまも先の研究と判断に頼っている。
- 悪い点：フックが動くのは Claude Code の中だけである。ほかのエージェントがチェックを受けるのは、`make check`・lefthook・CI を通してだけである。
- 悪い点：評価が動かすのは Claude Code だけである。
- 悪い点：1回の実行は、起動した人のアカウントの利用枠を使い、数分から30分かかる。そのため、どのチェックも評価を起動せず、誰にも実行を強いない。

### 確認の方法

- `make check` が関門である。人・エージェント・CI がこれを実行し、フックもターンの終わりにこれを実行する。
- `make check` はターゲット `lint-agents-md` を実行し、`AGENTS.md` を短く保つ。
- フックと権限の設定は `.claude/settings.json` にあり、フックの本体は `.claude/hooks/` にある。`make check` は、各フックに見本のイベントを与え、何を止めて何を通すかを確かめる（`test-hooks`）。
- `make check-all` は `test-evals` を実行する。`test-evals` は、評価の採点をエージェントなしで確かめる。作業ごとに、いまのリポジトリが不合格になることと、作業の解答が `make check` を含むすべての基準に合格することを見る。
- `make eval` を実行するチェックはない。そのため、新しい指示を `AGENTS.md` へ足すときは、その失敗を示した実行の記録が添えてあることと、どのチェックでもその指示を置き換えられないことをレビューで確かめる。

## 選択肢の長所と短所

### 決定的なチェックを優先し、指示は最小限にする

- 良い点：チェックは、どのエージェントにも、どのモデルにも、どの人にも同じように働く。
- 良い点：失敗したチェックの出力が直すべき点を示すので、エージェントは人の手を借りずに問題を直せる。
- 悪い点：チェックを書いて出力を役に立つ形に保つのは、文を1つ書くより手間がかかる。
- 悪い点：長いファイルなら得られたはずの文脈をエージェントが知らず、それを知るために、失敗するチェックに1ターンを使うことがある。

### 長い指示のファイル

- 良い点：すべてが1か所にあり、新しいエージェントも人も、一度読めば済む。
- 悪い点：どのエージェントも作業のたびにこれを読む。この記録で挙げた研究では、そうした概要は成功率を上げずに費用を増やした。
- 悪い点：エージェントがファイルの決まりを破っても、エージェントには何も伝わらない。ファイルが古くなっても、誰にも伝わらない。

### ハーネスを作らない

- 良い点：作るものも保守するものもない。
- 悪い点：エージェントは毎回コマンドと決まりを探し直し、見つけられなかった決まりを破り、その始末をレビュー担当者に残す。

### エージェント製品ごとに別々の決まりのファイルを置く

- 良い点：それぞれのファイルで、その製品の機能を使える。
- 悪い点：ファイルどうしの中身がずれていく。あるファイルで決まりを変えても、ほかのファイルでは古い決まりのまま残る。
