# TPL-0020: コーディングエージェントのハーネスでは決定的なチェックを優先し、指示は最小限から始める

## 背景と課題

このテンプレートでも、チームがテンプレートから作る製品でも、コードと文書の多くはコーディングエージェントが書く。
文章でしか書かれていない決まりは、エージェントが破りうる。決まりを読まないこともあれば、長い作業の途中で見失うことも、読み違えることもある。
そのとき、決まりが破られたことは、エージェントにも、ほかの誰にも伝わらない。

よくある対策は、リポジトリを説明する指示のファイルである。そこには、アーキテクチャ・慣習・すべての決まりを書く。
エージェントはこのファイルを作業のたびに読むので、毎回トークンを消費する。コードが変わるにつれてファイルの中身は古くなり、エージェントがそこに書かれた決まりを破っても何の知らせもない。
ETH Zurich による2026年の「Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?」という研究がある。この研究は、リポジトリの概要を書いたファイルがエージェントの作業の成功率を上げず、費用を2割ほど増やしたと報告している。

エージェントにこのテンプレートの決まりを守らせるにはどうすればよいか。また、すべてのエージェントが読む指示には何を書くべきか。

## 判断の基準

- 大事な決まりは、エージェントがそれを読まなかったときも、理解しなかったときも守られる。
- エージェントは、チェックの出力から自分の誤りを人の手を借りずに直せる。
- どのエージェントも作業のたびに指示を読むので、指示の1行1行が費用に見合う。
- どのエージェント製品にも、人と同じ決まりが効く。
- 指示を変えるときは、推測ではなく、失敗の証拠に基づく。

## 検討した選択肢

- 決定的なチェックを優先し、指示は最小限にして、評価で確かめた失敗からだけ増やす
- アーキテクチャとすべての決まりを説明する長い指示のファイル
- ハーネスを作らず、エージェントはコードと README だけを頼りに作業する
- エージェント製品ごとに別々の決まりのファイルを置く

## 決定

採用：「決定的なチェックを優先し、指示は最小限にして、評価で確かめた失敗からだけ増やす」。チェックはエージェントが何を読んだかに関係なく決まりを守らせ、短い指示のファイルは費用が小さく、古くなりにくいからである。

決まりは次のとおりである。

- 大事な決まりは、チェックで守らせる。チェックの指摘は1件1行で、ファイルと行・ルール・直し方・理由を書いた記録を示す。エージェントは、その1行から自分で誤りを直せる。
- `AGENTS.md` に書くのは、コマンド・ファイルの置き場所・「終える前に `make check` を実行する」という指示・よくある既定から外れる決まりだけである。理由は記録に、手順はスキルとガイドに書く。
- `CLAUDE.md` は `AGENTS.md` を読み込むだけにする。こうして、どのエージェントも同じファイルを読む。
- `AGENTS.md` に指示を足すのは、どのチェックでも捕まえられない失敗が評価で見つかったときだけである。評価は `evals/` に置き、後のマイルストーンで入る。

ハーネスは次の部品からなる。

- Claude Code のフック。エージェントがファイルを編集すると、そのファイルを整形する。生成コードの編集・`.env` の読み取り・prd への変更の適用・force push を止める。ターンの終わりには、変更の及ぶ範囲のチェックを実行し、失敗をエージェントに差し戻す。差し戻す回数には上限がある。
- 繰り返す手順のためのスキル。記録を書く手順や、対訳をそろえる手順がある。スキルは、後のマイルストーンでコードと一緒に増える。
- 書いた本人とは別の目で見るサブエージェント。1つは変更を記録に照らしてレビューし、もう1つは対訳を原文と比べる。
- 権限の設定。安全なコマンドは確認なしで実行させ、危険なコマンドは拒む。
- lefthook。人にも、コミットの前とプッシュの前に同じチェックをかける（`lefthook.yml`）。

### 結果

- 良い点：エージェントが決まりを読んだかどうかに関係なく、決まりは守られる。エージェントは、決まりを破ったその時点で決まりを知る。
- 良い点：人・エージェント・CI が1つの `make check` を共有するので、エージェント製品ごとの決まりは要らない。
- 良い点：`AGENTS.md` が短いままなので、作業ごとの費用が小さく、古くなる部分も少ない。
- 悪い点：名前の付け方、ドメインモデルの形、テストが確かめるべきことを確かめているかなど、チェックできない決まりもある。それらはレビューと、レビューを担うサブエージェントに頼る。
- 悪い点：指摘が記録を示すのは、このリポジトリが出力の形を決められるところだけである。具体的には、自前のチェックと、gitleaks と Trivy の出力テンプレートに限られる。ほかの linter は独自の形式で出力するので、エージェントはルールの名前から理由を探す必要がある。
- 悪い点：`evals/` ができるまでは、短い `AGENTS.md` で足りるかどうかを測る手段がない。それまでの選択は、先の研究と判断に頼っている。
- 悪い点：フックが動くのは Claude Code の中だけである。ほかのエージェントがチェックを受けるのは、`make check`・lefthook・CI を通してだけである。

### 確認の方法

- `make check` が関門である。人・エージェント・CI がこれを実行し、フックもターンの終わりにこれを実行する。
- `make check` はターゲット `lint-agents-md` を実行し、`AGENTS.md` を短く保つ。
- フックと権限の設定は `.claude/settings.json` にある。
- `evals/` の評価は、後のマイルストーンで入る。それまでは、`AGENTS.md` に足す指示がどのチェックでも置き換えられないものであることを、レビューで確かめる。

## 選択肢の長所と短所

### 決定的なチェックを優先し、指示は最小限にする

- 良い点：チェックは、どのエージェントにも、どのモデルにも、どの人にも同じように働く。
- 良い点：失敗したチェックの出力が直すべき点を示すので、エージェントは人の手を借りずに問題を直せる。
- 悪い点：チェックを書いて出力を役に立つ形に保つのは、文を1つ書くより手間がかかる。
- 悪い点：長いファイルなら得られたはずの文脈をエージェントが知らず、それを知るために、失敗するチェックに1ターンを使うことがある。

### 長い指示のファイル

- 良い点：すべてが1か所にあり、新しいエージェントも人も、一度読めば済む。
- 悪い点：どのエージェントも作業のたびにこれを読む。この記録で挙げた研究では、そうした概要は成功率を上げずに費用を増やした。
- 悪い点：エージェントがファイルの決まりを破っても、エージェントには何も伝わらない。ファイルが古くなっても、誰にも伝わらない。

### ハーネスを作らない

- 良い点：作るものも保守するものもない。
- 悪い点：エージェントは毎回コマンドと決まりを探し直し、見つけられなかった決まりを破り、その始末をレビュー担当者に残す。

### エージェント製品ごとに別々の決まりのファイルを置く

- 良い点：それぞれのファイルで、その製品の機能を使える。
- 悪い点：ファイルどうしの中身がずれていく。あるファイルで決まりを変えても、ほかのファイルでは古い決まりのまま残る。
