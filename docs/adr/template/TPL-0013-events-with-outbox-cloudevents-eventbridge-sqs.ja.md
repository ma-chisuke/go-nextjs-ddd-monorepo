# TPL-0013: 統合イベントは送信箱から CloudEvents の形で EventBridge に発行し、受け取る文脈ごとに SQS のキューを置く

## 背景と課題

区切られた文脈どうしは、API とイベントで連携する（TPL-0005）。
見本では、予約（Reservation）が通知（Notification）に予約の確定や取り消しを知らせ、通知がメールを送る。

イベントの発行は、見た目より難しい。
文脈は自分のデータベースで状態を変え、さらにメッセージをブローカーへ渡す必要がある。この2つは別々のシステムであり、両方をまとめるトランザクションはない。
サービスがコミットしたあと、送る前に落ちると、イベントは失われる。先に送ってからトランザクションが失敗すると、ほかの文脈は起きなかった変更をもとに動いてしまう。

受け取る側にも別の問題がある。
イベントが送られたときに止まっていることもあれば、1つのメッセージで何度も失敗することも、同じメッセージを2回受け取ることもある。

イベントの形も問題になる。
統合イベントは文脈の境界を越えるので、その形は API と同じく公開された契約である（TPL-0006）。受け取る側はその形に依存し、形は受け取る側の都合と関係なく変わっていく。

AWS の上で、文脈どうしが統合イベントを確実に発行し受け取るにはどうすればよく、イベントの形はどう定めればよいか。

## 判断の基準

- 状態の変更がコミットされたときに限り、その変更を知らせるイベントが発行される。
- 発行側は受け取る側を知らない。受け取る側を足しても、発行側は何も変わらない。
- 受け取る側が止まっていたり失敗し続けたりしても、イベントは失われない。1つの悪いメッセージが、残りのメッセージを止めない。
- 各イベントの形は、機械で検査できる契約である。
- ブローカーのクラスターを自分で運用しない、AWS のマネージドサービスを使う。流れ全体を手元でも動かせる（TPL-0017）。

## 検討した選択肢

- 送信箱と中継、EventBridge、受け取る文脈ごとの SQS のキュー
- コミットの直後にブローカーへ発行する（二重書き込み）
- SNS のトピックと SQS のキュー
- Kafka（Amazon MSK）
- データベースの変更データキャプチャ

## 決定

採用：「送信箱と中継、EventBridge、受け取る文脈ごとの SQS のキュー」。理由は2つある。送信箱を使えば、発行がコミットと同じだけ確実になる。EventBridge と受け取る側ごとのキューを使えば、発行側が受け取る側を知らないまま、マネージドサービスだけで購読の仕組みを作れる。

決まりは次のとおりである。

- 文脈は、統合イベントを自分のスキーマの送信箱のテーブルに書く。書くのは、状態の変更と同じトランザクションの中である。
- 中継は送信箱の新しい行を読み、専用の EventBridge のイベントバスへ発行し、そのあとで発行済みの印を付ける。2つの手順の間で中継が失敗すると、同じ行をもう一度発行する。したがって、少なくとも1回の配信になる。
- 中継はこのリポジトリのコード `backend/internal/platform/outbox` であり、その文脈のイメージから、独立したプロセスとして動く（TPL-0014）。
- バスの上では、イベントは EventBridge のエントリーである。エントリーの `source` と `detail-type` は封筒の `source` と `type` であり、`detail` は封筒そのものである。
- 受け取る文脈はそれぞれ、デッドレターキュー付きの SQS のキューを持つ。その文脈が必要とするイベントは、EventBridge のルールが `source` と `detail-type` で選び、`detail` だけをキューへ送る（入力パス `$.detail`）。そのため、キューが受け取るのは、発行側が書いたままの封筒である。ルールは受け取る側のインフラのユニットに置く（TPL-0015）ので、発行側は受け取る側を知らない。AWS では、受け取る側のユニット `contexts/<context>` がモジュール `context-service` を通してキューとルールを作り、ユニット `platform` がバスを作る。
- 発行する文脈のタスクロールが呼べるのは、バスに対する `events:PutEvents` と `events:DescribeEventBus` だけである。受け取る文脈のタスクロールが呼べるのは、自分のキューに対する `sqs:ReceiveMessage` と `sqs:DeleteMessage` だけである（TPL-0014）。
- すべてのイベントに、CloudEvents 1.0 の封筒を使う。イベントの種類ごとの中身は、`contracts/events/<context>/<Event>.v1.json` の JSON Schema で定める。受け取る側を壊す変更は、イベントの新しいバージョンとして新しいファイルに書く。
- AsyncAPI 3.0 の文書でチャネルを記述する。どの文脈がどのイベントを発行し、どの文脈がそれを受け取るかを、この文書に書く。
- 受け取る側は冪等にする。同じイベントを2回処理しても、効果は1回分になる。たとえば、処理したイベントの `id` を受け取る側で記録しておく。
- ドメインとユースケースは、EventBridge も SQS も知らない。送信箱とキューは、ポートとアダプターを通して使う（TPL-0004）。
- 見本には `ReservationConfirmed` と `ReservationCancelled` の2つのイベントがある。予約が発行し、通知が受け取る。

中継はライブラリを使わず、自分たちで書く。中継の仕事は小さく、ライブラリはそれ以上のものを持ち込むからである。

- River は、Go と PostgreSQL のためのジョブキューである。River は自分のテーブルとそのマイグレーションを持つ。一方、各文脈は自分の `schema.sql` でテーブルを宣言し（TPL-0010）、スキーマを1つ所有する（TPL-0009）。
- Watermill には SQL の送信箱があるが、独自のテーブルの形とメッセージの抽象を持ち込む。しかも EventBridge への発行側を持たないので、どのみちアダプターが要る。
- 中継は、待っている行を順に読み、1つずつ発行し、印を付ける。これを、2つのポートの裏の約170行で実現している。ポートは、文脈が自分の送信箱の上に実装する `Source` と、`platform/awsevents` が EventBridge の上に実装する `Publisher` である。送信箱はその文脈の `schema.sql` のテーブルであり、そのクエリは sqlc を通る（TPL-0011）。中継のテストは、2つのポートの偽物（`outbox/outboxtest`）を使う、素の Go のテストである。

中継は、1秒ごとに送信箱を見る。待っている行を id の順に最大20行、`FOR UPDATE SKIP LOCKED` で取る。そのため、複数の中継を同時に動かせ、各イベントはそのうちの1つに渡る。中継は、イベント1つにつき1回 `PutEvents` を呼んで発行し、発行した行に同じトランザクションの中で印を付ける。発行済みの行は、7日後に消す（`outbox.Config`）。

この決定のうち2つの点は、最初の計画と違う。

- 最初の計画は、中継の実装を決めずにおいた。候補は Watermill・River・自作のコードであり、イベントを扱うマイルストーンで決めることにしていた。
- 最初の計画には、AWS Emulator が EventBridge から SQS へ配信できない場合の代わりの案があった。中継が購読の表を読み、自分でキューへイベントを送る案である。AWS Emulator は配信できた（TPL-0017）ので、この案は作っていない。

### 結果

- 良い点：状態の変更がコミットされたときに限りイベントが保存される。そのため、イベントが失われることも、取り消された変更を知らせることもない。
- 良い点：受け取る側を足す作業は、その文脈のユニットにキューとルールを足すことだけである。発行側は変わらない。
- 良い点：受け取る側ごとにキューとデッドレターキューがある。ある受け取る側が遅れても失敗していても、ほかの受け取る側は影響を受けない。失敗し続けるメッセージは、決まった回数を試したあとでデッドレターキューへ移される。
- 良い点：流れの中で、中継以外はすべてマネージドサービスであり、運用するブローカーがない。
- 悪い点：配信は少なくとも1回であり、イベントの順序も保証されない。そのため、受け取る側はすべて冪等である必要があり、順序の入れ替わったイベントにも対応する必要がある。
- 悪い点：中継という部品を1つ運用する必要がある。コミットから発行までに、最大で中継の間隔である1秒の遅れも生じる。
- 悪い点：中継は、このリポジトリが保守するコードである。`PutEvents` は1回で10件まで受け付けるが、中継は1回に1件しか発行しない。
- 悪い点：受け取る側の処理の結果がずっと拒まれると、イベントは配信のたびに失敗し、最後はデッドレターキューへ移る。Amazon SES が拒むメール（検証済みの ID のどれにも当たらない差出人のメールなど）がその例である。人がアカウントや ID を直し、イベントをデッドレターキューから戻す。
- 悪い点：ブローカーが常に拒むイベントと、読めない送信箱の行は、送信箱に残る。中継は間隔ごとにそれらを試し直し、失敗をそのつどログに書く。試した回数は数えず、脇へ移す場所もないので、見つけるには人がログを読む必要がある。
- 悪い点：送信箱のテーブルは大きくなっていく。中継は、発行済みの行を7日間残し、そのあとで消す。
- 悪い点：流れ全体をテストするには、AWS か、そのエミュレーターが要る（TPL-0017）。

### 確認の方法

次のチェックが、この決定を守らせる。

- `make check` の `lint-events` が、各イベントの JSON Schema を調べる。調べるのは、ファイルの名前、形、オブジェクトが閉じていないこと、例がスキーマに合うこと、文脈の AsyncAPI 文書にスキーマを参照するメッセージがあることである。規則は[イベントを変更する](../../guides/event-changes.ja.md)にある。
- `make check` の `lint-events-breaking` が、各 JSON Schema を `origin/main` とのマージベースにあるバージョンと比べる。そのバージョンを受け取る側が読めなくなる変更と、スキーマのファイルの削除で失敗する。
- `lint-contracts` が、Redocly CLI で AsyncAPI 文書を lint する。
- 発行側のテスト（`adapter/postgres/events_test.go`）が、Reservation の作る統合イベントをすべて `eventtest.AssertMatchesContract` に通す。これは、イベントをその型の JSON Schema で検証する。統合イベントを持たない種類のイベントがドメインに加わったときにも、このテストは失敗する。
- 受け取る側のテストは、Notification が読む JSON Schema のすべての例をメールにする（Notification の `internal/app/events_test.go`）。そのため、Notification の読めない例があれば、テストは失敗する。
- Reservation の結合テストが、次のことを確かめる。ストアは変更のイベントをその変更と一緒に書き、拒んだ変更のイベントは書かない。2つの中継が同じイベントを取ることはない。読めない行があっても、ほかの行は止まらない。
- Notification の結合テストは、1つのイベントを2回（同時の2回も含む）配信し、メールが1通であることを確かめる。
- `platform/awsevents` の結合テストは、発行側と受け取る側を AWS Emulator に対して動かす。イベントはルールとキューを通って受け取る側のハンドラーに届き、ハンドラーが失敗し続けるイベントはデッドレターキューに移る。このテストは `make test-integration` で動き、`make check-all` と CI に含まれる。
- `infra/modules/context-service` のテストは、2つのことを確かめる。発行側のタスクロールが、そのバスに限ってバスを調べてイベントを載せられること。受け取る側のタスクロールが、自分のキューに限ってメッセージを受け取って消せること。
- `make smoke` は、手元のシステムで予約を作り、変更し、取り消す。そして、送信箱・中継・バス・キュー・Notification のワーカーを通って届く3通のメールを、Mailpit で待つ。`make e2e` は、同じことをブラウザーの画面から行う。

## 選択肢の長所と短所

### 送信箱と中継、EventBridge、受け取る文脈ごとの SQS のキュー

- 良い点：発行の成否がコミットの成否と一致する。受け取る側は発行側から切り離され、受け取る側どうしも互いに影響しない。使うサービスはマネージドサービスである。
- 良い点：EventBridge のルールはイベントのどの項目でも条件にでき、ルールは受け取る側がそれぞれ持つ。EventBridge には、イベントを保管して再送する機能もある。
- 悪い点：中継を作って運用する必要があり、配信は少なくとも1回であり、順序も保証されない。

### コミットの直後にブローカーへ発行する（二重書き込み）

- 良い点：いちばん単純である。送信箱のテーブルも中継も要らない。
- 悪い点：コミットと発行は別々のシステムであり、共通のトランザクションがない。両者の間で落ちるとイベントは失われ、コミットの前に発行すると、あとで取り消される変更を知らせうる。

### SNS のトピックと SQS のキュー

- 良い点：購読者ごとにキューを持つ SNS は、メッセージを複数の宛先へ配る方法として成熟しており、安い。フィルターポリシーでメッセージを選べる。
- 良い点：メッセージあたりの料金が EventBridge より安く、遅れも小さい。
- 悪い点：発行側はイベントのまとまりごとにトピックを作って名前を付け、受け取る側はそのトピックを知っている必要がある。EventBridge なら、バスは1つで、ルールはどの項目でも条件にできる。

### Kafka（Amazon MSK）

- 良い点：パーティションごとに順序付きのログを保持し、受け取る側は好きな位置から読み直せる。非常に大きなスループットにも耐える。
- 悪い点：クラスターは使っていないときも費用がかかる。パーティション・コンシューマーグループ・保持期間についての知識も要り、見本が必要とする規模をはるかに超える。
- 悪い点：それでも送信箱は要る。Kafka への書き込みも、データベースのトランザクションには加わらないからである。

### データベースの変更データキャプチャ

- 良い点：データベースのログがイベントの源になるので、二重書き込みも送信箱の読み取りもない。
- 悪い点：変更データキャプチャの仕組み（たとえば Debezium と Kafka Connect）は、運用するには大きなシステムである。
- 悪い点：送信箱と組み合わせない限り、テーブルの変更を拾うことは、文脈の内部のテーブルをそのまま公開することになる。Aurora では論理レプリケーションも必要であり、論理レプリケーションを有効にすると Serverless v2 のクラスターが一時停止しなくなる（TPL-0016）。

## 補足

- まだ決めていないこと：どの受け取る側も読まなくなったイベントのバージョンを、どう廃止するか。スキーマのファイルを削除すると `lint-events-breaking` が失敗するので、いまはすべてのバージョンが残る。
- イベントの変更と追加、新しい受け取る側の購読の仕方は、[イベントを変更する](../../guides/event-changes.ja.md)にある。
