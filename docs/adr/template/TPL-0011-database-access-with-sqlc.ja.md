# TPL-0011: データベースへのアクセスに sqlc を使う

## 背景と課題

文脈はそれぞれ、自分のスキーマのテーブルを読み書きする（TPL-0009）。
それを担うのは文脈のアダプターのコードであり、SQL と Go の型がつながる場所でもある。
列名の書き間違い、型の取り違え、Go の型では受けられない NULL といった誤りは、手前で検査しない限り、クエリを実行して初めて表に出る。

このコードには、ほかの決定による制約が3つある。
文脈は、ほかの文脈のテーブルにクエリを出さない（TPL-0009）。
ドメインはデータベースを知らない（TPL-0004）ので、行をドメインのオブジェクトに変えるのはドメインではなくアダプターである。
さらに、SQL の多くはエージェントが書く。そのため、クエリはレビューの前に機械で検査する必要がある。

文脈の Go のコードは、自分のスキーマに対して SQL をどう実行すればよいか。

## 判断の基準

- スキーマに合わないクエリは、実行する前に失敗する。失敗するのは生成の時点か、コンパイルの時点である。
- 実行される SQL は、レビューする人が読む SQL と同じである。見えないところで SQL を組み立てる層を置かない。
- 文脈は、自分のスキーマにしかクエリを出せない。
- 出来上がるのは pgx のドライバの上に書かれた素の Go であり、実行時にフレームワークを必要としない。

## 検討した選択肢

- sqlc：SQL を手で書き、pgx 向けの型付きの Go を生成する
- ORM（GORM・ent）
- クエリビルダー（squirrel・goqu など）
- pgx の上に手でコードを書く

## 決定

採用：「sqlc：SQL を手で書き、pgx 向けの型付きの Go を生成する」。すべてのクエリを生成の時点で文脈のスキーマと照らし合わせ、型付きの Go を出力しながら、SQL を素のまま読める形で残せるからである。

決まりは次のとおりである。

- SQL は `backend/internal/<context>/internal/adapter/postgres/queries/*.sql` に手で書き、文ごとに名前を付ける。
- sqlc は、それらのクエリから pgx（バージョン5）向けの型付きの Go を生成する。sqlc を実行するのは `make gen` であり、生成コードは誰も手で編集しない。
- sqlc は文脈ごとに設定する。文脈の設定が読むのは、その文脈の `schema.sql`（TPL-0010）とその文脈のクエリだけである。
- 生成コードはアダプターの中に置く。中核の文脈では、アダプターのリポジトリが生成された行をドメインのオブジェクトに変えるので、生成された型がドメインやユースケースに届くことはない（TPL-0004）。ドメイン層のない補完の文脈では、ユースケースが生成したクエリを直接呼ぶ（TPL-0003）。
- 生成した Go のファイルの名前は `.gen.go` で終える。そうすれば、OpenAPI から生成したコード（TPL-0006）と同じく、`.gitattributes` と `.lintignore` がそれを生成コードとして扱う。名前は、sqlc の出力ファイルの名前の設定（`output_db_file_name`・`output_models_file_name`・`output_files_suffix` など）で決める。まだ確かめていないこと：これらの設定が、sqlc の書くすべてのファイルに及ぶか。これは最初の区切られた文脈で確かめる。

### 結果

- 良い点：存在しない列を名指しするクエリや、型の違う値を渡すクエリは、テストを実行する前に、生成の時点で失敗する。
- 良い点：ほかの文脈のテーブルへのクエリは、生成の時点で失敗する。そのテーブルは、sqlc が読むスキーマにないからである。
- 良い点：レビューで読む SQL が、そのまま実行される SQL である。書いたままの SQL に `EXPLAIN` をかけられる。
- 悪い点：動的なクエリは書きにくい。省略できる絞り込み条件のある検索や、呼び出し側が並び順を選ぶ一覧がその例である。対処は、クエリを形の数だけ書くか、`sqlc.narg('status') IS NULL OR status = sqlc.narg('status')` のような条件を持つ1つのクエリにまとめるかのどちらかである。後者では、PostgreSQL が効率の悪い実行計画を選ぶことがある。
- 悪い点：生成コードをリポジトリに置くので、スキーマやクエリを変えると、同じプルリクエストで生成コードのファイルも変わる。
- 悪い点：sqlc は SQL を特定のリリースの PostgreSQL のパーサー（libpg_query）で読み、型と関数の一覧も独自に持つ。そのため、PostgreSQL 18 で新しく入った構文や関数は、sqlc が追いつくまで sqlc の側で失敗しうる。

### 確認の方法

次のチェックが、この決定を守らせる。

- 生成コードが `make gen` の書く内容と違うとき、`make check` が失敗する。
- `make check-all` のターゲット `lint-sqlc` は、手元の PostgreSQL に、文脈の `schema.sql` を適用した作業用のデータベースを作り、文脈ごとに `sqlc vet` を実行する。ルール `sqlc/db-prepare` はすべてのクエリを PostgreSQL で prepare し、ルール `no-unfiltered-write` は `WHERE` のない `UPDATE` と `DELETE` で失敗する。これらの設定はどの文脈の `sqlc.yaml` でも同じであり、`sqlc/db-prepare` のない `sqlc.yaml` があればチェックが失敗する。
- ほかの文脈のテーブルへのクエリは、生成の時点で失敗する。そのテーブルは、sqlc が読むスキーマにないからである。

## 選択肢の長所と短所

### sqlc：SQL を手で書き、pgx 向けの型付きの Go を生成する

- 良い点：生成の時点でクエリをスキーマに照らして検査でき、出力は実行時に pgx 以外を必要としない素の Go である。
- 良い点：pgschema が適用するのと同じ `schema.sql` を直接読む（TPL-0010）。
- 悪い点：動的なクエリは書きにくく、パーサーが PostgreSQL の新しい構文に遅れることがある。

### ORM（GORM・ent）

- 良い点：動的なクエリや関連を書きやすい。コードの多くは生成器が作るか（ent）、そもそも書く必要がない（GORM）。
- 悪い点：実行される SQL が見えない。そのため、必要以上に読み込んだり、行ごとに1回ずつクエリを出したりしても気づきにくい。
- 悪い点：GORM がクエリを検査するのは実行時だけである。ent はスキーマを Go で定義するので、`schema.sql` をスキーマの唯一の正とする決定（TPL-0010）とぶつかる。
- 悪い点：ORM のモデルをそのままドメインのオブジェクトとして使いたくなり、そうするとドメインがデータベースに縛られる（TPL-0004）。

### クエリビルダー（squirrel・goqu など）

- 良い点：動的なクエリを自然に書ける。
- 悪い点：列名や型がスキーマに合っているかを、クエリの実行前に検査するものがない。
- 悪い点：レビューする人が読むのは SQL そのものではなく、SQL を組み立てる Go のコードである。

### pgx の上に手でコードを書く

- 良い点：生成するものも隠れているものもない。pgx はどの選択肢でもドライバとして使う。
- 悪い点：行を構造体に読み込むコードを手で書くのは繰り返しが多い。クエリと読み込みのコードの食い違いは、クエリを実行したときに初めてわかる。
- 悪い点：ほかの文脈のテーブルへのクエリを、実行前に止めるものがない。実行時にデータベースのロールが止めるだけである（TPL-0009）。

## 補足

- まだ確かめていないこと：テンプレートのスキーマとクエリが使う構文を、sqlc が PostgreSQL 18 の分まで全部読めるか。これは最初の区切られた文脈で確かめる。

- Go 向けの PostgreSQL のドライバ [pgx](https://github.com/jackc/pgx)
