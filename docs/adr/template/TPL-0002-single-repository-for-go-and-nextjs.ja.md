# TPL-0002: Go の API と Next.js の Web アプリを1つのリポジトリに置く

## 背景と課題

テンプレートが想定する製品は、2つのプログラムからなる。Go で書いた HTTP の API と、Next.js で書いた Web アプリである。
そのまわりに、API の契約・データベースのスキーマ・インフラのコード・文書がある。

ふつうの変更は、これらの部分をまたぐ。
たとえば画面に新しい項目を出すには、OpenAPI の文書、Go のハンドラー、その文書から両側に生成したコード、画面そのものを変える。
部分ごとにリポジトリを分けると、この1つの変更が複数のプルリクエストに分かれる。それらは決まった順にマージする必要があり、その間に契約のバージョンを公開しなければならない。

テンプレートには、コーディングエージェントのためのハーネスも含まれる。`AGENTS.md` の指示、フック、`make check` の裏にあるチェックである。
エージェントが検査できるのは、手元のチェックアウトにあるものだけである。
API と画面が別のリポジトリにあると、エージェントは片側を変えても、もう片側をビルドもテストもできない。

テンプレートのコードをどこに置き、その部分どうしを何でまとめればよいか。

## 判断の基準

- 契約の変更とその両側のコードが1つのプルリクエストに入り、チェックがそのすべてを対象にする。
- 人・エージェント・フック・CI が、同じコマンドと同じバージョンの道具を使う。
- 各言語の道具（`go` と `pnpm`）をそのまま使える。テンプレートを読む人が、先にビルドシステムを覚えなくてよい。
- リポジトリが大きくなっても構成を保てる。保てなくなるなら、変えどきを示す明確な目安がある。

## 検討した選択肢

- 1つのリポジトリにし、Make・pnpm のワークスペース・1つの Go モジュールで動かす
- API・Web アプリ・契約・インフラを別々のリポジトリにする
- 1つのリポジトリにし、モノレポ用のビルドシステム（Bazel・Nx・Turborepo）を使う

## 決定

採用：「1つのリポジトリにし、Make・pnpm のワークスペース・1つの Go モジュールで動かす」。変更のすべての側を1つのプルリクエストに収めて同じチェックにかけられ、しかもテンプレートがまだ必要としない道具を足さずに済むからである。

最上位のディレクトリは次のとおりである。

| ディレクトリ | 中身 |
|---|---|
| `backend/` | すべての区切られた文脈の Go のコード。1つの Go モジュールにする |
| `frontend/` | Next.js の Web アプリ（App Router）。pnpm のワークスペースのパッケージにする |
| `contracts/` | HTTP の API の OpenAPI の文書と、統合イベントのスキーマ |
| `db/` | 文脈がデータベースを使う前に必要なもの（スキーマ・ロール・拡張） |
| `infra/` | Terraform のモジュールと Terragrunt の設定 |
| `docs/` | 決定の記録、ガイド、文脈ごとの文書 |
| `tools/` | バージョンを固定した Go の道具と、このリポジトリが自前で書くスクリプトとチェック |

- 入口は Makefile だけである。主なターゲットは `make setup`・`make fmt`・`make gen`・`make check`・`make check-all` である。フック・エージェント・CI は、道具を直接ではなく `make` のターゲットを通して動かす。例外は `commit-msg` のフックだけで、コミットメッセージをスクリプト `tools/scripts/commit-msg.sh` で直接検査する（TPL-0023）。
- `tools/go.mod` は、リポジトリの道具のための別の Go モジュールである。Go の道具を `tool` ディレクティブで固定し、このリポジトリが自前で書くチェック（`tools/cmd/docs` など）も持つ。製品のコードの Go モジュールは、`backend/` の1つだけである。
- それでも各文脈は、`backend/cmd/<context>/` から自分のコンテナイメージを作り、別々にデプロイする。API と、ワーカーがあればワーカーは、そのイメージから別々のサービスとして動く（TPL-0014）。
- 変更のあったファイルに絞ってもチェックが遅すぎる状態になるまで、モノレポ用のビルドシステムは入れない。その目安は `make check` の時間の上限である（TPL-0023）。上限に届いたチームは、その変更を利用者の記録に残す。

### 結果

- 良い点：契約の変更、Go のコード、TypeScript のコード、両側の生成コードを、まとめてレビューしチェックできる。
- 良い点：エージェントは1つのチェックアウトで作業できる。自分が実装する契約を読め、自分の変更が壊しうるチェックをすべて実行できる。
- 良い点：ハーネスが1つで済む。`AGENTS.md` も、フックも、CI も、道具のバージョンを固定する場所も1つである。
- 良い点：共有するコード（lint のルールや、`backend/internal/platform/` にある技術の基盤など）への変更が、同じコミットですべての文脈に届く。
- 悪い点：遅いチェックは、変更のあったパスに絞らなければならない。絞らないと、どのプルリクエストでも、そのすべてがすべてのファイルに対して走る。これを `CHECK_SCOPE=changed` が受け持つ。変更が道具の固定やチェックの定義に及ぶときは、範囲をすべてのファイルに広げる（TPL-0023）。
- 悪い点：GitHub はリポジトリ単位でアクセス権を与える。一部を読める人は、全体を読める。`CODEOWNERS` でパスごとにレビュー担当を必須にはできるが、パスを隠すことはできない。
- 悪い点：リポジトリの履歴もリリースのタグの系列も1つである。部分ごとに独自のバージョンは持たない。
- 悪い点：すべての文脈が、Go の依存を同じバージョンで使う。依存のバージョンを上げるときは、新しいバージョンがすべての文脈で同時に動かなければならない。

### 確認の方法

構成はレビューで守る。最上位のディレクトリが増えたり減ったりしても、失敗するチェックはまだない。

いまあるものは次のとおりである。

- `make check` と `make check-all` が、リポジトリのすべてのチェックを実行する。`lefthook.yml` も同じターゲットを呼び、コミットの前にはステージしたファイルに範囲を絞る（`CHECK_SCOPE=staged`）。そのため、範囲が同じなら、フックで実行しても手で実行しても結果は同じになる。
- `pnpm-workspace.yaml` は、ワークスペースのパッケージとして `frontend` だけを挙げている。フロントエンドのマイルストーンから、`frontend/` には Next.js のアプリがある。`make gen` は、Go のコードと同じ API の文書からその型を書く（TPL-0006）。そのため、文書の変更と、Go のコードと、その変更が壊す画面は1つのプルリクエストに入り、`make check` がそのすべてを見る。
- フロントエンドは、リポジトリのルートにあるロックファイル `pnpm-lock.yaml` から依存を入れる。そのため、そのイメージはルートからビルドする（`frontend/Dockerfile`）。ビルドに入る少数のパス（ワークスペースのファイルと `frontend/`）は、`frontend/Dockerfile.dockerignore` が挙げる。
- CI のワークフロー（TPL-0018）も同じターゲットを呼ぶ。`make check` を実行するジョブはすべてのファイルを検査し、`make check-all` の遅いチェックを加えるジョブは、プルリクエストでは変更のあったファイルに範囲を絞る（`CHECK_SCOPE=changed`）。
- `backend/` と `contracts/` は、最初の文脈から、区切られた文脈とその契約を収める。
- `infra/` は、イベントを扱うマイルストーンから、手元の環境と AWS が共有する Terraform のモジュールを収める。それらを AWS Emulator に適用する `infra/local/` もここにある（TPL-0015、TPL-0017）。

あとから加わるものは次のとおりである。

- `infra/` のほかの Terraform のモジュールと Terragrunt の設定は、デプロイとともに加わる。

## 選択肢の長所と短所

### 1つのリポジトリにし、Make・pnpm のワークスペース・1つの Go モジュールで動かす

- 良い点：人やエージェントが直接使う道具は、コードがもともと必要とする `make`・`go`・`pnpm` と、それらを入れる mise だけである。
- 良い点：変更のすべての側が、1つのプルリクエストに入る。
- 悪い点：変更がどのチェックに影響するかを計算するしくみがない。チェックはパスで範囲を絞るが、これはビルドグラフより粗い。
- 悪い点：ビルドのキャッシュは、`go` と `pnpm` が各マシンに持つものだけである。

### API・Web アプリ・契約・インフラを別々のリポジトリにする

- 良い点：アクセス権・担当・バージョンを、リポジトリごとに決められる。
- 良い点：リポジトリごとの CI が小さく、速い。
- 悪い点：契約の変更が、順にマージすべき複数のプルリクエストに分かれる。その間に契約のバージョンを公開する必要もある。
- 悪い点：ハーネスを各リポジトリへコピーするので、コピーどうしが少しずつずれていく。
- 悪い点：あるリポジトリで作業するエージェントには、自分の変更のもう片側が見えず、検査もできない。

### 1つのリポジトリにし、モノレポ用のビルドシステム（Bazel・Nx・Turborepo）を使う

- 良い点：変更がどのターゲットに影響するかをビルドシステムが計算でき、マシンの間でキャッシュを共有できる。
- 良い点：Bazel は Go と TypeScript を外から隔離した環境でビルドするので、結果がマシンに左右されない。
- 悪い点：ビルドの記述がもう1つ増える。Bazel なら `BUILD` ファイル、Nx と Turborepo ならプロジェクトの設定ファイルである。
- 悪い点：Nx と Turborepo は JavaScript のパッケージを中心に作られている。Go を扱うには、プラグインか、Go のコマンドを包むスクリプトが要る。
- 悪い点：人もエージェントも、`go` と `pnpm` の代わりにビルドシステムを覚えて使うことになる。テンプレートはまだ、その手間に見合うほど大きくない。
