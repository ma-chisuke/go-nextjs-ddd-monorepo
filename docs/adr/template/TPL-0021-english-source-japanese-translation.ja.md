# TPL-0021: 文書は英語で書き、どの文書にも日本語の対訳を隣に置く

## 背景と課題

このテンプレートは公開されており、コピーする人の多くは英語を読む。
一方、テンプレートの持ち主はすべての文書をレビューし、そのレビューを日本語で行う。
レビューで見逃した誤りは、テンプレートのすべてのコピーに広がる。

2つの言語で文書を書くと、別の危険が生まれる。2つの文面が食い違ったとき、どちらが正しいのか、どちらが古いのかを見分ける手段がない。

どちらの言語を原文とし、もう一方の言語をどこに置き、2つの文面がまだ一致していることを読み手はどうやって知るか。

## 判断の基準

- 公開テンプレートの読み手が、すべての文書を読める。
- 持ち主が、すべての文書を日本語でレビューできる。
- 2つの文面が食い違ったとき、どちらか一方が正となる。
- 古くなった対訳は、読み手ではなくチェックが見つける。
- コードとツールへの指示は1つの言語で書き、そこには対訳を必要としない。

## 検討した選択肢

- 英語を原文とし、どの文書にも日本語の対訳を隣に置く
- 英語だけ
- 日本語だけ
- 日本語を原文とし、どの文書にも英語の対訳を隣に置く
- 対訳を別のツリー（`docs/ja/`）に置く
- 必要なときに機械翻訳し、何もコミットしない

## 決定

採用：「英語を原文とし、どの文書にも日本語の対訳を隣に置く」。両方の読み手に応えられ、2つの文面がずれたことをチェックで見つけられるからである。

決まりは[対訳のガイド](../../guides/translation.ja.md)のとおりである。

- `foo.md` は英語で、これが原文である。`foo.ja.md` はその日本語の対訳で、同じディレクトリに置く。
- 2つのファイルは同じコミットで変える。
- 対訳の最後の行に、訳した英語版のファイルの SHA-256 ハッシュを書く。この行は `make i18n-stamp` が書く。
- コード・コメント・コミットメッセージ・OpenAPI の文書の説明は、英語だけで書く。
- `.claude/` と `.github/` の下のファイルはツールへの指示なので、英語だけで書く。
- 英語の文章は Vale が Google の開発者向け文書のスタイルに照らして検査し、日本語の文章は textlint が検査する。日本語の文章規範はリポジトリに置き（`.claude/skills/japanese-tech-writing/`）、対訳はそれに従う。

### 結果

- 良い点：どちらの言語の読み手も、要約ではなく文書の全文を読める。
- 良い点：2つの文面が食い違ったときは、英語の文面で決まる。
- 良い点：2つのファイルが並んでいるので、相対リンクがどちらでも同じように働き、両方への変更が1つの差分に出る。
- 良い点：ツールとエージェントは英語の指示だけを読むので、食い違いうる2つの版を持つ指示がない。
- 悪い点：文書を変えるたびに2回書く必要があり、レビューの時間も延びる。
- 悪い点：日本語を書かない貢献者は、自分だけでは `make check` を通せない。対訳をそろえるスキルか、メンテナーの手助けが要る。
- 悪い点：ハッシュが示すのは、原文が変わったあとに誰かが対訳を更新したことだけであり、意味が一致していることまでは示さない。意味は、対訳を原文と比べるサブエージェントが確かめるが、違いを見落とすこともある。
- 悪い点：持ち主がレビューするのは原文ではなく対訳である。そのため、英語の文面だけにある誤りはレビューを通り抜けうる。

### 確認の方法

- `make check` はターゲット `lint-i18n` を実行する。`lint-i18n` は、対訳のない文書があるとき、または対訳に書かれたハッシュが英語版のハッシュと違うときに失敗する。
- `make check` は、英語の Markdown に Vale を（`lint-prose-en`）、日本語の Markdown に textlint を（`lint-prose-ja`）実行する。
- 意味は、対訳を原文と比べるサブエージェントが確かめ、その見落としはレビューで補う。
- コード・コメント・コミットメッセージ・OpenAPI の説明が英語であることは、レビューで確かめる。言語を守らせるチェックはない。

## 選択肢の長所と短所

### 英語を原文とし、どの文書にも日本語の対訳を隣に置く

- 良い点：どちらの読み手も全文を読める。
- 良い点：どちらの文面が正なのかがはっきりしている。
- 悪い点：書く手間が2倍になる。

### 英語だけ

- 良い点：文面が1つなので、そろえるものがない。
- 悪い点：持ち主が日本語でレビューできない。

### 日本語だけ

- 良い点：持ち主のレビューする文面と、読み手の読む文面が同じである。
- 悪い点：公開テンプレートの読み手の多くが読めない。

### 日本語を原文とし、どの文書にも英語の対訳を隣に置く

- 良い点：正となる文面を、持ち主が書いてレビューできる。
- 悪い点：読み手が読むのは対訳である。対訳の質が低いところでは、公開される文面の質も低くなる。
- 悪い点：コード・コメント・コミットメッセージはどのみち英語なので、文書だけが、説明する対象のコードと違う言語になる。

### 対訳を別のツリーに置く

- 良い点：英語のツリーには英語しか置かれない。
- 悪い点：対訳が原文から離れた場所にあるので、片方だけを変えてしまいやすい。相対リンクも2つのツリーで変わる。
- 悪い点：README や `AGENTS.md` のように `docs/` の外にある文書には、別の仕組みが要る。

### 必要なときに機械翻訳する

- 良い点：何も2回書かずに済む。
- 悪い点：読み手が読む文面を誰もレビューしない。用語も訳すたびに変わる。
- 悪い点：持ち主が対訳をレビューしても、その跡がリポジトリに残らない。
