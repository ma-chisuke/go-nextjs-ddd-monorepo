# TPL-0003: 区切られた文脈ごとにコードを分け、実装の重さを業務領域の種類で決める

## 背景と課題

テンプレートは、業務のコードをどう組み立てるかを示す必要がある。しかも、チームが見本を自分たちの業務に置き換えたあとも、その組み立てが通用しなければならない。
構造の大部分は、2つの問いで決まる。

1つ目の問いは、コードを分ける主な軸である。
製品は、業務の機能の単位で育つ。予約の新しいルールや、新しい種類の通知がその例である。
製品全体を技術の層で分けるとは、ハンドラーをすべて1か所に置き、リポジトリをすべて別の1か所に置くことである。
この構成では、業務の変更が1つあるだけで、すべての層に手が入る。
しかも、どのコードが業務のどの部分に属するのかが見えない。ある部分が別の部分のテーブルや型を使うのを止めるものもない。

2つ目の問いは、各部分にどれだけ設計をかけるかである。
業務の部分は、価値も複雑さも違う。
会議室の予約のルールは、この製品がほかと差をつける部分である。会議室の一覧は単なるデータの入力であり、メールの送信はほかの誰かがすでに解いた問題である。
すべての部分に戦術的なパターン（集約・値オブジェクト・リポジトリ・ドメインイベント）を一式そろえると、見返りのないところに手間をかけることになる。
逆にすべての部分を薄いスクリプトで書くと、複雑なルールを表すモデルがなく、ルールがハンドラーとクエリに散らばる。

テンプレートはコードをどう分け、各部分にどれだけの構造を与えればよいか。

## 判断の基準

- 業務の変更がコードの1つの部分に収まり、その部分の名前が業務の言葉になっている。
- 設計の量は、製品全体に1つの決まりを当てはめて決めるのではなく、業務ロジックの複雑さに合わせて決める。
- 見本で2つの書き方を並べて見せる。チームは、自分の文脈に合うほうを写せる。
- コード・契約・スキーマ・文書・インフラを同じ単位で分ける。1つの名前から、そのすべてにたどり着ける。

## 検討した選択肢

- 区切られた文脈ごとに分け、実装の重さを業務領域の種類で決める
- 製品全体を技術の層で分ける
- 区切られた文脈ごとに分け、どの文脈にも戦術的なパターンを一式そろえる
- 分けない

## 決定

採用：「区切られた文脈ごとに分け、実装の重さを業務領域の種類で決める」。業務の変更を1か所に収められ、しかも設計の手間を業務ロジックが複雑なところにだけかけられるからである。

文脈はどれも、次の場所で同じ名前を持つ。

| 部分 | 場所 |
|---|---|
| Go のコード | `backend/internal/<context>/`。入口は `backend/cmd/<context>/` |
| 画面 | `frontend/src/features/<context>/` |
| HTTP の契約 | `contracts/http/<context>.openapi.yaml`（TPL-0006） |
| データベース | 文脈ごとに1つのスキーマ（TPL-0009） |
| 文書 | `docs/contexts/<context>/`。責務・公開する API・イベントを書いた README と、業務の言葉の用語集 |
| インフラ | 文脈ごとに1つの Terragrunt のユニット（TPL-0015） |

文脈の作り方は、業務領域の種類で決める。決め方は、Vlad Khononov『ドメイン駆動設計をはじめよう』の10章が示す経験則に従う。

| 種類 | 実装 |
|---|---|
| 中核の業務領域 | ドメインモデル。ポートとアダプターで組む（TPL-0004） |
| 補完の業務領域 | トランザクションスクリプト。ユースケースが生成したクエリを直接呼び（TPL-0011）、ドメイン層は置かない |
| 一般の業務領域 | 買ってくるか、既製のものを使う。製品もライブラリも、ポートを通して使う |

- 各文脈の README に、その業務領域の種類と、そう分類した理由を書く。
- この経験則は、アクティブレコードと、イベントソーシングを使うドメインモデルも選択肢に挙げている。テンプレートは種類ごとに1つのパターンだけを使う。そのため、読み手が覚える書き方は、4つでなく2つで済む。ほかのパターンが必要なチームは、それを利用者の記録に残す。

見本の業務は、会議室の予約である。

| 文脈 | 種類 | 実装 | 責務 |
|---|---|---|---|
| Reservation（予約） | 中核 | ドメインモデル | 会議室の予約・変更・取り消し |
| Facility（施設） | 補完 | トランザクションスクリプト | 会議室の登録（定員と使える時間帯を含む） |
| Notification（通知） | 補完 | トランザクションスクリプト | 予約の確定と取り消しを知らせるメールの送信 |

### 結果

- 良い点：業務の変更は、たいてい各部分の1つのディレクトリに収まる。そのディレクトリの名前は、文脈の名前である。
- 良い点：中核の業務領域の複雑なルールには、データベースなしでテストできるモデルがある。一方、単純な文脈は短いまま保てる。
- 良い点：見本で2つの書き方を並べて見られる。各文脈の README には、なぜその書き方にしたかが書いてある。
- 悪い点：人もエージェントも2つの書き方を覚え、文脈にコードを足す前にその README を読む必要がある。
- 悪い点：業務領域の種類は判断である。判断は誤ることがあり、業務が変わるにつれて古くなることもある。
- 悪い点：ルールが増えた補完の文脈は、ドメインモデルに移す必要がある。それには、業務ロジックを集約を中心に書き直さなければならない。
- 悪い点：文脈ごとにディレクトリ・契約・スキーマ・文書を持つので、1つのパッケージに比べてファイルも組み立てのコードも増える。ロジックの少ない文脈ほど、この負担が目立つ。

### 確認の方法

業務領域の分類はレビューで守る。中核の業務領域と補完の業務領域を見分けられるプログラムはないからである。
レビューする人は、変更を、その変更が手を入れる各文脈の README と照らし合わせる。

次のチェックが、Go のコードの分け方を守る。

- Go の `internal` ディレクトリと、`lint-arch` の import のルール（TPL-0004、TPL-0005）が、ある文脈のコードを別の文脈から使えないようにする。
- 文脈ごとに設定した sqlc と、自分のスキーマにだけ権限を持つ文脈ごとの実行時のロール（TPL-0009）が、各文脈を自分のスキーマの中にとどめる（TPL-0005）。
- `lint-arch` のルール `arch/glossary` は、文脈の英語と日本語の用語集が `docs/contexts/<context>/` になければ失敗する。エクスポートされた型の欠けた用語集や、パッケージのエクスポートしていない識別子を挙げる用語集でも失敗する。対象のパッケージは文脈の `domain` であり、それがない文脈では `app` である。

`backend/internal/` の下のディレクトリ（`platform/` を除く）のうち、`docs/contexts/` の下に README のないものがあると失敗するチェックは、まだ作っていない。作るまでは、レビューで守る。

画面も同じ単位で分ける。画面を持つ文脈にはそれぞれ機能 `frontend/src/features/<context>/` があり、その API の呼び出し、サーバー関数、純粋なロジック、コンポーネントを収める。機能を組み合わせるのは `frontend/src/app/` のページである。ある文脈が渡すものを別の文脈が必要とする形にするのは `frontend/src/app/_compose/` で、バックエンドのアダプター `adapter/facility` と同じ役目を持つ。たとえば会議室のページは、Facility の会議室を Reservation の言葉にして Reservation に渡す。

- `lint-frontend` が実行する eslint-plugin-boundaries が、機能どうしを分けておく。機能はほかの機能を import せず、`frontend/src/lib/` はどの機能も import しない（`frontend/eslint.config.mjs` のルール `boundaries/dependencies`）。自己テストは、Facility のサーバーのモジュールを import する機能で、このルールを確かめる（`case_lint_frontend`）。
- 機能が自分の文脈の API だけを呼ぶことを守るチェックはない。`frontend/src/lib/api/server/clients.ts` は、すべての API のクライアントをすべての機能に与える。これはレビューで守る。

## 選択肢の長所と短所

### 区切られた文脈ごとに分け、実装の重さを業務領域の種類で決める

- 良い点：設計の手間を、業務ロジックが複雑なところにかけられる。
- 良い点：コードの境界が、業務の言葉の境界に沿う。
- 悪い点：コードの書き方が2つあり、どちらを選ぶかは判断になる。

### 製品全体を技術の層で分ける

- 良い点：多くのフレームワークがこの構成から始まるので、たいていの読み手がすでに知っている。
- 悪い点：業務の変更が1つあるだけで、すべての層に手が入る。どのコードが業務のどの部分に属するかも、構成からは見えない。
- 悪い点：業務のある部分が別の部分のテーブルや型を使うのを止めるものがないので、部分どうしが絡み合っていく。

### 区切られた文脈ごとに分け、どの文脈にも戦術的なパターンを一式そろえる

- 良い点：覚える書き方が1つで済む。
- 悪い点：データを保存して一覧するだけの文脈にも、集約・リポジトリ・詰め替えのコードができる。その手間が、中のロジックに見合わない。
- 悪い点：「どの文脈にも一式が要る」という、経験則が防ごうとしている誤りを、見本が教えることになる。

### 分けない

- 良い点：小さな製品なら、1つのパッケージで始めるのがいちばん速い。
- 悪い点：あとから境界を引くには、部分どうしがすでに依存し合っているコードを切り分けなければならない。
- 悪い点：テンプレートが示すべき構造を示せない。

## 補足

- Vlad Khononov『ドメイン駆動設計をはじめよう』（オライリー・ジャパン）の10章：業務領域の種類ごとに実装のパターンを選ぶ経験則。原書は "Learning Domain-Driven Design"（O'Reilly、2021）の "Design Heuristics" の章である。
- 同書の1章：中核・補完・一般の業務領域。
