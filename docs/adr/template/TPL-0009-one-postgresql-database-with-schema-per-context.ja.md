# TPL-0009: PostgreSQL 18 のデータベースを1つにし、文脈ごとにスキーマとロールを分ける

## 背景と課題

バックエンドは区切られた文脈ごとに分かれており（TPL-0003）、文脈どうしは API とイベントだけで連携する（TPL-0005）。
データには文脈ごとに持ち主がいる。ほかの文脈がそのデータを知る手段は、持ち主の API とイベントだけである。

この決まりは、データベースの側でも支える必要がある。
すべての文脈のテーブルが同じ場所に並び、どの接続からも全部を読めるなら、文脈をまたぐ結合は SQL の1行で書けてしまい、それを止めるものがない。
反対に、文脈ごとにデータベースのサーバーを立てると、費用と運用の手間が文脈の数だけ増える。見本の文脈は小さなものが3つであり、多くのチームも少ない数の文脈から始める。

どのデータベースを使うかも決める必要がある。
テンプレートには、トランザクション、複数の行にまたがる制約（見本では、同じ会議室で期間が重なる2つの予約を排他制約で拒む）、UUIDv7 の値を持てる UUID 型が要る（TPL-0012）。

文脈ごとにデータベースのサーバーを立てずに、ある文脈がほかの文脈のデータを読むことも変えることもできないようにするには、すべての文脈のデータをどう置けばよいか。

## 判断の基準

- ある文脈がほかの文脈のデータを読み書きすることを、データベース自身が止める。レビューだけには頼らない。
- 共有のデータベースに収まらなくなった文脈を、クエリやキーのからまりをほどく作業なしに外へ移せる。
- 費用と運用の手間が、手元の環境・stg・prd のどれでも小さなチームに見合う。
- 排他制約に対応し、UUIDv7 の値を生成できる（TPL-0012）。

## 検討した選択肢

- PostgreSQL 18 のデータベースを1つにし、文脈ごとにスキーマとロールを分ける
- 文脈ごとにデータベースのクラスタを分ける
- データベースを1つにし、すべてのテーブルを共有の1つのスキーマに置く
- クラスタを1つにし、文脈ごとにデータベースを分ける

## 決定

採用：「PostgreSQL 18 のデータベースを1つにし、文脈ごとにスキーマとロールを分ける」。運用して費用を払うサーバーを1つに保ったまま、文脈の境界をデータベースの権限で守れるからである。

決まりは次のとおりである。

- すべての文脈が、PostgreSQL 18 の1つのデータベースを使う。
- 文脈はそれぞれ、スキーマを1つとロールを2つ持つ。
  - 所有者のロール：スキーマを所有する。スキーマを変えられるのは、このロールだけである（TPL-0010）。
  - 実行時のロール：その文脈のサービスが接続に使う。自分のスキーマの行は読み書きできるが、スキーマ自体は変えられず、ほかのスキーマには何の権限も持たない。
- 外部キー・ビュー・クエリは、ある文脈のスキーマからほかの文脈のスキーマへまたがらない。ほかの文脈が必要とするデータは、API とイベントで渡す（TPL-0005）。
- 1つのトランザクションが2つの文脈にまたがることはない。ほかの文脈に知らせるべき変更は、イベントとして発行する（TPL-0013）。
- スキーマの管理の道具が扱わないもの（スキーマ・ロール・拡張）は、`db/bootstrap.sql` が作る。拡張の1つは `btree_gist` で、見本の排他制約に必要である。

### 結果

- 良い点：境界をデータベースが守る。ある文脈の実行時のロールでほかの文脈のテーブルを読もうとすると、コードの書き方にかかわらず「permission denied」で失敗する。
- 良い点：あとで文脈を専用のデータベースへ移せる。スキーマの中にほかのスキーマを指すものがないので、移す作業はスキーマ1つの複製と、接続先の設定1つの変更で済む。
- 良い点：環境ごとに、運用・バックアップ・バージョンアップ・支払いの対象となるサーバーが1つで済む。
- 悪い点：すべての文脈が、障害の影響範囲と資源を共有する。1つの文脈で起きた障害・重いクエリ・接続の急増が、全部の文脈に及ぶ。
- 悪い点：すべての文脈の接続プールが、1つのサーバーの接続数の上限を分け合う。プールの合計を、その上限より小さく保つ必要がある。
- 悪い点：PostgreSQL のメジャーバージョンを上げるときは、全部の文脈が同時に上がる。
- 悪い点：2つの文脈にまたがるトランザクションがない。意図したことではあるが、イベント（TPL-0013）は1つのトランザクションよりコードが増え、相手の文脈が変更を知るのも遅れる。

### 確認の方法

この決定を守らせるチェックは、まだない。M0 にはスキーマもクエリもロールもないからである。
次のチェックは、最初の区切られた文脈と一緒に入る。

- sqlc を文脈ごとに設定し、その文脈の `schema.sql` だけを読ませる。ほかの文脈のテーブルへのクエリは、生成の時点で失敗する（TPL-0011）。
- ロールの権限によって、そのようなクエリは実行時にも失敗する。
- 各 `schema.sql` を検査し、外部キーなどでほかのスキーマを参照していれば失敗させる。
- 結合テストで、ある文脈の実行時のロールで接続し、ほかの文脈のスキーマを読めないことを確かめる。

それまでは、レビューでこの決定を守る。

## 選択肢の長所と短所

### PostgreSQL 18 のデータベースを1つにし、文脈ごとにスキーマとロールを分ける

- 良い点：権限で境界を守りつつ、1つのサーバーで全部の文脈をまかなえる。
- 良い点：PostgreSQL は排他制約に対応している。PostgreSQL 18 では、組み込みの関数 `uuidv7()` で UUIDv7 の値を作れる。
- 悪い点：1つのサーバーの資源・障害・バージョンを、全部の文脈で共有する。

### 文脈ごとにデータベースのクラスタを分ける

- 良い点：隔離の度合いがいちばん高い。資源・障害・バージョン・バージョンアップが、すべて文脈ごとに分かれる。
- 良い点：データベースの大きさと設定を、文脈ごとに決められる。
- 悪い点：費用と手間が文脈の数に比例して増える。どの環境でも、クラスタごとにバックアップ・監視・バージョンアップ・認証情報が要る。
- 悪い点：手元の環境でも、文脈の数だけ PostgreSQL のサーバーを動かすことになる。

### データベースを1つにし、すべてのテーブルを共有の1つのスキーマに置く

- 良い点：いちばん単純な構成であり、多くの道具や例がこの形を前提にしている。
- 悪い点：文脈を分けるものが、名前とレビューしかない。どの接続からも全部のテーブルを読んで結合できるので、境界を越えるクエリが1つずつ増えていく。
- 悪い点：あとで文脈を外へ移すときは、境界をまたぐクエリと外部キーをすべて探すところから始めることになる。

### クラスタを1つにし、文脈ごとにデータベースを分ける

- 良い点：PostgreSQL は2つのデータベースにまたがるクエリを実行できない。そのため、ある文脈からほかの文脈のデータにはまったく届かない。
- 良い点：サーバーは1つのままで、全部の文脈をまかなえる。
- 悪い点：スキーマで分ける場合と比べて、得るものが小さい。サーバーの資源・障害・バージョンは、やはり共有する。
- 悪い点：障害の調査に使う読み取り専用のロールのように、文脈を横断して見る作業では、データベースごとに接続し直す必要がある。

## 補足

- PostgreSQL 18 のドキュメントの[スキーマ](https://www.postgresql.org/docs/18/ddl-schemas.html)と[権限](https://www.postgresql.org/docs/18/ddl-priv.html)
- 見本の排他制約は `EXCLUDE USING gist (room_id WITH =, period WITH &&)` である。GiST のインデックスで `room_id` のような列に `=` を使えるのは、`btree_gist` 拡張を入れた場合だけである。
- スキーマの管理には pgschema（TPL-0010）を、クエリの生成には sqlc（TPL-0011）を使う。AWS 上のデータベースは Aurora PostgreSQL である（TPL-0016）。
