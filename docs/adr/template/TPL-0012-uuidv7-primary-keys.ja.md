# TPL-0012: 主キーに UUIDv7 を使う

## 背景と課題

どのエンティティにも、存在する間は変わらない ID が要る。
主キーの型は、あとから変えるのが難しい。ID は、文脈の中のインデックスと外部キー、API のパス、イベント、さらにその ID を保存するほかの文脈へと広がっていくからである。

型の選び方を左右する要件は3つある。

- 行ができる前に ID がわかっている必要がある。予約を作るユースケースは、その URL を `Location` ヘッダーで返し、予約を知らせるイベントもその ID を含む。ID をデータベースが振るなら、コードは先に挿入し、あとから ID を読み戻すしかない。
- 中核の文脈のドメインは、乱数も I/O も使わない（TPL-0004）。そのため、ドメインは自分で ID を作れない。ID はドメインの外から渡す必要があり、テストではその値を固定できる必要がある。
- テーブルが大きくなっても、主キーのインデックスの効率が落ちない。

主キーにはどの型を使い、新しい ID はどこで作ればよいか。

## 判断の基準

- サービスの中でも、テストの中でも、イベントを書く前でも、データベースへ問い合わせることなく ID を作れる。
- テーブルが大きくなっても、主キーのインデックスへの挿入が一か所に集まる。
- PostgreSQL・Go・TypeScript・JSON Schema のどれもが知っている標準の型である。
- テーブルの行数や増え方が、ID から漏れない。

## 検討した選択肢

- `uuid` 型の列に入れる UUIDv7
- `bigint` の identity
- UUIDv4
- ULID

## 決定

採用：「`uuid` 型の列に入れる UUIDv7」。調整なしにどこでも作れ、連番と同じくインデックスへの挿入を一か所に集められ、しかも標準（RFC 9562）だからである。

決まりは次のとおりである。

- 主キーはすべて、RFC 9562 のバージョン7の UUID とし、`text` ではなく `uuid` 型の列に入れる。
- 中核の文脈では、ユースケースがポートから新しい ID を受け取り、ドメインに渡す。ドメインは ID を作らず（TPL-0004）、テストは固定の ID を渡す。
- トランザクションスクリプトで書く文脈では、PostgreSQL 18 に組み込まれた `uuidv7()` を列の既定値とし、挿入の結果として ID を返す。
- API とイベントでは、ID を UUID の標準の文字列の形で表す。

### 結果

- 良い点：値が時刻とともに増えるので、新しい行は連番と同じく B-tree のインデックスの端に入り、インデックスが詰まった状態に保たれる。
- 良い点：行ができる前に、コードが ID を知っている。ユースケースは何かを書き込む前から、`Location` ヘッダーとイベントに使う ID を持っている。
- 良い点：ほかの文脈の ID とも、あとで分けたデータベースの ID とも、調整なしに衝突しない。
- 良い点：連番と違い、ID から行数がわからない。
- 悪い点：UUID は16バイトで、`bigint` の2倍の大きさである。その差は、キー、そのキーを含むインデックス、キーへの参照のすべてにかかる。
- 悪い点：先頭の48ビットはミリ秒単位の作成時刻である。ID を見た人は誰でも、エンティティがいつ作られたかがわかる。多くのエンティティでは API がもともと作成時刻を返しているが、作成時刻を隠す必要があるエンティティについては「補足」を参照。
- 悪い点：UUID は長い。ログや URL で人が読んだり、見比べたり、口頭で伝えたりするのは難しい。

### 確認の方法

M0 にはスキーマもドメインのコードもないので、この決定を守らせるものはまだない。
最初の区切られた文脈と一緒に、各 `schema.sql` の検査が入る。主キーが `uuid` 型でなければ、この検査が失敗する。
中核の文脈が新しい ID をポートから受け取っていること、そのドメインが ID を作っていないことは、レビューで確かめる。

## 選択肢の長所と短所

### `uuid` 型の列に入れる UUIDv7

- 良い点：時刻順に並び、どこでも作れ、標準であり、専用の型を持つ。PostgreSQL 18 からは組み込みの関数（`uuidv7()`）もある。
- 悪い点：16バイトを使い、作成時刻が漏れ、人には読みにくい。

### `bigint` の identity

- 良い点：8バイトで済み、インデックスがいちばん小さくなり、人にも読みやすい。
- 悪い点：値を振れるのはデータベースだけである。コードが ID を知るのは挿入のあとになる。
- 悪い点：推測しやすく、量が漏れる。1日空けて2つの ID を見れば、その間に作られた行の数が誰にでもわかる。
- 悪い点：2つのデータベースの ID が衝突する。そのため、2つのデータベースのデータを合わせるときには ID の振り直しが要る。

### UUIDv4

- 良い点：122ビットの乱数なので、作成時刻を含めて何も漏れない。どの道具も対応している。
- 悪い点：値がばらばらなので、挿入がインデックス全体に散らばる。挿入のたびに違うページへ書き込み、ページの分割も増え、テーブルが大きくなるとメモリに載るインデックスの割合が減っていく。

### ULID

- 良い点：UUIDv7 と同じく時刻順に並ぶ。文字列の形は短く（26文字）、並べたときの順序も保たれる。
- 悪い点：コミュニティの仕様であり、RFC 9562 のような標準ではない。PostgreSQL には ULID の型も関数もない。`uuid` 型の列に入れると、データベースとコードとで文字列の形が違ってしまう。
- 悪い点：同じ考え方（ミリ秒単位の時刻のあとに乱数を続ける）は、すでに RFC 9562 が UUIDv7 として標準にしている。

## 補足

次の指針は同じ検討から出たもので、どの文脈にも当てはまる。

- 推測しにくい ID は、アクセス制御の代わりにならない。どのリクエストでも、呼び出し元がその ID のリソースを使ってよいかを確かめる。呼び出し元が見てはいけない ID には、存在しない ID と同じ 404 を返す。
- エンティティの作成時刻を隠す必要があるとき（匿名の通報や、ユーザーの登録日など）は、UUIDv4 を一意のインデックス付きの別の列に持たせて外に出し、UUIDv7 の主キーは内部にとどめる。
- 共有リンク・パスワードの再設定・招待のように、それだけでアクセスを許すリンクには、ID ではなく、暗号用の乱数で作った別のトークンを使う。
