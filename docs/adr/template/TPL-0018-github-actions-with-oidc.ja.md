# TPL-0018: CI/CD を GitHub Actions で動かし、AWS には OIDC で入る

## 背景と課題

このテンプレートのコード・プルリクエスト・レビューは GitHub にある。
どのプルリクエストにも、人やコーディングエージェントが手元で回すのと同じチェックが要る。
のちには AWS へのデプロイを動かす場所も要る。stg と prd は別の AWS アカウントに置く（TPL-0015）。

どの CI を選んでも、2つの問題が付いてくる。
1つめに、CI には CI だけのコマンドが増えていきやすい。そうなると、手元で通るチェックが CI で落ちたり、その逆が起きたりして、失敗を誰も再現できない。
2つめに、デプロイには AWS の認証情報が要る。CI に置いた長期のアクセスキーは、手に入れた人なら誰でも、ローテーションされるまでどこからでも使える。このキーは、ログからも、乗っ取られたアクションからも、ワークフローの書き誤りからも漏れうる。

CI をどこで動かし、そのワークフローを手元のチェックとどう同じに保ち、キーを置かずにデプロイから AWS へどう入るか。

## 判断の基準

- CI・人・エージェントが同じコマンドを実行し、同じ結果を得る。
- AWS の長期の認証情報をどこにも置かない。
- prd への変更には人の承認が要る。
- ジョブを足したり名前を変えたりしても、GitHub 上のリポジトリの設定を変えずに済む。
- ワークフローはリポジトリとそのトークンにアクセスできる状態で動く。そのため、ほかのコードと同じだけ厳しく検査する。
- テンプレートをコピーしたチームが、GitHub と AWS のほかにサービスを必要としない。

## 検討した選択肢

- GitHub Actions。AWS には GitHub の OIDC プロバイダーを通して入る
- GitHub Actions。AWS のアクセスキーをシークレットに置く
- AWS CodePipeline と AWS CodeBuild
- ほかのホスティング型の CI サービス

## 決定

採用：「GitHub Actions。AWS には GitHub の OIDC プロバイダーを通して入る」。プルリクエストのすぐ隣で動き、盗まれうるキーをどこにも残さないからである。

ワークフローの決まりは次のとおりである。

- コードのチェックアウト・mise の導入・キャッシュの復元のステップを除き、ワークフローのステップは `make setup` や `make check-all` のような `make` のターゲットを呼ぶだけにし、独自の処理を持たない。こうして、CI・人・エージェントが同じコマンドを実行する。
- 必須チェックの名前を `check` の1つに固定する。`check` はワークフローの最後のジョブで、ほかのすべてのジョブに依存する。そのため、ジョブを足してもルールセットは変わらない。
- `check` は、依存するジョブが失敗したりスキップされたりしても実行される。そして、依存するジョブの結果に、成功とスキップのどちらでもないものが1つあれば失敗する。こうしておかないと、ジョブが1つ失敗しただけで GitHub は `check` をスキップする。GitHub はスキップされたジョブを、通ったチェックとして扱う。
- 同じブランチで新しい実行が始まると、そのブランチでまだ進んでいる古い実行を取り消す。
- 道具と依存はキャッシュし、実行のたびにダウンロードし直さない。
- `make check` を実行するジョブは、すべてのファイルを検査する。`make check-all` の遅いチェックを加えるジョブは、プルリクエストでは変更のあったファイルに範囲を絞る（`CHECK_SCOPE=changed`）。`main` では、また変更が道具の固定やチェックの定義に及ぶときは、すべてのファイルを検査する（TPL-0023）。
- どのアクションも、コミット SHA の全桁で固定する。
- `permissions` は既定で読み取りだけにし、各ジョブは必要な権限だけを求める。
- どのジョブにも `timeout-minutes` を書く。

デプロイの決まりは次のとおりである。これらはインフラのマイルストーンで入る。

- デプロイのジョブは、GitHub の OIDC プロバイダーを通して IAM ロールを引き受け、短時間で失効する認証情報を受け取る。AWS のアクセスキーは GitHub に置かない。
- 変更を適用する各ロールの信頼ポリシーには、このリポジトリと、デプロイ先の GitHub の環境（Environment）を書く。ほかのリポジトリや環境からは、そのロールを引き受けられない。
- 各アカウントには、プルリクエストで `terragrunt plan` を実行するための読み取り専用のロールも置く（TPL-0015）。その信頼ポリシーには、環境ではなく、このリポジトリとそのプルリクエストを書く。このロールはインフラを読めるが、変えられない。
- stg と prd は、それぞれのアカウントに別々のロールを持つ。
- prd へのデプロイは、レビュー担当者の承認を求める GitHub の環境を通す。

### 結果

- 良い点：CI の失敗は、同じ `make` のコマンドを手元で実行すれば再現できる。
- 良い点：ログが漏れても、ステップが乗っ取られても、さらされるのは短時間で失効する認証情報だけである。しかも、何かを変えられる認証情報を受け取れるのは、指定したリポジトリと環境だけである。
- 良い点：ルールセットが名指しするチェックは1つなので、ジョブを足す・分ける・名前を変えるときに、GitHub の設定を変えずに済む。
- 良い点：チェック・prd の承認・ログが、プルリクエストのすぐ隣にそろう。
- 悪い点：`check` の条件は注意して書く必要がある。条件を誤ると、失敗したジョブがすり抜ける。
- 悪い点：信頼ポリシーは正確に書く必要がある。「持ち主のどのリポジトリでもよい」のような広すぎる条件にすると、誰もレビューしていないコードにロールを渡してしまう。
- 悪い点：GitHub Actions が止まると、CI もデプロイも止まる。
- 悪い点：プルリクエストでは遅いチェックが変更のあったファイルしか見ないので、そのプルリクエストが触れていないファイルの問題（ほかの文書の切れたリンクなど）は、`main` で初めて見つかる。
- 悪い点：固定した SHA を新しく保ち続ける必要がある。この更新は Renovate が受け持つ（TPL-0025）。

### 確認の方法

- `make check` は、`.github/workflows/` のワークフローに4つのチェックをかける（`make/actions.mk`）。構文と式は actionlint が、テンプレートインジェクションや広すぎる権限のようなセキュリティ上の弱点は zizmor が調べる。権限とタイムアウトの方針は ghalint が、コミット SHA の全桁での固定は pinact が調べる。
- ファイルに書き込まれた AWS のキーは、`make check` の実行する gitleaks と、GitHub のシークレットスキャン が見つける。GitHub のシークレットに置かれたキーはどちらからも見えないので、置いていないことをリポジトリの設定のレビューで確かめる。
- ステップが `make` を呼ぶだけで独自の処理を持たないことは、レビューで確かめる。これを守らせるチェックはない。`check` を求めるルールセットは、`make github-settings` が `docs/guides/github-settings.md` と比べる。
- IAM ロールとその信頼ポリシーは、インフラのマイルストーンで入る。それまでは AWS へのアクセスが要るワークフローはなく、デプロイの決まりもまだ効いていない。

## 選択肢の長所と短所

### GitHub Actions。AWS には GitHub の OIDC プロバイダーを通して入る

- 良い点：長期の認証情報がないので、ローテーションするものも、長く悪用されうるものもない。
- 良い点：どのリポジトリと環境がデプロイしてよいかを信頼ポリシーで決め、AWS がそれを強制する。
- 良い点：GitHub の環境を使えば、ほかの道具なしで prd に承認の段階を置ける。
- 良い点：Actions は GitHub のどのリポジトリでも使え、公開リポジトリならホスト型のランナーは無料である。
- 悪い点：サードパーティーのアクションは、他人の書いたコードがジョブの権限で動くものであり、その固定と検査に手間がかかる（TPL-0024）。
- 悪い点：信頼ポリシーは、気づきにくい形で誤りやすい。

### GitHub Actions。AWS のアクセスキーをシークレットに置く

- 良い点：設定がいちばん早く済む。
- 悪い点：キーは長期にわたって有効で、どこからでも使える。ログや乗っ取られたアクションからキーを読んだ者は、ローテーションされるまでそれを使える。
- 悪い点：ローテーションは手作業であり、忘れやすい。

### AWS CodePipeline と AWS CodeBuild

- 良い点：ビルドが AWS の中で IAM ロールを使って動くので、キーが AWS の外に出ない。
- 悪い点：フォークからのものも含め、すべてのプルリクエストのチェックが持ち主の AWS アカウントで動く。結果を GitHub に返すには、別に接続を設定する必要がある。
- 悪い点：テンプレートをコピーしたチームは、最初のチェックを動かす前に AWS アカウントを用意する必要がある。

### ほかのホスティング型の CI サービス

- 良い点：サービスによっては、より速いマシンや、より細かいキャッシュを使える。
- 悪い点：アカウントが1つ増え、権限とシークレットを置く場所が2か所になり、GitHub との接続を安全に保つ手間も増える。
- 悪い点：prd の承認が GitHub から離れ、そのサービス独自の仕組みに移る。
