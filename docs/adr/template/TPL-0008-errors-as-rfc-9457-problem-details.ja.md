# TPL-0008: エラーはすべて RFC 9457 の problem details で返す

## 背景と課題

どの API もエラーを返す。検証に通らないリクエスト、業務のルールに反する予約、存在しないリソース、そして誰も予期しなかった障害である。
クライアントは、これらのエラーをコードで見分け、役に立つメッセージを出し、誤っていたフィールドを示せなければならない。

エンドポイントごとにエラーの本文の形を決めると、クライアントは複数の形を覚えることになり、OpenAPI の文書もエラーを1つのスキーマで記述できない。
予期しない障害にエラーの文面をそのまま返すと、SQL・パス・ほかのサービスの名前といった内部の情報が漏れうる。

業務エラーには、もう1つ問題がある。
予約がほかの予約と重なること、会議室の定員を超えることは、ドメインが判断する（TPL-0004）。
HTTP のアダプターは、こうしたエラーをそれぞれステータスと本文に変換しなければならない。
ところが、新しい業務エラーが加わったとき、汎用の 500 で済まされずに的確な応答と対応付けられる保証はどこにもない。

エラーはどの形式で返し、業務エラーのそれぞれにどうやって的確な応答を対応させるか。

## 判断の基準

- すべての文脈のすべてのエラーに、1つの形式を使う。形式は1回だけ記述し、すべての OpenAPI の文書で使う。
- 公開された標準である。多くのクライアントと道具が、すでにその形式に対応している。
- エラーの種類ごとに、変わらない識別子と、それを説明するページがある。
- 検証のエラーは、誤っているフィールドを1つずつ示す。
- 予期しない障害の応答からは、内部の情報が何もわからない。

## 検討した選択肢

- RFC 9457 の problem details
- 独自のエラーの形式
- RFC 7807 の problem details
- JSON:API のエラーオブジェクト

## 決定

採用：「RFC 9457 の problem details」。HTTP の API のエラーを表す現行の標準であり、API が従う HTTP の意味論（TPL-0006）に合い、検証のエラーのためにテンプレートが必要とする拡張も許しているからである。

- 4xx と 5xx の応答は、すべてメディアタイプを `application/problem+json` にする。
- 本文には、`type`・`title`・`status`・`detail`・`instance` のメンバーを置く。
- `type` は、`docs/problems/` の下のページを指す URI である。そのページは、その問題と、クライアントがとれる対処を説明する。クライアントは `type` で問題を見分けるので、一度公開した URI は変えない。
- 検証のエラーには、`errors` の配列も置く。各要素には、誤っているフィールドを指す JSON Pointer（RFC 6901）の `pointer` と、何が誤っているかを述べる `detail` を置く。これは、RFC 9457 が示す例に倣った形である。
- 業務エラーは型付きのエラーであり、中核の文脈ではドメインに（TPL-0004）、ドメイン層のない補完の文脈では `app` に置く（TPL-0003）。各文脈の HTTP のアダプターは、業務エラーを problem details（その `type` とステータス）に対応させる表を1つ持つ。
- 表にないエラーは、ステータスが 500 で、`title` と `detail` が汎用の文面である problem details にする。本当のエラーはログに書き、応答には決して入れない。
- 生成コードは、一部のエラー（解析できないパラメーターなど）に自分で応答する（TPL-0006）。テンプレートはその処理を差し替え、そこからも problem details で応答させる。

### 結果

- 良い点：クライアントは、すべての文脈のすべてのエラーを1つの解析処理で扱い、`type` で見分けられる。
- 良い点：各 `type` から、そのエラーを説明するページにたどり着ける。このページは、クライアントを書く人もエージェントも参照できる。
- 良い点：表に載っていない新しい業務エラーは、ユーザーが 500 を受け取るより先に、テストで見つかる。
- 良い点：予期しない障害では、クライアントは 500 だけを受け取り、詳細はログに残る。
- 悪い点：各 `type` の URI には、同じアドレスにあり続けるページが要る。テンプレートをコピーしたチームは URI を自分のサイトに向け直す必要があり、各ページには日本語の対訳も要る（TPL-0021）。
- 悪い点：oapi-codegen に、メディアタイプが `application/problem+json` の応答を生成させるには工夫が要る。これはまだ確かめておらず、最初のエンドポイントで確かめる。
- 悪い点：標準は拡張のメンバーの形を決めていないので、`errors` はテンプレートが自分で定める。クライアントは、その部分をテンプレートの文書から学ぶことになる。

### 確認の方法

この決定を守るチェックは、まだ働いていない。リポジトリには、OpenAPI の文書も Go のコードもまだないからである。

- `redocly.yaml` のルール `rule/problem-details-only` は、OpenAPI の文書にある 4xx と 5xx の応答のメディアタイプを調べる。`application/problem+json` 以外があれば失敗する（TPL-0007 の層7）。このルールは `lint-contracts` が実行する。ルールはすでにあり、最初の契約ができた時点で働き始める。
- 各文脈の HTTP のアダプターにあるテストは、その文脈の業務エラーのうち表に載っていないものを見つけると失敗する。このテストは、最初の文脈とともに加わる（マイルストーン M1）。
- テストはすべての応答を文書と照らし合わせて検証する（TPL-0007 の層4）。そのため、problem details でないエラーの本文は、それを返したテストで失敗する。このテストも、最初の文脈とともに加わる。

## 選択肢の長所と短所

### RFC 9457 の problem details

- 良い点：IETF の標準であり、多くの HTTP のフレームワークやクライアントが、すでにこの形式を生成し、読み取れる。
- 良い点：`errors` のような拡張のメンバーを許すので、標準から外れずに形式を広げられる。
- 悪い点：独自のエラーの形式しか扱わないクライアントは、この形式を新たに覚える必要がある。

### 独自のエラーの形式

- 良い点：従うべき標準がなく、テンプレートが欲しいものをそのまま入れられる。
- 悪い点：どのクライアントもどの道具も、この API でしか使わない形を覚えることになる。
- 悪い点：専用のメディアタイプがないので、クライアントはメディアタイプからエラーを見分けられない。

### RFC 7807 の problem details

- 良い点：形式は RFC 9457 と同じであり、古いライブラリの中にはこの RFC の名前を使うものがある。
- 悪い点：RFC 9457 によって廃止された。RFC 9457 は、よく使う問題の種類のレジストリと、複数の問題を一度に報告するための指針も加えている。

### JSON:API のエラーオブジェクト

- 良い点：エラーオブジェクトに、誤ったフィールドを示す `source.pointer` があり、テンプレートが必要とするものに近い。
- 悪い点：JSON:API の仕様の一部であり、その仕様は API 全体に専用のメディアタイプと決まりを課す。この API はそれに従っていない。
