# TPL-0001: 決定を ADR に残し、テンプレートの決定と利用者の決定を分ける

## 背景と課題

このリポジトリはテンプレートである。
利用者のチームはこれをコピーし、自分たちの製品に作り変える。
したがって、コピーには2種類の決定が入る。コピーの前にテンプレートが下した決定と、コピーのあとにチームが下す決定である。

このリポジトリの決まりの多くは、チェックが守らせる。
ところが、チェックが伝えられるのは「決まりに反した」という事実だけである。
決まりに従うか、決まりを変えるかを判断するには、人もコーディングエージェントも、その決まりの理由を知る必要がある。

決まりの理由をすぐに見つけられ、しかもテンプレートが何を決めたかを失わずにチームが決定を置き換えられるようにするには、決定をどう残せばよいか。

## 判断の基準

- チェックが失敗したときのメッセージから、決まりの理由にたどり着ける。
- チームがテンプレートの新しいバージョンを取り込める。チームがテンプレートの記録を書き換えると、取り込むたびに衝突する。
- 記録の形をプログラムで検査できる。記録の多くをエージェントが書くからである。
- すでに広く知られている形式である。

## 検討した選択肢

- MADR 4.0.0。テンプレートの決定と利用者の決定を別のディレクトリに置く
- MADR 4.0.0。すべての決定を1つのディレクトリに置き、番号を通しで振る
- Michael Nygard の元の形式
- 記録を作らず、README とコードのコメントで決定を説明する

## 決定

採用：「MADR 4.0.0。テンプレートの決定と利用者の決定を別のディレクトリに置く」。チームが決定を足したり置き換えたりしても、テンプレートの決定が変わらずに残る選択肢は、これだけだからである。

決まりは次のとおりである。

- テンプレートの決定は `docs/adr/template/TPL-NNNN-<slug>.md`、利用者の決定は `docs/adr/ADR-NNNN-<slug>.md` に置く。番号は 0001 から始め、使い回さない。
- 記録の先頭に front matter を置き、`status`（`proposed`・`accepted`・`rejected`・`deprecated` のどれか）と `date`（決定を最後に変えた日）を書く。
- 題は `# <ID>: <題>` の形にする。
- 記録には「背景と課題」「検討した選択肢」「決定」の節を置く。「決定」の下には「結果」と「確認の方法」の小節を置く。
- 「確認の方法」には、その決定を守らせるチェックを書く。チェックで守らせられない決定は、レビューで守ると書く。
- チームはテンプレートの記録を書き換えない。別の決定をするときは利用者の記録を書き、その front matter に置き換える記録を並べる（例：`supersedes: [TPL-0010]`）。
- `docs/adr/README.md` は、すべての決定の一覧であり、置き換えられた決定には印が付く。この一覧は `make gen` が書く。
- どの記録にも、日本語の対訳を隣に置く（TPL-0021）。

### 結果

- 良い点：チェックのメッセージに TPL-0004 のような ID を書ける。ID から1つのファイルにたどり着ける。
- 良い点：チームがテンプレートの新しいバージョンを取り込める。`docs/adr/template/` の下のファイルが、テンプレートとコピーで同じだからである。
- 良い点：チームがテンプレートのどの決定を置き換えたかが一覧に出る。読み手は、コピーがテンプレートからどれだけ離れたかを一覧から読み取れる。
- 悪い点：テンプレートの決定がいまも有効かどうかは、その記録ではなく一覧を見ないとわからない。
- 悪い点：テンプレートは、公開した記録をあとから黙って直せない。意味を変えるときは新しい記録が要る。

### 確認の方法

`make check` が `lint-adr` を実行する。`lint-adr` は次の場合に失敗する。

- 記録のファイル名・front matter・題・節の並びのどれかが決まりに合わない。
- `supersedes` に、存在しない記録が書かれている。
- `docs/adr/README.md` が、`make gen` の書く内容と違う。
- `docs/adr/template/` の下のファイルが、`docs/adr/template/checksums.txt` のチェックサムと違う。

## 選択肢の長所と短所

### MADR 4.0.0。テンプレートの決定と利用者の決定を別のディレクトリに置く

- 良い点：決定の持ち主がディレクトリからわかる。
- 良い点：テンプレートが記録を足しても、テンプレートの番号と利用者の番号がぶつからない。
- 悪い点：番号の系列を2つ覚える必要がある。

### MADR 4.0.0。すべての決定を1つのディレクトリに置き、番号を通しで振る

- 良い点：見る場所が1つで済む。
- 悪い点：テンプレートの新しい記録と利用者の新しい記録が、同じ番号を取りうる。
- 悪い点：チームが書き換えてよい記録がどれなのかが、どこにも示されない。

### Michael Nygard の元の形式

- 良い点：短い。
- 悪い点：退けた選択肢と、決定の確認の方法を書く場所がない。エージェントが変更を提案する前に必要とするのは、この2つである。

### 記録を作らない

- 良い点：保守するものがない。
- 悪い点：決まりの理由が失われる。次に来た人は、理由を知らないまま決まりに従うか、決まりを消すかのどちらかになる。

## 補足

- [MADR 4.0.0](https://adr.github.io/madr/)
- 記録を書くときは、`.claude/skills/write-adr/` のスキルを使う。
