# TPL-0007: OpenAPI の文書と実装の一致を、層に分けたチェックで保つ

## 背景と課題

区切られた文脈ごとの OpenAPI の文書は、その文脈の API の正である（TPL-0006）。
テンプレートの要件として、実装の入出力が文書から食い違ったとき、機械が気づかないままになってはならない。

生成した型は食い違いの多くを捕まえるが、すべてではない。

- 文書を変えたあとで生成し直していない生成コードも、コンパイルは通る。
- 手で登録したルートは、文書に現れない。
- 型では表せない制約がある。Go の型からわかるのは、値が文字列であることまでである。どの文字列が正しいかは、パターン・最大長・`date-time` のような形式として、文書だけに書いてある。
- エラーの応答の本文は、どんな形にもなりうる。型には、それを禁じるものがない。
- どのテストも送らないリクエストが、文書に反する動きをするコードまで届くことがある。
- 文書そのものは正しいままでも、文書の変更がそれを使うクライアントを壊すことがある。

1つの道具で、これらすべてを捕まえることはできない。
どのチェックを組み合わせれば、どの種類の食い違いも見えるようになるか。各チェックは、どこで動かせばよいか。

## 判断の基準

- どの種類の食い違いも、変更をマージする前に機械が捕まえる。
- 各チェックは、それより前のチェックが捕まえられないものを捕まえる。そのため、1つの誤りは、たいてい1件の指摘になる（TPL-0023）。
- 速いチェックは `make check` で、遅いチェックは `make check-all` と CI で動かす。
- 本番が負担するのは、本番を守るチェックの分だけである。

## 検討した選択肢

- 層に分けたチェック。各層は、前の層が捕まえられないものを捕まえる
- 生成した型だけ
- コンシューマ駆動の契約テスト（Pact）
- 層に分けたチェックと、本番での応答の検証

## 決定

採用：「層に分けたチェック。各層は、前の層が捕まえられないものを捕まえる」。上に挙げたどの種類の食い違いにも、それで失敗するチェックがあり、しかも本番で動かすのはリクエストの検証だけだからである。

| 層 | 捕まえるもの | 方法 |
|---|---|---|
| 1. コンパイル時 | 操作の実装漏れ、パラメーターの誤り、応答の型の誤り | Go では oapi-codegen の strict server のインターフェース。openapi-typescript が生成した型には `tsc` |
| 2. 生成物の更新漏れ | 文書より古い生成コード | 生成し直し、差分がないことを求める |
| 3. 文書にない入口の禁止 | 手で登録したルート | ルートを登録するのは生成コードだけにする。ルートを直接登録することは、lint のルールで禁じる |
| 4. テストでの検証 | 型では表せない制約と、エラーの形 | テストで、すべてのリクエストと応答を kin-openapi で文書と照らし合わせる |
| 5. 生成した入力 | 誰もテストを書いていない入力 | Schemathesis が、文書からリクエストを生成する。シードは固定する |
| 6. 互換性 | 既存のクライアントにとって互換性を壊す変更 | oasdiff が、文書を main ブランチ上のバージョンと比べる |
| 7. 文書そのもの | テンプレートの決まりに反する文書 | Redocly CLI で文書を lint する。4xx と 5xx の応答には `application/problem+json` だけを使う、というルールも含む（TPL-0008） |

- 本番では、ミドルウェアが各リクエストを kin-openapi で文書と照らし合わせ、不正なリクエストには problem details で応答する（TPL-0008）。
- 本番では応答を検証しない。応答は、リリースの前に層4がテストで確かめている。本番で各応答を検証すると、テストがすでに探している食い違いのために、すべてのリクエストの処理が増える。
- 層5は、動いている API とデータベースを必要とし、時間もかかる。そのため `make check-all` で動かす。シードを固定しているので、同じコミットなら毎回同じ入力を送り、失敗を再現できる。

### 結果

- 良い点：背景と課題で挙げたどの種類の食い違いにも、それで失敗するチェックがある。
- 良い点：層ごとに捕まえるものが違うので、1つの誤りに対する指摘は、たいてい7件でなく1件で済む。
- 良い点：エラーの形は、ほかの応答と一緒にテストで確かめられる。別のレビューは要らない。
- 悪い点：API の一致のために、テンプレートは生成器のほかに複数の道具（kin-openapi・Schemathesis・oasdiff・Redocly CLI）を固定し、更新し続ける。道具は、食い違いの種類ごとに1つずつである。
- 悪い点：層4が確かめるのは、テストが送るリクエストだけである。層5がその隙間を狭めるが、すべての操作のすべての応答が文書に合うことを証明する層はない。
- 悪い点：意図して互換性を壊す変更も、層6で失敗する。チームがそうした変更をどう受け入れるかは、このチェックを書くときに決める。
- 悪い点：層5を動かすには API とデータベースが要る。そのため `make check-all` が遅くなり、手元のノートパソコンでは動かしにくくなる。

### 確認の方法

どの層も、まだ何も検査していない。リポジトリには、OpenAPI の文書も Go のコードもまだないからである。
2つの層のターゲットはすでにあり、入力ができた時点で働き始める。`lint-contracts`（層7）は最初の契約を lint し、`lint-frontend-types`（層1のうち TypeScript の部分）は最初の TypeScript のファイルを検査する。
ほかの層は、最初の文脈とともに加わる（マイルストーン M1）。ただし層5は、Schemathesis を加えるマイルストーンで加わる。

次の表は、各層を動かすターゲットである。「予定」と書いたターゲットはまだなく、作るときに名前を変えることもある。

| 層 | Make のターゲット | 呼び出し元 |
|---|---|---|
| 1. コンパイル時 | Go は `lint-go` と `test-go`。`tsc --noEmit` は `lint-frontend-types` | `make check` |
| 2. 生成物の更新漏れ | `gen-check`（予定）。`make gen` を実行し、差分があれば失敗する | `make check` |
| 3. 文書にない入口の禁止 | `lint-arch` のルール `arch/route-registration` | `make check` |
| 4. テストでの検証 | `test-go` | `make check` |
| 5. 生成した入力 | `test-api`（予定） | `make check-all` |
| 6. 互換性 | `lint-contracts-breaking`。oasdiff で、`origin/main` とのマージベース（`CHECK_BASE` を設定したときはそれとのマージベースで、CI はベースブランチを設定する）にある同じ文書と比べる | `make check` |
| 7. 文書そのもの | `lint-contracts` | `make check` |

層6は、同じ変更で文書の `info.version` を上げたとき、互換性を壊す変更を受け入れる。1.0 未満ではマイナーバージョンを、1.0 以降はメジャーバージョンを上げる。指摘を受けた人に向けて、[API を変更する](../../guides/api-changes.ja.md)がこの方法を説明している。

## 選択肢の長所と短所

### 層に分けたチェック。各層は、前の層が捕まえられないものを捕まえる

- 良い点：どの種類の食い違いにもチェックがあり、各チェックは、ほかのチェックが見逃す種類の食い違いを狙う。
- 悪い点：理解すべき層が7つある。コントリビューターは、どの層がなぜ失敗したのかを読み取れるようになる必要がある。

### 生成した型だけ

- 良い点：TPL-0006 の生成器のほかに、手間がかからない。
- 悪い点：古い生成コード、手で足したルート、型では表せない制約、エラーの形、互換性を壊す変更を見逃す。

### コンシューマ駆動の契約テスト（Pact）

- 良い点：各利用側が自分の頼っている部分を書き、提供側はまさにその部分に対してテストされる。
- 悪い点：利用側の期待が、OpenAPI の文書と並ぶ2つ目の契約になり、両者が食い違いうる。
- 悪い点：契約を共有する場所（Pact Broker など）と、利用側ごとのテストが要る。しかもここでは、利用側のコードもすでに同じリポジトリの同じ文書から生成している。

### 層に分けたチェックと、本番での応答の検証

- 良い点：どのテストも扱わない操作の食い違いが、本番で見える。
- 悪い点：すべての応答に処理が加わる。しかも検証に失敗した応答は、クライアントにとって不要なエラーに置き換えるか、ログに残すだけにするかのどちらかになる。
- 悪い点：食い違いを見つけるのがリリースのあとになる。層4と層5なら、その大半をリリースの前に見つけられる。
