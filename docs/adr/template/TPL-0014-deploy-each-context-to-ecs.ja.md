# TPL-0014: 文脈ごとに ECS へデプロイし、API は非公開にして、公開の入口を1つにする

## 背景と課題

バックエンドは1つの Go のモジュールであり、区切られた文脈ごとに分かれている（TPL-0003）。
それでも、デプロイの単位は選べる。全部の文脈を1つのプログラムとしてまとめてデプロイしてもよいし、文脈ごとに別のプログラムとしてデプロイしてもよい。

文脈ごとに分けてデプロイすると、テンプレートの目的にかなう。
ビルド・リリース・スケール・ロールバックを単独でできる文脈なら、1つのチームが受け持てる。ある文脈の障害やデプロイが、ほかの文脈を止めることもない。
境界が守られていることの証明にもなる。API とイベントだけでやり取りする文脈（TPL-0005）なら、別々のプロセスとして動かせるはずだからである。

リクエストの入口も要る。
ブラウザーは Next.js と通信し、各文脈の API を呼ぶのは Next.js とほかの文脈である。
文脈の API はインターネットから届かないようにし、届くのは Next.js だけにしたい。

AWS でサービスごとに入口を作るよくある方法は、ロードバランサーかリスナーのルール、ターゲットグループ、セキュリティグループ、DNS をサービスごとに用意することである。文脈を足すたびに、これだけのインフラを繰り返し作ることになる。
2026年10月20日、AWS は ECS のサービス向けのマネージドな入口として、Amazon ECS Gateway を公開した。

文脈と Next.js をどこで動かし、リクエストをどうやってそこへ届ければよいか。

## 判断の基準

- 文脈を、ほかの文脈と関係なくビルド・デプロイ・スケール・ロールバックできる。
- 文脈の API は非公開とし、公開するのは画面の側だけにする。
- 文脈ごとに繰り返すインフラが少なく、運用するクラスターがない。
- プロセスは長く動き続ける。API のサーバーと、SQS を読むワーカー（TPL-0013）があり、どちらもデータベースの接続プールを持つ（TPL-0016）。
- すべての部品を Terraform が作り、すべてのアドレスを Terraform がつなぐ。そうすれば環境はコードだけから生まれ、そのコードを AWS アカウントなしでチェックが試せる（TPL-0015）。

## 検討した選択肢

- 文脈ごとに Fargate 上の ECS のサービスを置き、API は非公開にしてサービスどうしが ECS Service Connect で呼び、Web フロントエンドにだけ公開のロードバランサーを1つ置く
- 文脈ごとに Fargate 上の ECS のサービスを置き、入口を ECS Gateway にする
- 全部の文脈を1つのデプロイ単位にする（モジュラーモノリス）
- Lambda と API Gateway
- Kubernetes（Amazon EKS）
- 文脈ごとに ECS のサービスを置き、サービスごとにロードバランサーを置く

## 決定

採用：「文脈ごとに Fargate 上の ECS のサービスを置き、API は非公開にしてサービスどうしが ECS Service Connect で呼び、Web フロントエンドにだけ公開のロードバランサーを1つ置く」。サーバーもクラスターも運用せずに文脈を単独でデプロイでき、各 API には AWS でも Docker Compose と同じアドレスを与えられるからである。しかも、Terraform の AWS provider にいまあるリソースだけで組める。

決まりは次のとおりである。

- 文脈はそれぞれ、API があれば、それを Fargate 上の ECS のサービス `<context>` として動かす。ワーカー（送信箱の中継や、キューからイベントを受け取るプロセスのように、リクエストに答えないプロセス。TPL-0013）は、その文脈のイメージから、独立した ECS のサービス `<context>-<worker>` として動かす。Notification のワーカーは、サービス `notification-worker` である。1つの文脈のサービスは別々にスケールし、別々にデプロイされる。ワーカーはポートを公開しないので、リクエストの入口を持たない。
- ワーカーは、その文脈のコマンドのモードである。同じバイナリが、モードの名前を引数に受け取ると、そのモードを動かす。たとえば `reservation relay` である。Notification のように API のない文脈では、コマンドそのものがワーカーである（`notification`）。
- どのプロセスも、ワーカーも含めて、`GET /healthz` に答える（`httpserver.RunWorker`）。そのため、イメージのヘルスチェックのコマンド `<command> healthcheck` は、どのプロセスも同じ方法で見張れる。ワーカーのヘルスチェックが示すのは、プロセスが動いていることだけである。データベースやブローカーに届かないワーカーは、正常のまま試し直す。再起動しても、それらが戻るわけではないからである。
- サービスは、設定を秘密情報も含めて環境変数から読む（`platform/config`）。たとえば、`DATABASE_URL` の中のパスワードである。AWS では、タスク定義がその秘密情報を Secrets Manager から埋めるので、コードが秘密情報を読むために AWS の API を呼ぶことはない。
- 文脈はそれぞれ自分のコンテナイメージを持ち、イメージは `backend/cmd/<context>/` からビルドする。Go のモジュールは1つのままにする。
- イメージのタグは、そのイメージの元になるファイルのハッシュである（`tools/scripts/images.sh`）。文脈はほかの文脈のものを何も import しないので（`make lint-arch`）、文脈の元になるファイルは、そのコマンド、自分のパッケージ、platform のパッケージ、モジュールのファイルで尽きる。そのため、1つの文脈を変えると、その文脈のタスク定義だけが変わり、デプロイは変わった文脈だけを再起動する。
- デプロイのジョブは、イメージを `linux/amd64` 向けに、環境ごとに1回、同じコミットからビルドする。1つのイメージをダイジェストで stg から prd へ昇格させる方法もあるが、作っていない。
- 文脈はそれぞれ Terragrunt のユニット `contexts/<context>` を持ち、その中でモジュール `context-service` を1回呼ぶ（TPL-0015）。1つの文脈のサービスは、タスク実行ロールとタスクロールを1つずつ共有する。タスク実行ロールは ECS がタスクを起動するときに使い、タスクロールはプロセスが AWS を呼ぶときに使う。タスクロールが持つのは、その文脈が呼ぶものだけである。たとえば Notification のタスクロールは、環境の ID に対する `ses:SendEmail` を持つ。
- タスクが正常にならないデプロイは止まる。そのとき ECS は、サービスを最後にうまくいったデプロイの状態へ戻す（デプロイのサーキットブレーカー）。
- Next.js も、Fargate 上の ECS で、専用のイメージ（`frontend/Dockerfile`）から動かす。
- 文脈の API を呼ぶのは、Next.js のサーバーだけである。ブラウザーは Next.js とだけ通信するので、どの API にも CORS は要らず、API のアドレスがブラウザーに届くこともない。API のクライアントは、`server-only` を import する `frontend/src/lib/api/server/clients.ts` にある。サーバーは、各 API のベース URL を環境変数（`FACILITY_API_URL`、`RESERVATION_API_URL`）から読む。そのため、1つのイメージがどの環境でも動く。
- フロントエンドのヘルスチェック `GET /healthz` は、API を呼ばない。文脈のヘルスチェックがほかのサービスを呼ばないのと同じである。止まっている文脈があるからといって、プラットフォームがフロントエンドを再起動してはならない。このヘルスチェックは、204 ではなく、本文を付けた 200 で答える。Next.js がその答えをビルドの時点で描くからである。イメージにシェルがないので、このチェックは Docker Compose でも ECS でも Node が実行する（`frontend/healthcheck.mjs`）。
- 文脈の API は非公開である。文脈も Next.js のサーバーも、API を ECS Service Connect を通して `http://<context>:8080` で呼ぶ。Docker Compose の中と同じアドレスである。どのサービスも環境の名前空間のクライアントであり、API のサービスは文脈の名前で呼ばれる側にもなる。どの API にもロードバランサーとパブリックアドレスはなく、モジュール `context-service` には、そのどちらかを与えられる入力がない。
- 公開するのは Web フロントエンドだけである。モジュール `web` が公開サブネットに置く1つのロードバランサーが HTTPS で応え、Next.js のタスクに転送する。タスクは、そのロードバランサーからのリクエストだけを受け付ける。
- サービスのネットワークモードは、Fargate が必要とする `awsvpc` にする。
- Notification は、タスクロールを使って Amazon SES でメールを送る。SMTP を話すのは手元の環境だけで、相手は Mailpit である（TPL-0017）。

タスクは、インターネットではなく VPC エンドポイント（AWS PrivateLink）を通して AWS に届く。

- 既定では、タスクの置かれる非公開サブネットにインターネットへの経路はない。Amazon S3 にはゲートウェイエンドポイントを置く。インターフェイスエンドポイントは、次のサービスにそれぞれ1つ置く。`ecr.api`・`ecr.dkr`・`logs`・`secretsmanager`・`ecs-agent`（Service Connect のプロキシが使う）・`events`・`sqs`・`email`（Amazon SES の API）である。
- そのため、セキュリティグループのどのルールも、VPC の外のアドレス範囲を名指ししない。タスクが VPC の外へ送れるのは、エンドポイントのセキュリティグループと Amazon S3 のプレフィックスリストへの HTTPS だけである。
- Amazon ECS のドキュメントは、NAT ゲートウェイを AWS のサービスに届くいちばん簡単な方法だと説明し、その代償として、NAT ゲートウェイではタスクの通信先を絞れないことを挙げている。AWS Well-Architected Framework のセキュリティの柱は、マネージドサービスに届く既定の方法として VPC エンドポイントを勧めている。また Trivy は、`0.0.0.0/0` への送信を重大と評価する（AWS-0104、TPL-0024）。テンプレートは AWS の勧めに従う。
- AWS の外のサービスを呼ぶ文脈のために、NAT ゲートウェイはモジュール `network` の選択肢（`nat_gateways`）として残す。

この決定は2つの点で最初の計画と違う。

- 最初の計画では、どの文脈にも API があり、その隣にワーカーがあった。Notification には API がないので、そのコマンドがワーカーである。
- 最初の計画では、API を非公開の ECS Gateway の後ろに、Next.js を公開の ECS Gateway の後ろに置いていた。インフラのマイルストーンは、ECS Gateway を見送った。AWS provider ではゲートウェイを作れず、ゲートウェイがサービスに与えるアドレスを Terraform が読めず、このリポジトリのどのチェックでもゲートウェイを試せなかったからである（下の[ECS Gateway](#文脈ごとに-fargate-上の-ecs-のサービスを置き入口を-ecs-gateway-にする)を参照）。

### 結果

- 良い点：文脈ごとにデプロイ・スケール・障害が分かれる。デプロイが再起動するのは、イメージの変わった文脈だけである。
- 良い点：実行時にも境界が守られる。文脈は別々のプロセスなので、ほかの文脈に届く手段はその API とイベントだけである。
- 良い点：API のアドレスは、`http://facility:8080` のように、AWS でも Docker Compose でも同じである。そのため、`FACILITY_API_URL` のように API を指す設定は、どちらでも同じである。
- 良い点：この決定のリソースはすべて Terraform の AWS provider にある。そのため Terraform がすべてのアドレスをつなぎ、そのテスト、全ユニットの検証、AWS Emulator でのリハーサルが、アカウントなしでコードを確かめる（TPL-0015、TPL-0017）。
- 良い点：どの API にも VPC の外からは届かず、タスクのセキュリティグループは VPC の外のアドレス範囲を名指ししない。
- 悪い点：1つのデプロイ単位にする場合よりサービスが増える。イメージ・タスク定義・ログ・アラームが増え、サービスごとに最低限の費用もかかる。Fargate のタスクは、何もしていなくても動いている間は課金されるからである。
- 悪い点：VPC の中のタスクどうしの通信は、暗号化しない HTTP である。Service Connect は AWS Private CA の TLS で暗号化できるが、それは設定していない。
- 悪い点：ただ1つの公開の入口のロードバランサーは、リスナー、ターゲットグループ、証明書、DNS レコードとともに、モジュール `web` に手で書いてある。ECS Gateway なら、これらを用意してくれたはずである。
- 悪い点：Service Connect のプロキシはどのタスクでも動き、タスクの CPU とメモリを分け合う。
- 悪い点：インターフェイスエンドポイントはゾーンごとに時間単位で課金され、小さな環境では NAT ゲートウェイ1つより高くつく。stg はエンドポイントごとのネットワークインターフェイスを1つにしている（`interface_endpoints_in_every_zone = false`）。費用は下がるが、そのゾーンとともに使えなくなる。prd は、どのゾーンにも1つずつ置く。
- 悪い点：タスクが届くのは、エンドポイントのある AWS のサービスだけである。タスクが新しいサービスを呼ぶなら `interface_endpoints` に1つ足す必要があり、AWS の外のサービスを呼ぶなら、NAT ゲートウェイと、その文脈のセキュリティグループのルールが要る。
- 悪い点：文脈どうしの呼び出しはネットワークを越える。1つのプロセスの中の呼び出しにはない遅延と失敗が加わる。
- 悪い点：AWS ではまだ何も動かしていない。タスクがエンドポイントを通してイメージを取得すること、シークレットを読むこと、ほかの文脈に名前で届くことは、ある環境への最初のデプロイで確かめる（[AWS にデプロイする](../../guides/deploy.ja.md#最初の適用で確かめること)）。

### 確認の方法

- `backend/Dockerfile` は、ビルド引数 `CONTEXT` が指す文脈のイメージを `backend/cmd/<context>/` からビルドする。そのため、文脈を足しても専用の Dockerfile は要らず、Go のモジュールは1つのままである。
- `make check-all` に含まれる `make smoke` は、すべての文脈のすべてのプロセスを、Docker Compose で別々のコンテナとして動かす。プロセスは、Facility と Reservation の API、Reservation の中継（Reservation のイメージから動く `reservation relay`）、Notification のワーカーである。そして、HTTP 越しに API を使って会議室を予約し、予約のイベントから生じるメールを待つ。文脈は別々のプロセスとして動き、互いの API とイベントを通してしか相手に届かない。
- 各イメージのバイナリは、API でもワーカーでも、自分自身のヘルスチェックを行う（`<command> healthcheck`）。`context-service` のタスク定義は、このコマンドを実行する。ワーカーが動いている間ヘルスチェックに答えることは、`httpserver.RunWorker` のテストが確かめる。
- フロントエンドも自分のイメージを持つ。Docker Compose はそれをサービス `web` として動かし、`web` は Compose のネットワークを通して API に届く。AWS で Service Connect を通して届くのと同じ形である。`make e2e` はこれをブラウザーで操作し、そのテストの1つはヘルスチェックが答えることを確かめる。
- `frontend/src/**/server/` の下のモジュールが `server-only` を import していないと、`lint-frontend` が失敗する。そのモジュールを import するクライアントコンポーネントでも失敗する（`no-restricted-syntax`）。クライアントコンポーネントが `server-only` を import すると、Next.js のビルドが失敗する。
- `make check` の `lint-arch` は、ほかの文脈の import で失敗する。これによって、イメージのタグの元になるファイルが欠けずに済む。
- `infra/modules/context-service` のテスト（`make check-all` の `validate-terraform`）は、AWS provider のモックに対してモジュールを plan する。テストが確かめるのは次の4つである。サービスが非公開サブネットで動き、パブリックアドレスもロードバランサーも持たないこと。文脈のルールがセキュリティグループを名指しし、アドレス範囲を名指ししないこと。API が Service Connect を通して文脈の名前で呼ばれること。失敗したデプロイが元に戻ること。
- `make check` の `scan-config` は、インターネットに面したロードバランサーが `infra/modules/web/main.tf` 以外のファイルにあると失敗する。`.trivyignore.yaml` が指摘 AWS-0053 を認めるのは、このファイルだけである。`0.0.0.0/0` への送信を許すルールでも失敗する（AWS-0104）。
- `make check-all` の `validate-live` と `rehearse-infra` は、すべてのユニットを検証し、stg のユニットを AWS Emulator に適用する（TPL-0015、TPL-0017）。
- 公開の入口を作るのが `infra/modules/web` だけであることは、レビューで確かめる。

## 選択肢の長所と短所

### 文脈ごとに Fargate 上の ECS のサービスを置き、API は非公開にしてサービスどうしが ECS Service Connect で呼び、Web フロントエンドにだけ公開のロードバランサーを1つ置く

- 良い点：文脈を単独でデプロイでき、運用するクラスターがない。API は、置き場所とモジュールの受け付ける入力の両方によって非公開になり、Docker Compose と同じアドレスを持つ。
- 良い点：どのリソースも Terraform の AWS provider にあり、AWS Emulator もそのすべてを受け付ける。
- 悪い点：サービスごとに最低限の費用がかかり、VPC の中の通信は暗号化しない HTTP であり、ただ1つの公開の入口は手で書く。

### 文脈ごとに Fargate 上の ECS のサービスを置き、入口を ECS Gateway にする

最初に選んだのは、この選択肢である。次の事実は、2026年11月19日に確かめた。

- 良い点：ゲートウェイはマネージドな入口である。1回だけ定義し、各サービスがそこに参加する。サービスどうしは、ホスト名による振り分けと自動生成のホスト名を使ってロードバランサーを共有する。用意されるロードバランサーの料金のほかに費用はかからない。
- 悪い点：Terraform の AWS provider には、ECS Gateway のリソースがない。最新のバージョンは2026年11月11日に出た 6.73.0 であり、リソースの要望は未解決のままである（2026年10月21日に開かれた [issue 50573](https://github.com/hashicorp/terraform-provider-aws/issues/50573)）。プルリクエストは3つ（50894、50895、50896）開いているが、どれもマイルストーンがない。
- 悪い点：Terraform では、アドレスをつなげなかった。provider `awscc` には、バージョン 1.107.0 から次のものがある。`awscc_ecs_gateway`、`awscc_ecs_gateway_cluster_associations`、`awscc_ecs_service` の `gateway_connectors` である。しかし、ゲートウェイがサービスに与える URL `https://<random id>.ecs.<region>.on.aws` は、この provider も CloudFormation も出力しない。URL を返すのは ECS の API（`describe-service-revisions`、`describe-gateway-route`）だけであり、削除して作り直したサービスは別の URL になる。そのため Terraform は、Facility のアドレスを Reservation に渡せず、2つの API のアドレスを Next.js に渡すこともできなかった。
- 悪い点：カスタムドメイン名への対応がドキュメントに書かれていない。そのため、Next.js の公開の入口にチーム自身のドメイン名を付けられることを示せなかった。
- 悪い点：AWS Emulator は `CreateGateway` に "scaffolded but not implemented" と答える。そのため、このリポジトリのどのチェックもゲートウェイを適用できなかった。
- 悪い点：新しい製品である。公開は2026年10月20日であり、本番での限界はまだわかっていない。

### 全部の文脈を1つのデプロイ単位にする（モジュラーモノリス）

- 良い点：イメージもサービスもデプロイも1つで済み、いちばん安く単純に運用できる。文脈どうしの呼び出しも、プロセスの中にとどめられる。
- 悪い点：どのデプロイでも全部の文脈を出すことになる。ある文脈のリリースに不具合があれば全部の文脈を戻すことになり、文脈ごとのスケールもできない。
- 悪い点：文脈が独立していることを、実行時に示すものがない。共有メモリや共有の接続プールを通る近道は、足すのは簡単で、見つけるのは難しい。

### Lambda と API Gateway

- 良い点：使っていない間は費用がかからず、管理するサーバーもなく、リクエストに合わせてスケールする。
- 悪い点：関数のインスタンスはそれぞれデータベースへの接続を開く。インスタンスが一斉に増えると、PostgreSQL の接続を使い切りうる。よくある対策の RDS Proxy を入れると、Aurora Serverless v2 のクラスターが一時停止しなくなる（TPL-0016）。
- 悪い点：コードも手元の環境も、Lambda の実行環境とそのイベントを前提とした形になる。ECS を選べば、同じ Go のサーバーを、ECS でも Docker Compose でもそのまま動かせる。

### Kubernetes（Amazon EKS）

- 良い点：もっとも移植性と柔軟性が高く、エコシステムも最大である。
- 悪い点：EKS のクラスターには、動かすキャパシティとは別に、コントロールプレーンの時間あたりの料金がかかる。
- 悪い点：Kubernetes は、バージョンアップ・アドオン・マニフェストなどの技能と手入れを必要とする。小さなチーム向けのテンプレートが求めてよい範囲を大きく超える。

### 文脈ごとに ECS のサービスを置き、サービスごとにロードバランサーを置く

- 良い点：ECS のサービスを公開する方法として長い実績があり、ドキュメントも例も多い。
- 悪い点：サービスごとに、ロードバランサーかリスナーのルール、ターゲットグループ、セキュリティグループ、DNS を繰り返し作る。ロードバランサーは時間単位で課金される。
- 悪い点：API には VPC の外からの入口が要らないので、API ごとのロードバランサーは使い道のないインフラになる。代わりに、Service Connect が VPC の中で API に名前を与える。

## 補足

2026年11月時点で、Amazon ECS Gateway について[ドキュメント](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/gateway-connect-service.html)からわかることは次のとおりである。

- 2026年10月20日に公開された。
- マネージドな入口である。ゲートウェイを1回だけ定義し、各サービスがそこに参加する。
- 用意されるロードバランサーの料金のほかに、追加の費用はかからない。
- サービスどうしは、ホスト名による振り分けと自動生成のホスト名を使って、ロードバランサーを共有する。
- ネットワークモード `awsvpc` が必要である。
- ECS Express Mode のサービスはつなげない。
- カスタムドメイン名への対応は、ドキュメントに書かれていない。

Terraform の AWS provider が ECS Gateway のリソースを持ち、ゲートウェイがサービスに与える URL を Terraform が読めるようになったら、この決定を見直す。

まだ確かめていないこと：Amazon SES の API のエンドポイントのサービス名 `email`。Amazon SES のドキュメントは、エンドポイントのサービスを "email" で絞り込むように書いているだけで、名前をそのままの形では書いていない。AWS Emulator もこの名前を知らないので、リハーサルはこのエンドポイントを除く。ある環境への最初のデプロイで確かめる。

- モジュールは `infra/modules/network`・`platform`・`context-service`・`web` で、それぞれに README がある。
- [AWS にデプロイする](../../guides/deploy.ja.md)は、アカウントの準備とデプロイの流れを説明する。
