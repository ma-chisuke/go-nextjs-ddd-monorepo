# TPL-0004: クリーンアーキテクチャを採り、ドメイン層では I/O を扱わない

## 背景と課題

中核の区切られた文脈（TPL-0003）には、製品の存在理由であるルールが入る。
これらのルールは業務の都合で変わるものであり、読みやすく、テストしやすくなければならない。

業務のルールがデータベースを呼んだり、時計を読んだり、ログを書いたりすると、テストも読解も難しくなる。
ルールを1つテストするのに、データベース、時刻を固定する手段、ロガーが要る。読み手は、ルールとそのまわりの配管を自分で切り分けなければならない。
技術の変更（新しいデータベースのドライバーや HTTP のライブラリなど）も、ルールにまで及ぶ。

扱いに注意が要るのは、時刻と乱数である。
`time.Now` を呼ぶルールは実行のたびに違う答えを返し、テストで答えを固定するには、グローバルな何かを差し替えるしかない。
乱数で ID を自分で作るルールも同じである。

中核の文脈の中で、どのコードがどのコードに依存してよいか。そして、I/O はどこで扱うか。

## 判断の基準

- 業務のルールを、ただの関数呼び出しとしてテストできる。データベースもネットワークも、偽の時計も要らない。
- ドメインのコードは、通信や保存の言葉ではなく、業務の言葉で書かれる。
- 依存の向きが一方向で、その向きをプログラムで検査できる。
- 構成は Go としてふつうの形である。小さなインターフェースを、それを使う側のコードが宣言する。

## 検討した選択肢

- クリーンアーキテクチャ。ポートはアプリケーション層に置き、ドメインでは I/O を扱わない
- クリーンアーキテクチャ。ポートはドメイン層に置く
- ドメインのオブジェクトが永続化に依存するレイヤードアーキテクチャ
- 層を分けない

## 決定

採用：「クリーンアーキテクチャ。ポートはアプリケーション層に置き、ドメインでは I/O を扱わない」。ドメインのコードが動くのに外から何も要らない選択肢はこれだけであり、しかも Go では、インターフェースをそれを使うコードの隣で宣言するのがふつうだからである。

中核の文脈は、次の構成にする。

```text
backend/internal/<context>/
├── module.go         各層を組み立てる。cmd/<context> だけが使う
└── internal/
    ├── domain/       集約・値オブジェクト・ドメインイベント・業務エラー
    ├── app/          ユースケース（1業務操作1ファイル）とポート
    └── adapter/
        ├── http/     生成した strict server の実装（TPL-0006）
        ├── postgres/ スキーマ・クエリ・リポジトリ（TPL-0010、TPL-0011）
        └── event/    送信箱への書き込みと、他の文脈のイベントの受信（TPL-0013）
```

- 依存は内側を向く。`adapter` は `app` と `domain` を import し、`app` は `domain` を import する。`domain` はどちらも import しない。
- ドメインは、`context.Context`・時計（`time.Now`）・乱数・データベース・HTTP・ファイルシステム・ログを使わない。値を受け取り、値・ドメインイベント・業務エラーを返す。
- ユースケースは、現在時刻と新しい ID をポートから得て、ドメインに引数で渡す。
- ポートは `app` に置くインターフェースである。リポジトリ、時計、ID の生成器、他の文脈のクライアント（TPL-0005）がこれにあたる。アダプターがこれらを実装する。
- `module.go` は、アダプター・ユースケース・HTTP のハンドラーを組み立てる。これを import するのは `cmd/<context>` だけである。
- 補完の文脈には `domain` の層がない。そのユースケースは、生成したクエリを直接呼ぶ（TPL-0003）。

### 結果

- 良い点：ドメインのテストは、値を作り、関数を呼び、結果を比べるだけである。モックは要らない。
- 良い点：時刻に依存するルールは時刻を引数で受け取るので、各テストは、どの時点を確かめるのかを明示する。
- 良い点：データベース・HTTP のライブラリ・メッセージブローカーを、ドメインを変えずに取り替えられる。
- 悪い点：境界ごとにデータを詰め替える。生成した HTTP の型からドメインへ、ドメインから sqlc が読み書きする行へ、である。詰め替えのコードは書く手間がかかり、両側の変更に合わせて直し続ける必要もある。
- 悪い点：現在時刻と新しい ID がユースケースごとに引数として渡っていくので、関数のシグネチャが長くなる。
- 悪い点：ドメインは、必要になった時点でデータを読み込めない。集約の外のデータを要するルールは、そのデータをユースケースから受け取る。ユースケースが先に読み込んでおく。
- 悪い点：補完の文脈は別の構成をとるので、ある文脈の構成から次の文脈の構成を予測できない（TPL-0003）。

### 確認の方法

層を守るチェックは、まだない。最初の文脈とともに加わる（マイルストーン M1）。
`.golangci.yml` はすでに depguard と forbidigo を有効にしているが、そのルールはすべての Go のファイルに当てはまるものだけである。層のためのルールは最初の文脈とともに加える、と同じファイルに書いてある。

そのとき加わるチェックは次のとおりである。

- import のルール（depguard か go-arch-lint。どちらにするかはルールを書くときに決める）。ドメインが import できるのは、自分のパッケージと、標準ライブラリのうち許可リストに載せたパッケージだけである。許可リストには、`context`・`database/sql`・`net/http`・`os`・`log/slog`・乱数のパッケージを載せない。`app` は `adapter` を import しない。`module.go` のパッケージを import できるのは、`cmd/<context>` だけである。
- forbidigo：ドメインでは、時計を読む関数（`time.Now` や `time.Since` など）を呼ばない。`time.Time` という型のために `time` パッケージは許可リストに残るので、import のルールだけではこれらの呼び出しを見つけられない。
- Go の `internal` ディレクトリ：`backend/internal/<context>/` の外から `backend/internal/<context>/internal/...` を import すると、コンパイラーが拒む。

## 選択肢の長所と短所

### クリーンアーキテクチャ。ポートはアプリケーション層に置き、ドメインでは I/O を扱わない

- 良い点：ドメインには偽物に差し替えるべきインターフェースがないので、そのテストはただの関数呼び出しになる。
- 良い点：ポートは、それを呼ぶユースケースの隣にある。
- 悪い点：Java や C# の DDD の構成を見慣れた読み手は、リポジトリのインターフェースがドメインにあると考え、まずそこを探す。

### クリーンアーキテクチャ。ポートはドメイン層に置く

- 良い点：多くの DDD の本の構成と一致する。そこでは、ドメインが集約ごとのリポジトリを宣言する。
- 悪い点：リポジトリのメソッドは `context.Context` を受け取り、保存先のエラーを返す。そのため、ドメインがそのメソッドを一度も呼ばないとしても、ドメインのシグネチャには I/O が入り込む。
- 悪い点：ドメインのコードからリポジトリを呼べてしまう。「ドメインでは I/O を扱わない」という決まりを守る手段が、レビューだけになる。

### ドメインのオブジェクトが永続化に依存するレイヤードアーキテクチャ

- 良い点：コードが少ない。アクティブレコードや ORM のエンティティがルールを持ち、自分で自分を読み込み、保存するので、詰め替えが要らない。
- 悪い点：ルールのテストに、データベースか、永続化のライブラリの偽物が要る。
- 悪い点：テーブルの形がモデルの形を決め、どちらかを変えると、もう一方にも及ぶ。

### 層を分けない

- 良い点：リクエストを読み、ルールを当てはめ、行を書くハンドラーが、いちばん短いコードである。
- 悪い点：ルールがハンドラーに散らばり、解析や SQL と混ざる。テストは HTTP を通してしかできない。
- 悪い点：層のないコードでは、依存の向きをプログラムで検査しようがない。
