# TPL-0025: 依存と道具の更新を Renovate に任せる

## 背景と課題

このリポジトリでは、すべてを固定している。道具のバージョンは `mise.toml` で、パッケージはロックファイルで、アクションはコミット SHA で固定する。のちには、コンテナイメージをダイジェストで、Terraform の provider をバージョンで固定する（TPL-0022・TPL-0024）。
固定すれば、どのマシンも同じコードを動かす。ただし、固定したものがひとりでに新しくなることはない。
誰も更新しない固定は既知の脆弱性を抱えたままになり、何か月も先送りした更新は移行作業に変わる。

固定は多くの形式にまたがっている。Go のモジュール・npm のパッケージ・Python のパッケージ・Docker のイメージ・アクション・`mise.toml` の道具・Terraform の provider である。
これらを手で更新する作業を、期限どおりにこなす人はいない。一部の形式しか扱えない更新の道具を使えば、残りの形式が取り残される。

どうすれば、更新を負担や危険にせず、すべての固定を新しく保てるか。

## 判断の基準

- 1つの更新の道具が、`mise.toml` を含むすべての種類の固定を扱う。
- 更新はプルリクエストとして届き、ほかの変更と同じようにチェックで検証される。
- 更新は、pnpm や uv と同じく、リリースから3日待つ（TPL-0024）。
- 決まりきった更新には人が要らず、危険な更新には人が要る。
- プルリクエストの数を、レビューできる程度に抑える。

## 検討した選択肢

- すべての更新に Renovate を使い、Dependabot は警告だけに使う
- Dependabot のバージョン更新
- 手作業での更新
- Renovate と Dependabot のバージョン更新の両方

## 決定

採用：「すべての更新に Renovate を使い、Dependabot は警告だけに使う」。Renovate は `mise.toml` を含め、このリポジトリのすべての種類の固定を扱えるが、Dependabot のバージョン更新は扱えないからである。

決まりは次のとおりである。

- Renovate は、Go のモジュール・npm のパッケージ・Python のパッケージ・Docker のイメージのダイジェスト・アクションの SHA・`mise.toml` の道具・Terraform の provider を更新する。
- 環境の provider は `infra/live/providers.hcl` で固定し、Renovate の Terraform のマネージャーがそれを読む（`renovate.json` の `terraform`）。グループ `Terraform providers` は、同じ provider を使う `infra/local/` のものと一緒にそれらを動かす。Renovate は `infra/live/providers.lock.hcl` を書かない。そこで、`mise.lock` のための `make tools-lock` と同じく、人が更新のブランチで `make infra-lock` を実行する。それまでは、そのブランチの Terragrunt の実行はどれも失敗する。
- リリースから3日待ってから、そのリリースを提案する。
- 関連する更新は1つのプルリクエストにまとめる。
- プルリクエストは週1回の予定に沿って開く。セキュリティの修正は、この予定を待たない。
- patch・ダイジェスト・固定の更新は、必須チェックが通れば自分でマージする。minor と major の更新は人を待つ。
- 更新は固定やロックファイルを変えるので、そのプルリクエストのチェックは、変更のあったファイルだけでなく、すべてのファイルを対象にする（TPL-0023）。道具の新しいバージョンは、更新がマージされる前にリポジトリ全体で動く。
- Dependabot は警告のためだけに有効にしておき、プルリクエストは開かせない。
- 設定は `renovate.json` に書く。

### 結果

- 良い点：どの固定も、チェックで検証されるプルリクエストという同じ方法で更新される。
- 良い点：patch の更新には人が要らないので、人がレビューするのは、何かを壊す見込みの高い更新だけになる。
- 良い点：Renovate は pnpm や uv と同じ期間だけ待つので、それらがインストールを拒むリリースを提案しない。
- 悪い点：プルリクエストは途切れずに届く。まとめて週1回にしても、毎週レビューの時間を取られる。
- 悪い点：自動のマージは、チェックと同じ程度にしか安全でない。テストがカバーしていない振る舞いを壊す patch のリリースは、人を通さずにマージされる。
- 悪い点：Renovate のアプリは、ブランチをプッシュしてプルリクエストを開くために、リポジトリへの書き込みの権限を必要とする。信頼する相手が1つ増える。
- 悪い点：設定を誤ると、ある種類の固定の更新が知らないうちに止まることがある。スキーマではそれを見分けられない。
- 悪い点：Renovate のどのマネージャーも読まない固定は、更新されない。`infra/local/aws-emulator/Dockerfile` のビルド引数にある、AWS Emulator のバージョンとそのパッケージのチェックサムがそれにあたり、人が手で更新する（TPL-0017）。`frontend/Dockerfile` の `ADD` にある、pnpm のバージョンとそのパッケージのチェックサムもそうである。`renovate.json` のグループ `pnpm` は `mise.toml`・`package.json`・`pnpm-lock.yaml` を動かし、人が同じプルリクエストで Dockerfile を変える（TPL-0024）。`db/Dockerfile` にある、pgschema のバージョンとそのバイナリのチェックサムが3つ目である。Renovate が `mise.toml` の pgschema を動かしたら、人が Dockerfile を変える。両者がそろうまで、`make test-db-image` は失敗する。
- 悪い点：provider の更新には、人が `make infra-lock` を実行する必要がある。そのため、この更新がひとりでにマージされることはない。

### 確認の方法

- `make check` は、check-jsonschema に同梱された Renovate のスキーマで `renovate.json` を検証する（ターゲット `lint-schema`）。ネットワークは使わない。
- スキーマで捕まえられるのは形の崩れた設定であり、中身の誤った設定は捕まえられない。Renovate がすべての種類の固定を扱っていることは、Renovate の開くプルリクエストのレビューで確かめる。
- Dependabot alerts と自動のマージはリポジトリの設定であり、`make github-settings` がこれらを有効にする（`docs/guides/github-settings.md`）。Renovate のアプリは、ガイドのとおり手で入れる。

## 選択肢の長所と短所

### すべての更新に Renovate を使い、Dependabot は警告だけに使う

- 良い点：1つの道具・1つの設定・1つの形のプルリクエストで、すべての固定を扱える。
- 良い点：待つ期間・まとめ方・予定・自動のマージを、設定で制御できる。
- 悪い点：リポジトリへの書き込みの権限を持つ、サードパーティーのアプリである。

### Dependabot のバージョン更新

- 良い点：GitHub に組み込まれており、入れるアプリがない。
- 悪い点：`mise.toml` を更新しないので、道具の固定には別の仕組みが要る。
- 悪い点：自分ではマージしない。自動でマージするには、別にワークフローが要る。

### 手作業での更新

- 良い点：人を通さずに変わるものがない。
- 悪い点：誰かが思い出したときにしか更新しないので、固定はしだいに古くなる。セキュリティの修正も、誰かが気づくまで入らない。

### Renovate と Dependabot のバージョン更新の両方

- 良い点：一方の更新の道具が止まっても、もう一方が更新を提案し続ける。
- 悪い点：同じパッケージについて両方がプルリクエストを開くので、通知が2倍になり、2つの道具が競い合う。

## 補足

- [Renovate のドキュメント](https://docs.renovatebot.com/)
- 固定については TPL-0022 に、3日の待ちについては TPL-0024 に書いてある。
