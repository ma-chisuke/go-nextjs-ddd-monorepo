# TPL-0019: テンプレートのライセンスを MIT-0 にする

## 背景と課題

テンプレートは、コピーされて利用者自身の製品になる。利用者は名前を変え、中身の大半を書き換えて出荷する。
したがって、テンプレートのライセンスが効いてくるのは、テンプレートそのものよりも、そこから始まるすべての製品に対してである。

寛容なライセンスとして普通に選ばれる MIT License は、これをすべて認める。ただし条件が1つある。著作権表示と許諾表示を、ソフトウェアのすべての複製または重要な部分に含めることである。
テンプレートの場合、この条件はコードと一緒に、そこから作ったすべての製品へ付いていく。製品がテンプレートの面影をなくしたあとも、条件は残る。
実際には、利用者はテンプレートの名残を消すときに、この表示も一緒に消す。すると、その製品は、誰も気づかないままライセンスに違反する。

ほとんどのチームが守れない条件を付けずに、チームがテンプレートを自分のものにできるライセンスはどれか。

## 判断の基準

- チームがテンプレートの作者の表示を残さずに、テンプレートを使い、変え、出荷できる。
- 法務の担当者とライセンスのスキャナーが、そのライセンスを判別できる。つまり、OSI が承認し、SPDX の識別子を持つライセンスである。
- 読み手がライセンスの許す範囲をすぐに読み取れるよう、文面が見慣れたものである。
- どの国でも同じように効く。

## 検討した選択肢

- MIT-0（MIT No Attribution）
- MIT
- Apache-2.0
- パブリックドメインへの献呈（CC0-1.0 または Unlicense）
- 0BSD

## 決定

採用：「MIT-0」。MIT License から条件を除いたものなので、チームが必要とする自由を、読み手がすでに知っている文面で与えられるからである。
AWS も、サンプルコードを同じ理由で MIT-0 にしている。利用者がサンプルを自分のコードに写すからである。

決まりは次のとおりである。

- `LICENSE` には MIT-0 の本文を置き、`package.json` には `"license": "MIT-0"` と書く。
- 利用者がコピーするものには、2種類のライセンスの依存を含めない。強いコピーレフトのライセンス（GPL・AGPL）と、ソースは公開していても利用を制限するライセンス（SSPL・BUSL・Commons Clause・NonCommercial の付いた Creative Commons）である。`trivy.yaml` は、これらのライセンスを禁止として並べている。
- リポジトリに置いた第三者のファイルは、それぞれのライセンスのままにし、ライセンスをファイルの中か隣に書く。`.vale/styles/Google/` にある Vale 用の Google のスタイルは MIT License である。`.claude/skills/japanese-tech-writing/` にある日本語の文章規範は Unlicense である。

### 結果

- 良い点：チームは製品からテンプレートの痕跡をすべて消しても、ライセンスに従ったままでいられる。
- 良い点：MIT-0 は OSI が承認しており、SPDX の識別子 `MIT-0` を持つ。そのため、スキャナーも法務の担当者もこのライセンスを判別できる。
- 悪い点：MIT-0 には、MIT と同じく特許の許諾がない。Apache-2.0 にはある。
- 悪い点：禁止したライセンスの依存がどうしても要るチームは、自分の記録でこの決定を置き換え、`trivy.yaml` を変える必要がある。
- 悪い点：別のライセンスのファイルは例外であり、チームはそれに気づく必要がある。それらのファイルを残すなら、その表示も残すことになる。

### 確認の方法

- `LICENSE` と `package.json` が MIT-0 を指していることは、レビューで確かめる。
- `make check-all` はターゲット `scan-deps` を実行する。`scan-deps` は、`trivy.yaml` が禁止するライセンスの依存を Trivy が見つけると失敗する。指摘にはこの記録が書かれる（`tools/trivy/findings.tpl`）。
- `trivy.yaml` は `license.full: false` を設定している。そのため、Trivy が読むのは各パッケージが宣言したライセンスであり、各ファイルのライセンスの本文は読まない。手でリポジトリにコピーしたファイルは Trivy の対象外なので、そのライセンスがファイルの中か隣に書かれていることをレビューで確かめる。

## 選択肢の長所と短所

### MIT-0

- 良い点：テンプレートの利用者が破ることになる MIT の条件を、ちょうどその1つだけ除いている。
- 良い点：本文は MIT から条件を除いたものなので、MIT を知っている読み手はすぐに読める。
- 悪い点：MIT ほどには知られておらず、調べる読み手もいる。
- 悪い点：特許の許諾がない。

### MIT

- 良い点：寛容なライセンスの中で最も広く知られている。
- 悪い点：テンプレートから作ったすべての製品が、テンプレートの著作権表示を残す必要がある。テンプレートの名残を消すチームの多くは、この表示も消してしまう。

### Apache-2.0

- 良い点：貢献者の特許を許諾し、その特許をめぐって訴えた者からは許諾を取り上げる。
- 悪い点：条件は MIT より少ないどころか多い。複製にはライセンスを含め、表示を残し、変えたファイルに印を付け、`NOTICE` ファイルがあればそれも付ける必要がある。

### パブリックドメインへの献呈

- 良い点：何も求めない。
- 悪い点：パブリックドメインの扱いは国によって違い、それぞれの文面が独自の言葉でこれに対処している（CC0-1.0 は代わりのライセンスを用意している）。法務の担当者は、これらの文面を MIT ほどには知らない。
- 悪い点：CC0-1.0 は特許の権利を許諾しないと明記しており、OSI の承認も受けていない。

### 0BSD

- 良い点：これも表示の条件がなく、OSI が承認している。
- 悪い点：名前からは BSD のライセンスに見えるが、本文は ISC License から来ている。MIT-0 なら、ほとんどの読み手が知っている文面のままである。

## 補足

- [SPDX License List の MIT-0](https://spdx.org/licenses/MIT-0.html)
- [AWS が公開している MIT-0](https://github.com/aws/mit-0)
- ライセンスのスキャンと、そのほかのサプライチェーンの守りは TPL-0024 にある。
