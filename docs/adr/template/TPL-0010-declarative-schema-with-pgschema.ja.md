# TPL-0010: スキーマを pgschema で宣言的に管理する

## 背景と課題

文脈はそれぞれ PostgreSQL のスキーマを1つ持ち（TPL-0009）、そのスキーマは文脈の成長に合わせて変わっていく。

スキーマを変えるよくある方法は、マイグレーションのファイルを順に並べ、1つのファイルに1段階ぶんの DDL を書くやり方である。
この方法では、テーブルのいまの形がどこにも書かれない。それを知るには、並んだファイルを頭の中で順に適用するか、データベースを開くしかない。
エージェントも同じ問題を抱えており、しかも変更の多くを書くのはエージェントである。

テンプレートが求めるのは、その逆である。
文脈のいまのスキーマを1つのファイルに書き、人もエージェントもそのファイルを読み、変え、レビューする。データベースをその状態にするための DDL は、道具が求める。
クエリの生成器も同じファイルを読む（TPL-0011）。そのため、クエリは実際に動いているスキーマに照らして検査される。

スキーマの変更は、よく使われるテーブルをロックしたり、データを消したりしうる。そのため、実行する前に、正確な DDL を人とリンターで確かめられるようにしておく必要がある。

各文脈のスキーマをどう書き表し、データベースをどうやってそれに合わせればよいか。

## 判断の基準

- 文脈のいまのスキーマを、データベースなしに1つのファイルで読める。
- 変更の DDL を実行する前に見てレビューでき、リンターで検査できる。
- 文脈はスキーマを1つ持つので（TPL-0009）、道具は PostgreSQL のスキーマを1つずつ扱える。
- テンプレートはコピーした誰にとっても動く必要があるので、道具はオープンソースで、アカウントを要しない。
- クエリの生成器が同じファイルを読める（TPL-0011）。

## 検討した選択肢

- pgschema：あるべき状態を SQL で書き、plan と apply で反映する
- バージョン付きのマイグレーション（golang-migrate・goose・Flyway）
- Atlas を宣言的に使う
- sqldef
- ORM の自動マイグレーション

## 決定

採用：「pgschema：あるべき状態を SQL で書き、plan と apply で反映する」。文脈のあるべきスキーマを1つのファイルの素の SQL で持ち、変更ごとの DDL を plan として示し、アカウントなしにスキーマを1つずつ扱えるからである。

決まりは次のとおりである。

- 文脈のあるべきスキーマは `backend/internal/<context>/internal/adapter/postgres/schema.sql` に書く。このファイルには、その文脈のスキーマのテーブル・インデックス・制約・コメントを書き、スキーマの外のものは書かない。
- `pgschema plan` はデータベースと `schema.sql` を比べ、データベースをその状態にする DDL を求める。`pgschema apply` はその DDL を実行する。どちらも、その文脈の所有者のロールで実行する（TPL-0009）。
- AWS では、データベースを準備するタスクが、デプロイのたびにすべての `schema.sql` を pgschema で適用する。適用は各文脈の所有者のロールで行い、デプロイが新しいコードを起動する前、古いコードがまだ動いているうちに行う（TPL-0016）。そのため、`schema.sql` への変更は、変更の前のコードとも後のコードとも動かなければならない。先に足し、削るのは後のデプロイにする（[スキーマを変える](../../guides/change-a-schema.ja.md)）。このタスクのイメージ `db/Dockerfile` は、`mise.toml` が固定する pgschema のリリースを持つ。
- マイグレーションの履歴ファイルは置かない。スキーマの履歴は、`schema.sql` の Git の履歴である。
- plan の DDL はすべて squawk で検査し、`schema.sql` を変えるプルリクエストでレビューする。
- スキーマ・ロール・拡張は pgschema では作らない。作るのは `db/bootstrap.sql` である（TPL-0009）。
- pgschema は、あるべき状態を検証するために作業用のスキーマを作る。その場所は、フラグ `--plan-host`・`--plan-db` などの `--plan-*` で指定した PostgreSQL のサーバーであり、pgschema が変えるのと同じサーバーである。既定では、pgschema は検証用に組み込みの PostgreSQL を実行時にダウンロードする。これは何も固定していないダウンロードであり、TPL-0024 はそれを認めない。
- pgschema は権限も管理する。そのため、文脈の `schema.sql` が、文脈の各テーブルについて実行時のロールに権限を与え、`db/bootstrap.sql` は既定の権限を設定しない。
- データを動かしたり書き換えたりする変更（バックフィルなど）は、別の明示的な手順として書き、単独でレビューする。2つのスキーマを比べるだけでは、データをどうすべきかはわからないからである。
- 名前は段階を踏んで変える。新しい列やテーブルを足し、データを写し、コードを移してから、古いほうを消す。plan は2つの状態を比べるので、`schema.sql` 上の名前の変更は削除と追加に見え、その削除でデータが失われる。

### 結果

- 良い点：文脈のスキーマの正は `schema.sql` だけであり、誰でも読める。sqlc も同じファイルを読む（TPL-0011）ので、データベースで動くスキーマと、クエリの検査に使うスキーマがずれない。
- 良い点：レビューする人は、意図（`schema.sql` の差分）と正確な DDL（plan）の両方を見られる。
- 良い点：マイグレーションのファイルが年々たまっていくことがない。スキーマを変えるプルリクエストが2つあっても、1つのファイルへの編集どうしとして統合されるので、ファイルの順番を正しく保つ手間がない。
- 悪い点：データの移行とバックフィルには、pgschema の助けがない。1つずつ書き、レビューし、別の手順として実行する。
- 悪い点：名前の変更には注意が要り、決まりに書いたとおり何回かの変更に分ける必要がある。
- 悪い点：DDL は、plan が比べるデータベースによって変わる。ある環境が main ブランチの状態からずれていると、そこで実行される DDL は、レビューした DDL と違うものになる。
- 悪い点：AWS では、新しいコードが起動する前にスキーマが変わる。古いコードが耐えられない変更（古いコードが読む列を消す変更など）は、新しいコードが動くまで、動いているサービスを壊す。そのため、そうした変更は2回のデプロイに分ける。
- 悪い点：pgschema は若い道具であり、1つの会社（Bytebase）が支援していて、コミュニティも小さい。開発が止まれば、テンプレートはほかの道具に替える必要がある。ただし `schema.sql` は素の SQL なので、道具を替えてもファイルはそのまま残せる。

### 確認の方法

`make check` のターゲット `lint-sql` は、リポジトリのすべての SQL ファイル（各文脈の `schema.sql` や `db/bootstrap.sql` など）を squawk で検査する。これらのファイルはあるべき状態を書いたものであり、マイグレーションとして実行されることはない。そのため、設定ファイル `.squawk.toml` で、稼働中のデータベースに対して実行するマイグレーションにしか意味のないルールを外している。

`make check-all` のターゲット `lint-sql-plan` は、変更ごとの DDL を検査する。手元の PostgreSQL に作業用のデータベースを作り、そこに各文脈の `schema.sql` を、ベースのコミットの時点の内容で適用する。ベースのコミットは `origin/main` とのマージベースであり、`CHECK_BASE` を設定したときはそれとのマージベースである（CI はベースブランチを設定する）。次に、変更後の `schema.sql` への plan を pgschema に求め、その plan を squawk で検査する。設定は `.squawk.plan.toml` であり、マイグレーションの実行に関わるルールを有効にしてある。plan は `.cache/sql-plan/` に残り、指摘はそこを指す。
CI は、plan をまだプルリクエストに示さない。レビュアーは、チェックを実行してから `.cache/sql-plan/` で plan を読む。
名前を変える手順の最後に古い列を削除する場合のように、ルールが禁じる変更を意図して行うこともある。そうした変更は、文脈がその SQL 文を `backend/internal/<context>/internal/adapter/postgres/schema-changes.allow` に書けば、チェックを通る。書き方は SQL 文1つにつき1行で、`<squawk のルール> | <指摘が引用するとおりの SQL 文> | <理由>` である。
この行は、レビューで人が下す判断である。理由のない行は指摘になる（`sql-plan/allowance-format`）。いまの plan のどの SQL 文にも合わない行も指摘になる（`sql-plan/unused-allowance`）ので、スキーマを次に変える変更がその行を消し、許可は積み上がらない。そうした変更に至る手順は、[スキーマを変える](../../guides/change-a-schema.ja.md)が説明している。

`make check-all` のターゲット `test-db-image` は、データベースを準備するタスクのイメージを、手元の PostgreSQL に対して2回動かす。2回目の実行がスキーマを変えたとき、またはイメージの pgschema が `mise.toml` の固定するリリースと違うときに失敗する。

## 選択肢の長所と短所

### pgschema：あるべき状態を SQL で書き、plan と apply で反映する

- 良い点：あるべきスキーマは1つのファイルの素の SQL であり、道具がなくても読める。
- 良い点：手順は、Terraform を使う人になじみのある plan と apply である。apply は、plan のあとでデータベースが変わっていないことを確かめる。
- 良い点：スキーマを1つずつ扱うので、文脈ごとに1つのスキーマという形（TPL-0009）に合う。
- 良い点：オープンソース（Apache 2.0）であり、アカウントが要らない。
- 悪い点：若く、コミュニティが小さい。
- 悪い点：plan を求めるだけでも PostgreSQL のサーバーが要る。既定では実行時にダウンロードするので、テンプレートは自分のサーバーを指定する（決まりを参照）。

### バージョン付きのマイグレーション（golang-migrate・goose・Flyway）

- 良い点：成熟しており、広く知られている。
- 良い点：各段階が明示的である。データの移行を、同じ並びの中で DDL の隣に置け、実行されるものはレビューしたものと同じである。
- 悪い点：いまのスキーマがどこにも書かれない。読む人はファイルを順にたどるか、データベースか、古くなりうるダンプを読むことになる。
- 悪い点：マイグレーションを1つずつ足す2つのプルリクエストは、きれいにマージできても、両方を実行すると衝突することがある。結果はファイルの順番で決まる。
- 悪い点：ファイルがたまり続け、まとめるのは手作業になる。

### Atlas を宣言的に使う

- 良い点：成熟しており、宣言的な方法とバージョン付きの方法の両方を備える。あるべき状態は、SQL でも独自の HCL でも書ける。
- 良い点：PostgreSQL のドライバは、どのエディションでも排他制約に対応している（2026年11月時点）。
- 悪い点：2026年11月時点で、一部の機能には Atlas のアカウントと有料の Pro プランが要る。PostgreSQL ではビュー・関数・トリガー・拡張がそうであり、マイグレーションの lint などの機能もそうである。テンプレートは、コピーした誰にとってもアカウントなしで動く必要がある。

### sqldef

- 良い点：pgschema と同じく宣言的で、素の SQL を読み、DDL を dry run で事前に示せる。本番での利用の実績も長い。
- 良い点：複数のデータベースに対応している。あるべきスキーマに名前の変更を書いておけば、列の名前を変えられる。
- 悪い点：SQL を、PostgreSQL のパーサーではなく、複数のデータベースで共用する独自のパーサーで読む。そのため、PostgreSQL の構文への対応が遅れたり、構文を受け付けなかったりしうる。

### ORM の自動マイグレーション

- 良い点：スキーマがコードに追随し、余分なファイルが要らない。
- 悪い点：テンプレートは ORM を使わない（TPL-0011）。ドメインはデータベースを知らないという決まりもある（TPL-0004）。
- 悪い点：自動マイグレーションは、レビューする DDL なしに、プログラムの起動時にデータベースを変える。しかもたいていは足すだけであり、たとえば GORM の `AutoMigrate` は、コードが使わなくなった列を消さない。

## 補足

- 最初の区切られた文脈で確かめたこと：pgschema 1.14.1 は、見本の部分的な排他制約を plan に含めて適用できる。その制約は `EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&) WHERE (status = 'confirmed')` である。適用したあとのデータベースに対する2回目の plan は空である。2026年11月時点の pgschema のドキュメントは、制約として主キー・外部キー・一意・検査を挙げており、排他制約の記載はない。
