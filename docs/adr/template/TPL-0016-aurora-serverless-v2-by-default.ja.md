# TPL-0016: Aurora は Serverless v2 を既定にし、キャパシティを環境ごとに選ぶ

## 背景と課題

すべての文脈は、PostgreSQL 18 の1つのデータベースを共有する（TPL-0009）。
AWS では、このデータベースを Amazon Aurora PostgreSQL でも Amazon RDS for PostgreSQL でも動かせる。
Aurora のキャパシティには2種類ある。大きさの決まった provisioned のインスタンスと、Aurora のキャパシティの単位（ACU）で最小値と最大値の間を伸び縮みする Serverless v2 である。

環境によって、必要なものが違う。
stg はほとんどの時間（夜、週末、テストとテストの合間）使われておらず、使われていない間の費用をできるだけ小さくしたい。
prd には予測できる性能が要る。負荷が十分に安定していれば、大きさの決まったインスタンスのほうが安くなることもある。

Serverless v2 は 0 ACU まで縮み、接続が1本もないときは一時停止できる。そのため、使われていない stg はストレージの料金しかかからない。
ただし、一時停止には固有の条件と代償がある。開いた接続が1本でもあるとデータベースは止まらず、一時停止のあとの最初の接続は、データベースが再開するまで待たされる。

環境ごとにどの種類のキャパシティを使い、一時停止するデータベースとともに動くために、コードは何をすればよいか。

## 判断の基準

- stg は、使われていない間はほとんど費用がかからない。
- prd は、モジュールを変えずに、負荷に合わせてキャパシティを選べる。
- 1つのモジュールで両方の環境をまかない、違いは値に書く（TPL-0015）。
- データベースが一時停止しても、サービスは動き続ける。接続は失敗せずに待ち、再試行する。

## 検討した選択肢

- Aurora で、Serverless v2 と provisioned のインスタンスを変数で選び、既定を Serverless v2 にする
- どの環境でも provisioned の Aurora のインスタンスを使う
- RDS for PostgreSQL
- どの環境でも Serverless v2 を使い、最小値を 0 より大きくする

## 決定

採用：「Aurora で、Serverless v2 と provisioned のインスタンスを変数で選び、既定を Serverless v2 にする」。1つのモジュールのまま、stg はほとんど費用をかけずに一時停止でき、prd は provisioned のインスタンスを選ぶ余地を残せるからである。

決まりは次のとおりである。

- `database` のモジュールは変数 `capacity` を受け取り、キャパシティの種類をちょうど1つ選ぶ。Serverless v2（最小と最大のキャパシティと、一時停止までの時間を指定する）か、1つのクラスの provisioned のインスタンスである。`instance_count` はライターにリーダーを足し、ライターが故障するとリーダーの1つが引き継ぐ。
- stg は 0〜2 ACU の Serverless v2 をインスタンス1つで使い、使われていないときは一時停止させる。
- prd は必要に応じて選ぶ。テンプレートは、安定した負荷を見込んで、クラス `db.r8g.large` の provisioned のインスタンスを2つ（ライターとリーダー）与えている。
- 開いた接続が1本でもあると、クラスターは止まらない。そのため、どのサービスの接続プールも最小の接続数を 0 にし、3分使われなかった接続を閉じる（`platform/postgres`）。
- サービスのヘルスチェックでは、データベースにクエリを出さない。数秒ごとに接続するヘルスチェックがあると、クラスターは一時停止できなくなる。
- 再開には約15秒、24時間を超えて止まっていたあとは30秒以上かかる。接続のタイムアウトはそれより長くし、失敗したら再試行する。
- RDS Proxy は使わない。RDS Proxy は各インスタンスへの接続を開いたままにするので、RDS Proxy のあるクラスターは一時停止しない。
- 論理レプリケーションも使わない。下に挙げた Aurora のドキュメントの自動の一時停止の説明は、論理レプリケーションも、クラスターが一時停止しなくなる条件の1つに挙げている。

モジュール `infra/modules/database` は、さらに次の決まりでクラスターを作る。

- ストレージ、バックアップ、スナップショットは、モジュールが作るカスタマーマネージドキーで暗号化する。このキーはローテーションする。クラスターは、環境がそう指定すれば削除から保護され、削除のときには最終スナップショットを残す。
- マスターユーザーのパスワードは、RDS が作り、Secrets Manager のシークレットに保管し、ローテーションする。マスターユーザーとしてサインインするのは、データベースを準備するタスクだけである。
- 文脈はそれぞれ2つのシークレットを持つ。所有者のロールのものと、実行時のロールのものである（TPL-0009）。どちらも、キー `username`・`password`・`url` を持つ JSON である。パスワードはエフェメラルな値であり、書き込み専用の引数で書くので、Terraform の state には入らない。
- サービスは、実行時のロールのシークレットのキー `url` から `DATABASE_URL` を受け取り、TLS で接続する（`sslmode=require`）。
- デプロイの前に、1つの ECS のタスクが `db/Dockerfile` のイメージを動かす。そのスクリプト `db/prepare.sh` は、再開の途中かもしれないクラスターを待ち、マスターユーザーとして `db/bootstrap.sql` を実行し、ロールのパスワードをシークレットから設定する。そして、すべての文脈の `schema.sql` を pgschema で適用する（TPL-0009、TPL-0010）。最初の接続は5回まで試し、1回の接続は30秒待つ。

### 結果

- 良い点：使われていない stg にかかるのは、ストレージの料金だけである。コンピューティングの料金は、クラスターが動いている間しかかからない。
- 良い点：stg と prd は、同じモジュールと同じエンジンを使う。違うのは、キャパシティの種類と量だけである。
- 良い点：Serverless v2 は、負荷が上がれば範囲の中で大きくなる。インスタンスクラスを変える必要がない。
- 悪い点：一時停止のあとの最初のリクエストは、約15秒かそれ以上待たされる。stg を使う人やテストは、この遅れに気づく。
- 悪い点：コードは、一時停止のためだけにある決まり（接続プールに最小の接続数を持たせない、ヘルスチェックでデータベースを使わない、接続を再試行する）に従う必要がある。接続したまま放置された道具が1つあるだけで、stg は気づかれないまま止まらず、費用がかかり続ける。
- 悪い点：stg と prd でキャパシティの種類は違いうる。そのため、負荷をかけたときの stg のふるまいから prd を正確には予測できない。
- 悪い点：一時停止の間は、`pg_cron` の予定のようなデータベースの中の定期的な処理が動かない。一時停止の時点で進んでいた autovacuum の処理も取り消される。
- 悪い点：Aurora のマスターユーザーはスーパーユーザーではない。そのため、スキーマを所有者のロールに渡せるのは、そのロールのメンバーとしてだけであり、マスターユーザーはすべての所有者のロールの権限を継承する（TPL-0009）。
- 悪い点：`sslmode=require` は接続を暗号化するが、サーバーの証明書を RDS の CA に照らして検証しない。
- 悪い点：ロールの新しいパスワードがサービスに届くのは、サービスが起動し直したときである。パスワードを設定するタスクを実行してからサービスが起動し直すまでのあいだ、サービスの新しい接続は失敗する。
- 悪い点：AWS にはまだ何も適用していない。AWS Emulator は Aurora PostgreSQL をバージョン 17.9 までしか知らず、データベースも動かさない。そのため、リハーサルは 17.9 でモジュールを適用し、タスクは代わりに `make test-db-image` が手元の PostgreSQL に対して動かす。

### 確認の方法

- モジュール `database` の `capacity` の検証は、2種類のキャパシティの両方を指定した値とどちらも指定しない値、最大値より大きい最小値、0.5 ACU 刻みから外れたキャパシティを拒む。300〜86400 秒の範囲から外れた一時停止までの時間と、provisioned のクラスとしての `db.serverless` も拒む。モジュールのテスト（`make check-all` の `validate-terraform`）は、これらをそれぞれ試す。また、既定が 0 ACU からの Serverless v2 であることと、クラスターが暗号化され、削除から保護されることも確かめる。
- `rehearse-infra` は、stg の値でモジュールを AWS Emulator に適用し、prd の値で plan する（TPL-0017）。
- `make check-all` の `test-db-image` は、データベースを準備するイメージを手元の PostgreSQL に対して2回動かし、準備されたものを確かめる。動かすロールは、スーパーユーザーではないマスターユーザーである（TPL-0009）。
- 接続プールとヘルスチェックの設定は、レビューで確かめる。

## 選択肢の長所と短所

### Aurora で、Serverless v2 と provisioned のインスタンスを変数で選び、既定を Serverless v2 にする

- 良い点：使われていない stg はほとんど費用がかからず、prd は自由に選べ、1つのモジュールで両方をまかなえる。
- 悪い点：再開を待つ時間がかかり、クラスターが一時停止できるように、コードが決まりに従う必要がある。

### どの環境でも provisioned の Aurora のインスタンスを使う

- 良い点：性能が安定し、費用を予測しやすい。負荷が安定していれば、provisioned のインスタンスは同じキャパシティの Serverless v2 より安い。
- 悪い点：stg は1日中インスタンスの料金を払うか、手で止めたり起こしたりする必要がある。しかも、止めたクラスターは7日たつと AWS が自動で起動する。

### RDS for PostgreSQL

- 良い点：小さなインスタンスなら Aurora より安い。PostgreSQL の新しいメジャーバージョンも、これまではたいてい Aurora より先に RDS で使えるようになっている。
- 悪い点：0 まで縮めない。使われていない stg も、誰かが止めない限りインスタンスの料金がかかる。
- 悪い点：よく使われる Multi-AZ のインスタンスの構成では、インスタンスがストレージを共有する Aurora より、フェイルオーバーに時間がかかる。

### どの環境でも Serverless v2 を使い、最小値を 0 より大きくする

- 良い点：再開を待つ時間も一時停止のための決まりもなく、どこでも同じ種類のキャパシティを使える。
- 悪い点：stg でも、最小値（0.5 ACU 以上）の料金が1日中かかる。
- 悪い点：負荷が安定した prd では、同じキャパシティの provisioned のインスタンスより高くつく。

## 補足

- Aurora PostgreSQL は、2026年6月からメジャーバージョン18（バージョン 18.3）に対応している（[発表](https://aws.amazon.com/about-aws/whats-new/2026/06/amazon-aurora-postgresql-major-version-18)）。
- 2026年11月19日に AWS のドキュメントで確かめたこと：Aurora PostgreSQL 18 には、18.3（2026年6月11日に公開）、18.4、18.6 がある。最小 0 ACU の Serverless v2 は 18.3 から使え、アジアパシフィック（東京）リージョンでも使える。一時停止までの時間は 300〜86400 秒である。再開には約15秒かかり、24時間を超えて止まっていたあとは30秒以上かかる。モジュールの既定は 18.6 である。
- AWS ではまだ確かめていないこと：何も適用していないので、次のことは確かめていない。エンジンのバージョン、0 ACU での一時停止、クラスターの再開のあいだにデータベースを準備するタスクが待つ時間である。Aurora PostgreSQL 18 のマスターユーザーにできることも確かめていない（[AWS にデプロイする](../../guides/deploy.ja.md#最初の適用で確かめること)と、モジュールの README）。
- Aurora のドキュメントの [Scaling to zero ACUs with automatic pause and resume](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2-auto-pause.html)
