# TPL-0022: 道具のバージョンはエコシステムごとに1か所で固定し、全体の土台に mise を置く

## 背景と課題

`make check` と `make check-all` は、ランタイム・パッケージマネージャー・整形の道具・リンター・スキャナーなど、数十の道具を動かす。
人は macOS と Linux で、コーディングエージェントはそれぞれのサンドボックスで、CI はまっさらなマシンでこれらを動かす。
この中の2か所で道具のバージョンが違うと、ある場所では通るチェックが別の場所では落ち、その原因は見えにくい。

バージョンの番号だけでも足りない。
道具はリポジトリにアクセスできる状態で動くコードであり、CI ではトークンにもアクセスできる。
リリースがあとから差し替えられたり、ダウンロードの途中で改ざんされたりすると、その道具を入れたすべてのマシンで攻撃者のコードが動く。

誰にも手作業で道具を入れさせずに、どのマシンにもバイト単位で同じ道具を入れるにはどうすればよいか。

## 判断の基準

- 人・エージェント・CI が、どの道具も同じバージョンで動かす。
- ダウンロードしたものがロックしたときのものと違えば、インストールが失敗する。
- `make setup` の1つのコマンドで、すべてが入る。
- 何もグローバルに入れないので、1台のマシンにある2つのプロジェクトが互いに干渉しない。
- 道具の依存を、製品の依存に混ぜない。
- 各エコシステムで、そのエコシステムの道具と Renovate が扱えるロックファイルを使い続ける。

## 検討した選択肢

- 全体の土台に mise を置き、各エコシステムのパッケージはそのエコシステムのロックファイルで固定する
- aqua だけを使う
- asdf
- Nix または devbox
- コンテナイメージを唯一の環境にする
- 道具とバージョンの一覧を README に書く

## 決定

採用：「全体の土台に mise を置き、各エコシステムのパッケージはそのエコシステムのロックファイルで固定する」。ランタイムと単体のバイナリを1つのファイルにチェックサムとともに固定でき、パッケージの固定は、すでにそれを検証しているロックファイルに任せられるからである。

決まりは次のとおりである。

- `mise.toml` には、ランタイム（Go・Node.js・Python）、パッケージマネージャー（pnpm・uv）、単体のバイナリのそれぞれについて、正確なバージョンを書いて固定する。
- `mise.lock` には、すべての道具について、4つのプラットフォーム（Linux と macOS のそれぞれの x64 と arm64）の URL とチェックサムを記録する。テンプレートが固定する道具は、どれも4つのプラットフォームのすべてに配布物を出している。`locked = true` にしているので、ロックファイルに書かれていないものを入れようとすると失敗する。
- 配布元が来歴（GitHub の artifact attestations・cosign・SLSA）を提供している場合、mise はロックを書くときにそれを検証し、検証した来歴の種類を記録する。
- エコシステムのパッケージである道具は、そのエコシステムのロックファイルで固定する。npm の道具は `package.json` と `pnpm-lock.yaml` で固定する。Python の道具は `pyproject.toml` と（ハッシュ付きの）`uv.lock` で、Go の道具は `tools/go.mod` の `tool` ディレクティブで固定する。
- Makefile が、これらの道具をすべて `PATH` に載せる。道具は誰もグローバルに入れない。
- `GOTOOLCHAIN=local` により、Go が mise の入れたもの以外のツールチェーンをダウンロードすることはない。
- `mise.toml` を変えたあとは、`make tools-lock` で `mise.lock` を書き直す。
- デプロイの道具も `mise.toml` で固定する。Terraform、Terragrunt、AWS CLI（`aws-cli`。インフラのマイルストーンでは 2.41.0）である。`tools/scripts/infra.sh` と `tools/scripts/images.sh` は、イメージのプッシュとデータベースを準備するタスクの実行に AWS CLI を使う。リハーサルは、AWS Emulator に証明書をリクエストし、ホストゾーンを作るのに AWS CLI を使う。ワークフロー `Plan` と `Deploy` は、これらの道具と `jq` を `mise.toml` から入れ、それ以外は入れない。

この決定には、最初の計画と違う点が2つある。どちらも意図したものである。

- Go の道具は、バックエンドの `go.mod` ではなく、別のモジュール `tools/` に置く。最初の計画では、バックエンドのモジュールに置く予定だった。モジュールを分けると、道具の依存は、バックエンドのモジュールの依存グラフと SBOM のどちらにも入らない。ライセンスのスキャンも `tools/` を飛ばす（`scan-deps`、TPL-0024）。そのため、製品は自分が実際に動かすものだけを宣言できる。
- npm と Python の道具は、mise の `npm:` と `pipx:` のバックエンドでは入れない。これらのバックエンドは道具そのもののバージョンは固定するが、推移的な依存はロックしない。pnpm と uv は、推移的な依存をすべてハッシュ付きでロックする。

### 結果

- 良い点：1つのコマンドで、対応するどのマシンにも、バイト単位で同じ道具が入る。
- 良い点：リリースが差し替えられたり、ダウンロードが改ざんされたりすると、チェックサムが `mise.lock` のものと合わなくなり、インストールが失敗する。
- 良い点：製品の依存グラフ・SBOM・ライセンスのスキャンに、製品が使うものだけが入る。
- 悪い点：マニフェストが4種類（`mise.toml`・`package.json`・`pyproject.toml`・`tools/go.mod`）あり、それぞれにロックファイルとコマンドがある。
- 悪い点：mise そのものは、最初に手で入れる必要がある。リポジトリも `mise trust` で信頼する必要がある（これは `make setup` が実行する）。
- 悪い点：`mise.lock` には道具ごとに4つの項目があるので、更新のたびに多くの行が変わる。
- 悪い点：ロックがカバーするのは Linux と macOS だけである。Windows では WSL か dev container を使う。
- 悪い点：道具を足すには、インストールのコマンド1つでは済まない。`mise.toml` に項目を書き、`make tools-lock` を実行する必要がある。

### 確認の方法

- `make setup` は、`locked = true` のもとでの `mise install`、`pnpm install --frozen-lockfile`、`uv sync --locked` を実行する。どれも、ロックファイルがマニフェストと合わなければ失敗する。`make setup` は Go のモジュールのダウンロードと Go のビルドのキャッシュの準備も行うので、そのあとの `make check` はネットワークを使わない（TPL-0023）。
- Makefile は `GOFLAGS=-mod=readonly` を設定している。そのため、Go のコマンドは `go.mod` や `go.sum` を書き換える代わりに失敗する。`GOTOOLCHAIN=local` も Makefile が設定している。
- CI も同じファイルで同じ `make setup` を実行する。
- `make check-all` は、`mise.toml` を mise の公開しているスキーマで検証する（ターゲット `lint-schema-remote`）。
- 道具をグローバルに入れていないことは、レビューで確かめる。エージェントへの指示にも同じことが書いてある。

## 選択肢の長所と短所

### 全体の土台に mise を置き、各エコシステムのロックファイルを使う

- 良い点：ランタイム・パッケージマネージャー・バイナリを1つのファイルで固定できる。mise はほとんどのバイナリを aqua のレジストリからチェックサム付きで入れる。
- 良い点：各エコシステムで、その道具と Renovate が扱えるロックファイルを使い続けられる。
- 悪い点：4つのマニフェストをそろえておく必要がある。

### aqua だけを使う

- 良い点：チェックサムと来歴を検証し、レジストリは単体のコマンドラインの道具の大半をカバーしている。
- 悪い点：単体のコマンドラインの道具のために作られている。Python のように独自のインストーラーと環境を持つランタイムは対象の中心から外れるので、もう1つの管理の道具が残る。

### asdf

- 良い点：広く知られており、`.tool-versions` ファイルも単純である。
- 悪い点：プラグインはそれぞれの作者が書いたスクリプトで、ダウンロードを検証するかどうかもプラグインごとに違う。asdf 自体はチェックサムのロックファイルを持たない。

### Nix または devbox

- 良い点：すべての入力がハッシュで固定され、環境をそのまま再現できる。
- 悪い点：Nix はインストールが大きく、独自の言語も持つ。それを、すべての貢献者とすべてのエージェントのサンドボックスが必要とする。devbox は Nix を隠すが、下では Nix を必要とする。

### コンテナイメージを唯一の環境にする

- 良い点：1つのイメージにすべての道具が入り、それを動かすマシンはどれも同じものを持つ。
- 悪い点：ホストで動くエディターやエージェントからは道具が見えず、どのコマンドもコンテナの分だけ重くなる。
- 悪い点：イメージという成果物が1つ増え、そのビルド・固定・スキャン・更新が要る。

### 道具とバージョンの一覧を README に書く

- 良い点：一覧のほかに、入れるものも保守するものもない。
- 悪い点：バージョンはマシンごとにずれていき、ダウンロードを検証するものもない。エージェントは見つけたバージョンを何でも入れる。
