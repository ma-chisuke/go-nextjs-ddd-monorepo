# TPL-0022: ツールの版はエコシステムごとに1か所で固定し、全体の土台に mise を置く

## 背景と課題

`make check` と `make check-all` は、ランタイム・パッケージマネージャー・整形ツール・linter・スキャナーなど、数十のツールを動かす。
人は macOS と Linux で、コーディングエージェントはそれぞれのサンドボックスで、CI はまっさらなマシンでこれらを動かす。
この中の2か所でツールの版が違うと、ある場所では通るチェックが別の場所では落ち、その原因は見えにくい。

版の番号だけでも足りない。
ツールはリポジトリにアクセスできる状態で動くコードであり、CI ではトークンにもアクセスできる。
リリースがあとから差し替えられたり、ダウンロードの途中で改ざんされたりすると、そのツールを入れたすべてのマシンで攻撃者のコードが動く。

誰にも手作業でツールを入れさせずに、どのマシンにもバイト単位で同じツールを入れるにはどうすればよいか。

## 判断の基準

- 人・エージェント・CI が、どのツールも同じ版で動かす。
- ダウンロードしたものがロックしたときのものと違えば、インストールが失敗する。
- `make setup` の1つのコマンドで、すべてが入る。
- 何もグローバルに入れないので、1台のマシンにある2つのプロジェクトが互いに干渉しない。
- ツールの依存を、製品の依存に混ぜない。
- 各エコシステムで、そのエコシステムのツールと Renovate が扱えるロックファイルを使い続ける。

## 検討した選択肢

- 全体の土台に mise を置き、各エコシステムのパッケージはそのエコシステムのロックファイルで固定する
- aqua だけを使う
- asdf
- Nix または devbox
- コンテナイメージを唯一の環境にする
- ツールと版の一覧を README に書く

## 決定

採用：「全体の土台に mise を置き、各エコシステムのパッケージはそのエコシステムのロックファイルで固定する」。ランタイムと単体のバイナリを1つのファイルにチェックサムとともに固定でき、パッケージの固定は、すでにそれを検証しているロックファイルに任せられるからである。

決まりは次のとおりである。

- `mise.toml` には、ランタイム（Go・Node.js・Python）、パッケージマネージャー（pnpm・uv）、単体のバイナリのそれぞれについて、正確な版を書いて固定する。
- `mise.lock` には、すべてのツールについて、4つのプラットフォーム（Linux と macOS のそれぞれの x64 と arm64）の URL とチェックサムを記録する。`locked = true` にしているので、ロックファイルに書かれていないものを入れようとすると失敗する。
- 配布元が来歴（GitHub の artifact attestations・cosign・SLSA）を提供している場合、mise はロックを書くときにそれを検証し、検証した来歴の種類を記録する。
- エコシステムのパッケージであるツールは、そのエコシステムのロックファイルで固定する。npm のツールは `package.json` と `pnpm-lock.yaml` で固定する。Python のツールは `pyproject.toml` と（ハッシュ付きの）`uv.lock` で、Go のツールは `tools/go.mod` の `tool` ディレクティブで固定する。
- Makefile が、これらのツールをすべて `PATH` に載せる。ツールは誰もグローバルに入れない。
- `GOTOOLCHAIN=local` により、Go が mise の入れたもの以外のツールチェーンをダウンロードすることはない。
- `mise.toml` を変えたあとは、`make tools-lock` で `mise.lock` を書き直す。

この決定には、最初の計画と違う点が2つある。どちらも意図したものである。

- Go のツールは、バックエンドの `go.mod` ではなく、別のモジュール `tools/` に置く。最初の計画では、バックエンドのモジュールに置く予定だった。モジュールを分けると、ツールの依存がバックエンドのモジュールの依存グラフにも、SBOM にも、ライセンスのスキャンにも入らない。そのため、製品は自分が実際に動かすものだけを宣言できる。
- npm と Python のツールは、mise の `npm:` と `pipx:` のバックエンドでは入れない。これらのバックエンドはツールそのものの版は固定するが、推移的な依存はロックしない。pnpm と uv は、推移的な依存をすべてハッシュ付きでロックする。

### 結果

- 良い点：1つのコマンドで、対応するどのマシンにも、バイト単位で同じツールが入る。
- 良い点：リリースが差し替えられたり、ダウンロードが改ざんされたりすると、チェックサムが `mise.lock` のものと合わなくなり、インストールが失敗する。
- 良い点：製品の依存グラフ・SBOM・ライセンスのスキャンに、製品が使うものだけが入る。
- 悪い点：マニフェストが4種類（`mise.toml`・`package.json`・`pyproject.toml`・`tools/go.mod`）あり、それぞれにロックファイルとコマンドがある。
- 悪い点：mise そのものは、最初に手で入れる必要がある。リポジトリも `mise trust` で信頼する必要がある（これは `make setup` が実行する）。
- 悪い点：`mise.lock` にはツールごとに4つの項目があるので、更新のたびに多くの行が変わる。
- 悪い点：ロックがカバーするのは Linux と macOS だけである。Windows では WSL か dev container を使う。
- 悪い点：ツールを足すには、インストールのコマンド1つでは済まない。`mise.toml` に項目を書き、`make tools-lock` を実行する必要がある。

### 確認の方法

- `make setup` は、`locked = true` のもとでの `mise install`、`pnpm install --frozen-lockfile`、`uv sync --locked` を実行する。どれも、ロックファイルがマニフェストと合わなければ失敗する。
- Makefile は `GOFLAGS=-mod=readonly` を設定している。そのため、Go のコマンドは `go.mod` や `go.sum` を書き換える代わりに失敗する。`GOTOOLCHAIN=local` も Makefile が設定している。
- CI も同じファイルで同じ `make setup` を実行する。
- `make check-all` は、`mise.toml` を mise の公開しているスキーマで検証する（ターゲット `lint-schema-remote`）。
- ツールをグローバルに入れていないことは、レビューで確かめる。エージェントへの指示にも同じことが書いてある。

## 選択肢の長所と短所

### 全体の土台に mise を置き、各エコシステムのロックファイルを使う

- 良い点：ランタイム・パッケージマネージャー・バイナリを1つのファイルで固定できる。mise はほとんどのバイナリを aqua のレジストリからチェックサム付きで入れる。
- 良い点：各エコシステムで、そのツールと Renovate が扱えるロックファイルを使い続けられる。
- 悪い点：4つのマニフェストをそろえておく必要がある。

### aqua だけを使う

- 良い点：チェックサムと来歴を検証し、レジストリは単体のコマンドラインツールの大半をカバーしている。
- 悪い点：単体のコマンドラインツールのために作られている。Python のように独自のインストーラーと環境を持つランタイムは対象の中心から外れるので、もう1つの管理ツールが残る。

### asdf

- 良い点：広く知られており、`.tool-versions` ファイルも単純である。
- 悪い点：プラグインはそれぞれの作者が書いたスクリプトで、ダウンロードを検証するかどうかもプラグインごとに違う。asdf 自体はチェックサムのロックファイルを持たない。

### Nix または devbox

- 良い点：すべての入力がハッシュで固定され、環境をそのまま再現できる。
- 悪い点：Nix はインストールが大きく、独自の言語も持つ。それを、すべての貢献者とすべてのエージェントのサンドボックスが必要とする。devbox は Nix を隠すが、下では Nix を必要とする。

### コンテナイメージを唯一の環境にする

- 良い点：1つのイメージにすべてのツールが入り、それを動かすマシンはどれも同じものを持つ。
- 悪い点：ホストで動くエディターやエージェントからはツールが見えず、どのコマンドもコンテナの分だけ重くなる。
- 悪い点：イメージという成果物が1つ増え、そのビルド・固定・スキャン・更新が要る。

### ツールの一覧を README に書く

- 良い点：一覧のほかに、入れるものも保守するものもない。
- 悪い点：版はマシンごとにずれていき、ダウンロードを検証するものもない。エージェントは見つけた版を何でも入れる。
