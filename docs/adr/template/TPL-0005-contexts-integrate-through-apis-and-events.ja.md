# TPL-0005: 区切られた文脈どうしは直接依存せず、HTTP の API とイベントで連携する

## 背景と課題

区切られた文脈（TPL-0003）が役に立つのは、その境界が保たれている間だけである。
境界は少しずつ崩れる。
ある文脈が、詰め替えを省くために別の文脈の型を import する。API の呼び出しを省くために別の文脈のテーブルを読む。2つのテーブルの整合を保つために外部キーを足す。
1つ1つは安く見える。
しかし積み重なると、モデルどうしが結び付く。ある文脈の変更が別の文脈を壊し、文脈を別々にデプロイできなくなる。

このリポジトリでは、こうした近道がすぐ手の届くところにある。
すべての文脈が1つの Go モジュール（TPL-0002）と1つのデータベース（TPL-0009）を共有しているので、ほかの文脈のコードもテーブルも、import 1行やクエリ1つで使えてしまう。

見本の文脈どうしも、互いを必要とする。
Reservation は、会議室の定員と使える時間帯を知る必要がある。これを持っているのは Facility である。
Notification は、予約が確定したことや取り消されたことを知る必要がある。これを決めるのは Reservation である。

文脈どうしは、互いのコードと保存先に依存しないまま、どうやってデータをやりとりすればよいか。

## 判断の基準

- ある文脈は、別の文脈を壊さずに、自分のモデルとテーブルを変えられる。
- 各文脈は独立したサービスとして動く（TPL-0014）。そのため、呼び出す相手にはネットワーク越しに届く必要がある。
- 決まりをプログラムで検査する。どの近道も、コード1行で手が届くからである。
- 連携には、公開された標準と生成コードを使う。手書きの通信手順は使わない。

## 検討した選択肢

- HTTP の API と統合イベントで連携し、直接には依存しない
- 1つのプログラムの中で、モジュールどうしを関数として呼ぶ（モジュラーモノリス）
- テーブルを共有する、またはスキーマをまたいで結合する
- 共有カーネルのライブラリ

## 決定

採用：「HTTP の API と統合イベントで連携し、直接には依存しない」。文脈ごとに別々にデプロイする形に合い、しかも各文脈が自分のモデルを単独で変えられる選択肢は、これだけだからである。

決まりは次のとおりである。

- ある文脈は、別の文脈の Go のパッケージを import しない。
- ある文脈は、別の文脈のテーブルを読み書きしない。文脈をまたぐ外部キーも作らない。
- 同期的に必要なものは、相手の文脈の HTTP の API を呼んで得る。呼び出しには、相手の OpenAPI の文書から生成したクライアントを使う（TPL-0006）。受け取った答えは、モデル変換装置で自分のモデルに変換する。モデル変換装置は自分のアダプターに置き、ポートを通して使う（TPL-0004）。
- API を持つ文脈は、それを共用サービスとして提供する。API とその OpenAPI の文書は公開された言語であり、内部のモデルとは切り離しておく。そうすれば、API を変えずにモデルを変えられる。
- 非同期の連携では、文脈は統合イベントを発行し、ほかの文脈がそれを購読する（TPL-0013）。

見本では、Reservation が HTTP で Facility に会議室の定員と使える時間帯を問い合わせ、それを自分の言葉に変換する。
Reservation は、予約の確定と取り消しをイベントで Notification に伝える。

文脈どうしは、同じリポジトリにあっても HTTP を使う。各文脈が ECS の上で独立したサービスとして動くからである（TPL-0014）。
実行時には、ある文脈から別の文脈の関数を呼ぶことはできない。開発中だけプロセス内で呼ぶと、本番にある遅延と障害が見えなくなる。

### 結果

- 良い点：API とイベントの互換性さえ保てば、ある文脈がテーブルやドメインの名前・分け方・形を変えても、別の文脈は変えずに済む。
- 良い点：文脈の間の依存は、生成したクライアントとイベントの購読という2か所ですべて見える。
- 良い点：文脈の間の呼び出しは、画面が使う API と同じ種類の契約と、同じチェックを使う（TPL-0007）。
- 悪い点：文脈の間の呼び出しは、失敗したりタイムアウトしたりしうる。呼ぶ側には、タイムアウト・再試行・冪等な操作が要る。相手の文脈が止まっている間にどうするかも決めなければならない。
- 悪い点：イベントで届くデータについては、結果整合性しか得られない。短い間、文脈はすでに古くなったデータをもとに動く。
- 悪い点：文脈は、ほかの文脈から必要なデータの写しを持ち、その写しを最新に保たなければならない。
- 悪い点：2つの文脈のデータを合わせて見せる画面や帳票は、両方の API を呼ぶか、写しを持つ必要がある。スキーマをまたぐ結合は許されない。
- 悪い点：小さなチームでも、小さなやりとりのために契約・クライアント・変換を書く。1つのプログラムなら要らない手間である。

### 確認の方法

この決まりを守るチェックは、まだない。最初の文脈とともに加わる（マイルストーン M1）。
チェックごとに、捕まえる近道と、失敗する時点が違う。

| 近道 | チェック | 失敗する時点 |
|---|---|---|
| 別の文脈の層の import | Go の `internal` ディレクトリ。`backend/internal/<context>/internal/...` を import できるのは、`backend/internal/<context>/` の中のコードだけである | コンパイル時 |
| 別の文脈の最上位のパッケージ（`module.go` のあるパッケージ）の import | import の lint（depguard か go-arch-lint）。これを import できるのは `cmd/<context>` だけである | `make check` |
| 別の文脈のテーブルへのクエリ | 文脈ごとに設定した sqlc。その文脈の `schema.sql` だけを読む（TPL-0011） | コードの生成時 |
| 実行中の、別の文脈のスキーマへのアクセス | 文脈ごとのデータベースのロール。権限は自分のスキーマにだけある（TPL-0009） | 実行時 |
| 文脈をまたぐ外部キー | 各 `schema.sql` が、ほかのスキーマを参照していないかを調べるチェック | `make check` |

`internal` ディレクトリだけでは足りない。
文脈の最上位のパッケージは `backend/internal/` の直下にあるので、`backend/` の下のどのパッケージからも import できてしまう。
その穴を、import の lint がふさぐ。

## 選択肢の長所と短所

### HTTP の API と統合イベントで連携し、直接には依存しない

- 良い点：文脈ごとに、別々にデプロイし、規模を変え、変更できる。
- 良い点：文脈の間の契約が明示され、画面向けの API と同じチェックがそれを守る。
- 悪い点：文脈の間の呼び出しは、すべてネットワークを越える。遅延も障害もついてくる。

### 1つのプログラムの中で、モジュールどうしを関数として呼ぶ（モジュラーモノリス）

- 良い点：呼び出しはただの関数呼び出しである。ネットワークもシリアライズもなく、1つのトランザクションで複数のモジュールにまたがれる。
- 良い点：小さなチームにはいちばん簡単な始め方であり、それでもモジュールごとにコードを分けておける。
- 悪い点：文脈ごとに別々にデプロイする形（TPL-0014）に合わない。あとから移ると、すべての呼び出しがネットワーク越しになる。呼ぶ側は、それまで扱う必要のなかった障害を扱うことになる。
- 悪い点：モジュールをまたぐトランザクションは、データどうしを結び付け、あとからほどくのが難しい。

### テーブルを共有する、またはスキーマをまたいで結合する

- 良い点：1つのクエリで2つの文脈のデータが一度に得られ、結果は常に整合している。
- 悪い点：テーブルが、誰も宣言していない契約になる。ある文脈で列を変えると別の文脈のクエリが壊れ、それに実行時より前に気付くチェックはない。
- 悪い点：あとで文脈に専用のデータベースを持たせる道を閉ざす。

### 共有カーネルのライブラリ

- 良い点：2つの文脈が合意した型を、1回書けば済む。
- 悪い点：ライブラリを変えるには、それを使うすべての文脈の合意が要る。変えれば、そのすべてをビルドし直し、デプロイし直すことになる。
- 悪い点：こうしたライブラリは、共通のモデルへと育ちやすい。これは、文脈を区切ることで避けようとしている結び付きそのものである。
