# Notification

Notification は、会議の主催者に予約のことを知らせる役を受け持つ。予約が確定したときと、取り消されたときに、メールを送る。
予約そのものは受け持たない。それは Reservation が受け持ち、Notification は予約について、Reservation のイベントに含まれることだけを知る。
以下の言葉は[用語集](glossary.ja.md)の言葉である。

## 業務領域の種類

補完の業務領域である。出来事をメールで知らせることは必要だが、製品をほかと分ける要素ではない。Notification に固有の決まりも1つしかない。イベント1つにつき、メールを1回だけ送ることである。
そこで Notification はトランザクションスクリプトで書く（TPL-0003）。`domain` パッケージを持たず、`internal/app/` のユースケースがイベントを読み、sqlc が生成したクエリを呼び、メールをメーラーに渡す。
一般の業務領域ではない。メールの文面と、どのイベントを知らせるかの選択は、この文脈に固有だからである。一般的なのはメールの配送だけであり、それはメールサーバーが担う。

## 公開する API

ない。Notification はワーカーであり、自分のキューから Reservation のイベントを受け取るだけで、リクエストには答えない。そのため、API 文書も problem も持たない。
ほかの文脈が Notification に働きかける手段は、イベントを発行することだけである（TPL-0005、TPL-0013）。

## イベント

Notification はイベントを発行しない。受け取るのは、[`contracts/events/notification.asyncapi.yaml`](../../../contracts/events/notification.asyncapi.yaml) が宣言する、次の Reservation のイベントである。

| イベント | データの契約 | Notification がすること |
|---|---|---|
| `reservation.ReservationConfirmed.v1` | [`ReservationConfirmed.v1.json`](../../../contracts/events/reservation/ReservationConfirmed.v1.json) | 予約が確定したことを、時間帯と参加人数を添えて、メールで主催者に知らせる。Reservation は予約を変更したときにもこのイベントを発行するので、変更のたびに、新しい時間帯を書いた同じ種類のメールがもう1通届く。 |
| `reservation.ReservationCancelled.v1` | [`ReservationCancelled.v1.json`](../../../contracts/events/reservation/ReservationCancelled.v1.json) | 予約が取り消されたことを、メールで主催者に知らせる。 |

ほかの種類のイベントは、ログに残して無視し、処理したものとして扱う。
この2種類のイベントでも、データが契約を破っているもの（主催者のアドレスがないものなど）の処理は失敗する。そのイベントはもう一度届き、最後の試行のあと、ブローカーが Notification のデッドレターキューに移す。

## 決まり

- 配信は少なくとも1回だが、イベント1つにつきメールは1回だけ送る（TPL-0013）。Notification は1つのトランザクションの中で、メールを `notifications` に記録し、メールを送り、コミットする。`notifications` にはイベントの id の一意制約があるので、同じイベントの2つ目の記録は拒まれる。記録がすでにあれば、何も送らない。
- 同じイベントが同時に2回配信されても、送るメールは1通である。2つ目の記録は1つ目のトランザクションが終わるのを待ち、そのコミットのあとで、すでにある記録を見つける。
- メールの送信に失敗すると、記録はロールバックされ、イベントはあとでもう一度届く。
- メールを2回送る場合が1つだけある。メールを送ったあとで、その記録のコミットが失敗した場合である。イベントはもう一度届き、記録は見つからない。少なくとも1回の配信では、メールサーバーの助けなしにこれを避けられない。避けるには、メールサーバーがもう一度届いたメールを見分けなければならない。Notification はこの時間の幅を短くしている。メールを送ったあとのコミットは、配信の期限が来ても打ち切らない。
- イベントは、順序が入れ替わって届くことがある。たとえば、予約の取り消しがその確定より先に届く。Notification は届いたイベントのメールをそのつど送り、同じ予約のイベントどうしを比べない。そのため主催者は、イベントが届いた順のままメールを受け取ることがある。

## サンプルとしての制約

- メールは、会議室を id で示し、時間帯を UTC で書く。イベントには会議室の名前もタイムゾーンも含まれないからである。製品では、それらを加えた新しいバージョンのイベントを発行するか、メールを送るたびに Facility へ問い合わせることになる。
- メーラーは、手元の環境の Mailpit に、認証も TLS もない素の SMTP で送る。クラウドのメールサービスには、`Mailer` の別のアダプターが要る。

## ほかの文脈から必要とするもの

- Reservation からは、そのイベントを、JSON Schema が定めるとおりの形で受け取る。`internal/app/events.go` がモデル変換装置である。各イベントのデータを Notification の構造体に読み込み、メールに要るプロパティを確かめる。読まないプロパティは無視するので、Reservation はプロパティを加えても Notification を壊さない。単体テストは2つの JSON Schema のすべての例をメールにするので、Notification の読めない例があれば、テストは失敗する。
- Facility からは何も必要としない。
- SMTP を受け付けるメールサーバーが要る。そのアドレスと、メールの差出人のアドレスは、コマンドが渡す。
